# Rules by change class

Imperative rules per change class: tool registration, skill payloads, the live E2E stand, light mode and deliverables, retention, delegated subagents, cancellation, onboarding and settings, transport and late-result custody, LLM calls, timeout/wait control, and loop/acceptance state machines. Each section names its enforcing test or marks the rule review-only and points to ARCHITECTURE for mechanism instead of restating it. `docs/CHECKLISTS.md` remains the only reviewer scorer; its `development_compliance` item points at this handbook as a whole.

### Tool registration and guard surfaces

- A new Tool: export it from `get_tools()` as a `ToolEntry` in `registry.py`, give it an explicit `ouroboros/safety.py::TOOL_POLICY` entry (`POLICY_SKIP` for trusted built-ins, `POLICY_CHECK` for opaque or outward-facing ones) and declare its capability class in `ouroboros/tool_capabilities.py`. Without the policy entry it falls through to `DEFAULT_POLICY = POLICY_CHECK` and pays a light-model call per invocation. A child profile receives it only when that narrower principal should.
- A tool that writes the repo working tree also joins `_ROOT_ARG_REPO_WRITE_TOOLS` and canonicalizes its target paths (`_PATH_NORMALIZED_TOOLS` for a top-level `path`; `canonical_repo_relative_path` plus `_payload_write_paths` for payload-borne paths): visibility checks stay green while the write guard is missing, so tests exercise the real guard chain (ARCHITECTURE §6 "Tool capability and execution").
- Forwarding host wrappers take their own arguments positional-only; never rename or denylist a public tool keyword to avoid collision (`tests/test_pause_forwarding_names.py`).
- Read-only producers report admitted absent targets as typed misses only after query, confinement, runtime and protected-artifact checks; denials and bad content remain errors (`tests/test_discovery_miss_warnings.py`).
- New memory/data files: decide in the same change whether they enter LLM context (`context.py`).

Enforcement: CHECKLISTS items 11(g) and 14 (`tool_registration`); `tests/test_tool_api_v2_public_surface.py` pins the public schema/registry contract and `tests/test_safety_policy.py::test_tool_policy_covers_all_builtin_tools` the policy fallthrough; CHECKLISTS item 25 (`context_building`) backstops the context decision.

### Skill repair and payload lanes

- Repair is ordinary managed development carrying the selected skill, source request and admitted revision; the Repair-and-run request is a real owner message on the ordinary task path. The model enabling the repaired skill resolves that source, never a client `allow_enable` flag; a later direct owner disable wins and a load-error revert is not one. `skill_repair` records are selectors, never a reduced tool profile.
- Installed payloads are ordinary directories; a delegated Git copy is optional. Check the known revision before an operation and record the observed revision after opaque process work without claiming exclusive authorship; no long shell lock, no automatic rollback.
- Every path form uses the existing payload binding owners: a valid `TaskConstraint` supplies omitted skill-name/bucket selectors, and explicit selectors must match the physical payload.
- Review, grants, dependency readiness, desired enablement and actual execution are independent facts: a dependency or load failure never rewrites the review verdict, and an unchanged reviewed snapshot resumes through its free replay. Skill-review convergence keys on the lifecycle's group `review_round` (`snapshot_attempt` is display only).
- UI, CLI commands and task tools call the shared operation owners. Actor identity is host-derived: an owner-only action needs a real member chat/quiz/mailbox source naming the exact skill, revision and items; a synthetic reference creates no permission, and Repair implies neither grant-all, attestation nor deletion.
- Test the real installed script/tool/HTTP/widget/companion after review and prerequisites, repeat after corrections, inspect a widget screenshot. Execution receipts name the dispatched revision; they are not PASS.

Mechanism: ARCHITECTURE §13; §6 "Skills and extensions". Enforcement: `tests/test_skill_payload_binding.py`, `tests/test_skill_lifecycle_actions.py`; `tests/test_review_cycles_gates.py` pins the replay fingerprint; UI lane `tests/test_ui_smoke_skill_lifecycle.py`.

### Extension dispatch and isolated dependencies

- A `type: extension` skill with a reviewed isolated dependency env or a payload-native marker (`.so`, `.dylib`, `.dll`, `.pyd`) never imports `plugin.py` or runs handlers inside `server.py`, even when the dependency tree looks pure-Python: `extension_process_runner` dispatches it in short-lived child processes; only no-dependency pure-Python extensions use `extension_loader`'s in-process PluginAPI. Containment, not admission: a native payload still faces skill review.
- A child crash, invalid JSON, timeout or abort answers as a normal tool error, HTTP 502 or WS log message; a child `SIGABRT` is a handled extension failure, not a server crash. Add no host-process fallback that imports native-risk modules.

Mechanism: ARCHITECTURE §13. Enforcement: `tests/test_extension_process_runner.py`.

### Declared skill resources and builds

- Exact downloads and literal build/check argv reuse the isolated dependency owner: a new declaration needs a fresh executable review and hash-covered specs; the pinned payload is revalidated before its processes launch.
- Package-manager success is not proof of the requested function; only an explicitly declared check is. Resolved versions, hashes and diagnostics go into the existing dependency records; verified caches stay outside the replaceable payload/env.
- Keep wheel-only and npm ignore-scripts unless the entry opts into the build action. Large downloaded or built resources belong to the isolated dependency path, not a giant source patch.
- Deno flags express the script's current effects and the task's network constraints, not new grants or a stronger claimed OS sandbox.

Mechanism: ARCHITECTURE §13. Enforcement: `tests/test_skill_install_resources.py`.

### Task contract resource policy

- Outside Cyber Pro, `resource_policy.protected_artifacts` is execute-only: the declared path may run as a black box; byte reads, copy/hash/static introspection, tracing and debugging of it are refused (ARCHITECTURE §6 "Safety and runtime mode").
- Acceptance claims are bounded advice, never gates or taxonomies; `success_criteria` is an input alias; children receive only claims explicitly passed through `schedule_subagent`. Bind reviewer `evidence_refs` by exact host-packet membership, never fuzzy matching, file reads or re-execution, and change only the clean bit and disclosure, never actor parsing, quorum or verdict (ARCHITECTURE §6 "Task acceptance", §11.1).

Enforcement: `tests/test_acceptance_claims_wiring.py`, `tests/test_protected_artifacts_policy.py`.

### Skill-defined Presence

- Behavior is portable, authority installation-local: a reviewed `presence:` profile declares instructions, context topics, bounded runtime defaults and conceptual tool/script/resource requests, never credentials, room ids or one installed tool spelling; `presence_capabilities.py` stores the owner's exact selections outside the payload, fingerprinted by the request semantics that authorize them. Presence keeps canonical shared memory and derives no Project or forked drive from it (ARCHITECTURE §6 "Skills and extensions").
- Presence authority is a positive immutable ceiling, never a denylist or a prompt promise: admission requires the owner-created binding plus an installed, enabled, freshly executable behavior skill and every required selection, then freezes fingerprints, grants, argument bindings, runtime slot and round limit into `task_contract.capability_ceiling`, which schema discovery and execution enforce for every tool class.
- `state/presence_bindings.json` is host-owned authority: a transport token resolves only bindings naming that exact transport skill, and provider/account/conversation/thread must match the binding origin; identities are never recovered from message text (turn flow: ARCHITECTURE §12).
- Each admitted event runs a fresh agent under a deterministic binding-plus-source-event task id, a cross-process state-root-wide turn cap and per-conversation serialization; the transport's durable custody owns arrival FIFO. Add no transport-specific scheduler, memory silo, core outbox or resident cross-room agent.
- Every descendant producer (promotion, `schedule_followup`) copies the Presence carrier, admitted workspace and capability ceiling by value or refuses the transition. A Presence caller reads, steers and cancels only roots of its own binding.
- Knowledge-topic and scratchpad mutation each serialize on one stable lock, so concurrent owner and Presence turns cannot overwrite a newer projection with an older render.

Enforcement: `tests/test_presence_admission.py` (parsing, admission, schema and execution filtering, binding/token/origin checks, idempotency and ordering, inheritance); provider-adapter E2E is separate evidence.

### Devtools isolation

`devtools/` is tracked operator code outside runtime package discovery and the import graph: runtime modules, `server.py`, web modules and build scripts never import it; generated outputs live in an explicit external root, never in `repo/` or live `data/`; domain methodology lives beside the devtool, not in core governance docs. Review-only (ARCHITECTURE §1 "Devtools boundary").

### Live E2E stand (`devtools/e2e_live/`)

`python -m devtools.e2e_live.run_live_lanes` exercises owner-shaped work (the SM1, SW1 and SK1 scenarios) on isolated real servers; `stub_lane.py` reuses the loopback model and review answers of `tests/system_e2e/harness.py` for the `--stub` rehearsal. The rule that binds runtime changes: keep this opt-in stand outside runtime imports and default local evolution. Its operation is the operator manual `devtools/e2e_live/README.md`, in these sections:

#### Scenario acceptance

Judge durable artifacts and real consumer observations, never model prose or an HTTP 200 alone (`devtools/e2e_live/README.md#scenario-acceptance`).

#### Seed and settings

One admitted, clean, detached seed; settings from the tree's defaults plus explicit stand knobs, never the owner's live settings; the provider key by environment name only (`devtools/e2e_live/README.md#seed-and-settings`).

#### Budget admission and ordering

Admit an attempt only while settled spend, in-flight reservations and its own reservation fit the run cap, FIFO by dispatch index; `run_live_lanes.lane_spend` reads `state/usage.sqlite` (the journal only for an older seed) (`devtools/e2e_live/README.md#budget-admission-and-ordering`).

#### Self-modification and browser lifetime

`--self-mod` is opt-in; only SM1 owes the real re-exec/absorb proof, which liveness alone never passes; the browser client reopens across a restart on the lane thread (`devtools/e2e_live/README.md#self-modification-and-browser-lifetime`).

#### Reports, focused verification and CI

Run roots are append-only outside `repo/` and live `data/`; the focused contracts are `tests/test_e2e_live_*` plus `tests/test_server_runner_absorb_wait.py`; the `e2e-live` CI job runs only on an explicit `e2e_live=true` dispatch (`devtools/e2e_live/README.md#reports-focused-verification-and-ci`).

### Light mode and external deliverables

- `runtime_mode=light` is a self-modification boundary, not a deliverables boundary: Light refuses mutation of the Ouroboros repo and control plane and still builds user deliverables outside them; Pro permits protected rewrites; Cyber follows the same effective Access owner (`ouroboros/config.py`; the ladder: ARCHITECTURE §6 "Safety and runtime mode").
- Flow: `task_drive` for scratch, `artifact_store` for the canonical deliverable, `user_files` for the owner's visible copy (ARCHITECTURE §6 "Tool capability and execution"). `write_file(root=user_files)` and declared process `outputs` register the canonical artifact; a rewrite keeps the previous copy as recovery history, never a second deliverable list; `root=deliverables` is read/list/search-only for every actor.
- Task files stream (`artifacts.stream_artifact_file`, atomic `copy_artifact_file`), never a whole dataset in a bytes object; a changed file or missing member is an explicit capture failure. Blocking HTTP admission and materialization run off the event loop (`gateway._helpers.run_sync_to_completion`); cancelling an HTTP waiter never cancels the admitted task. `send_file` uses immutable captured names, so an earlier delivery URL never aliases a later rewrite. Inputs stay outside deliverable inventories; the inline preview never stands in for the full `attachment_manifest_ref` (ARCHITECTURE §1).
- `scratch=[...]` and `outputs=[...]` are distinct channels: scratch is ephemeral in-cwd verification, exempt from the undeclared-output guard, never an artifact, adopted only with a declaration-time sha through `artifacts.record_task_scratch` and excluded from the workspace patch; the guard verifies candidates post-exec by stat, so a path mention is not a write (ARCHITECTURE §6 "Safety and runtime mode").
- cwd: an omitted cwd selects `active_workspace`; a light direct task needing writable scratch selects `task_drive` explicitly; a long-running service in light uses an explicit external/task/artifact cwd and its declared `outputs` are copied when it stops; every script observes the requested cwd (`ouroboros/tools/shell.py`). Policy outcomes: ARCHITECTURE §6 "Tool capability and execution".
- Outside Cyber Pro the default shell lane carries target-aware git policy (`git_shell_policy.py`): `commit_reviewed` is the remedy for self-repo changes; `git init`/`commit`/`push` in an external project tree is legitimate task work.
- `claude_code_edit` is not a tool name; its one-way compatibility contract stays: a saved `disabled_tools=["claude_code_edit"]` also withholds `delegate_start` (registry `_disabled_tools`), whose exact-payload class is `delegate_start(subagent_id=..., prompt=..., root="skill_payload", bucket=..., skill_name=...)`. `run_ci_tests` has no alias; `get_github_checks` reads a commit's checks and `docs/CHECKLISTS_ARCHIVE.md` records outcomes with no successor. Claim successor parity only after a persistent golden test proves every supported user-visible target class through the replacement to its final outcome; deleted-test tombstones prove removal, not parity; dropping a target class needs an explicit owner-approved record naming the lost outcome. `runtime_data/uploads`, skill payloads and owner state directories are not generic artifact transport.

Enforcement: `tests/test_v674_light_mode_cwd.py` (cwd selection and what light refuses), `tests/test_deliverables_layout.py` (placement and output manifest), `tests/test_git_shell_policy.py`; successor parity and artifact transport are review-only.

### Own-body candidates and adoption

Mechanism: ARCHITECTURE §6 "Own-body candidates" and §2. Rules a change keeps:

- One identity. A consumer of the body root reads `ctx.repo_dir` / `system_repo_dir_for` (the candidate when bound); only what must describe the running body (review governance, the restart marker, rollback) reads `body_candidate.serving_repo_dir_for`. Never rebind `Env`; never give a candidate workspace-mode authority.
- Prepare before effects, by seam: a new body-writing tool joins `body_candidate.authoring_seam`. Never classify command text or infer a candidate from a room, name, date or PID; ownership moves only from a terminal task record whose ledgered processes are dead (`live_lineage_processes`).
- Attribution is the lineage's own baseline (`mutation_attribution.capture_mutation_baseline`); the commit gate resolves attributed paths on `ctx.repo_dir` with no candidate bypass. A process inside the candidate or an admitted own-body child copy gets its isolated environment or a typed refusal.
- Retention never deletes unique work on age: extend `unique_work` / `_preserve` together, an incomplete capture retains the directory, and a GC verdict computed outside the registry lock applies only while `verdict_holds` under it.
- The old generation never writes the serving tree for an adoption: arm only from the existing stop owners' outcomes (PID census, `stop_owned_work`'s ownership set, reaped children); add no wait, drain or PID probe, nothing on the Panic path. Boot settles `adopted` only for a process that attested the switched tree before its imports (`sys._ouroboros_body_generation`).
- The hook in `ouroboros/__init__.py` and `body_switch.py` stay stdlib-only and compatible with the helper an older body captured; a body without the hook receives it through an ordinary release, never by adoption.
- No generic reset on the adoption path (`holds_checkout` covers landed, returned and open transitions); returning Git files never claims restored dependencies; a launcher whose loaded modules changed re-executes on exit 42 (`launcher_sources_changed`), never a blanket relaunch.
- A candidate commit is never auto-pushed; the serving push sends only reachable annotated tags (`--follow-tags`). The release gate names the form from the diff, `numbered` or `neutral` (`neutral_allowed` for the prepared index lane and a bound candidate); a partial carrier move is a finding in either form. Crash recovery grants no new adoption authority.

Enforcement: `tests/test_body_adoption.py` with `tests/test_body_candidate.py`. Not exercised there: Windows handover, the packaged launcher's frozen code, a native Android host, an end-to-end `commit_reviewed` with live reviewers on a candidate.

### Runtime cleanup and retention

- Age-based GC of disposable runtime artifacts shares one owner knob, `OUROBOROS_GC_RETENTION_DAYS` (default and clamp: ARCHITECTURE §7), and the helpers in `ouroboros/retention.py` (`age_cutoff`, `clamp_retention_days`, `get_gc_retention_days`); no hand-rolled cutoff math. Prune functions keep an explicit `retention_days=` parameter, only the default resolution reads the knob, and startup prunes are wired from `server.py`.
- A subsystem that needs its own lifetime passes explicit `retention_days=`; an owner-settable one is an ordinary `OUROBOROS_<SUBSYSTEM>_RETENTION_DAYS` in `SETTINGS_DEFAULTS` clamped through `clamp_retention_days`. Do not restore the consolidated keys or keep a knob that deletes nothing.
- Durable artifacts are not age-pruned: genesis projects (`OUROBOROS_SUBAGENT_PROJECTS_ROOT`) and forensic observability blobs (kept compressed indefinitely, never deleted or counted).
- Review continuations are recovery state, not disposable GC: archive a record (collision-safe move, never delete) only when its owner task is settled, it stayed un-resumed past `task_continuation.RETIRE_SETTLED_CONTINUATION_AFTER_DAYS` and no recorded obligation is open; any uncertainty or move error leaves the live record intact.

Enforcement: `tests/test_phase3c_observability_gc.py` (knob and cutoff math), `tests/test_observability_retention.py` (preserve indefinitely); the continuation archive rule is review-only.

### Live subagents

Mechanism (registry, scheduling, bootstrap, zero-run receipts, custody, work orders, supervision, recovery, patch integration) is ARCHITECTURE §6 "Delegated subagents (Claudexor transport + the nanny)" and the module docstrings it names. Review gate: CHECKLISTS items 17 (`subagent_isolation`) and 20 (`delegated_transport`). The imperatives:

- `schedule_subagent` alone schedules: schema and handler keywords derive from `control.schedule_subagent_properties()` to prevent drift. Child needs use the closed capability enum, never contract fields or prose. `subagent_id` selects a complete `OUROBOROS_SUBAGENTS` row admitted by both enabled axes; capture it at scheduling and dispatch from that snapshot. No second selector, host ranking or substitute after refusal. At-least-once delivery makes an exact task id with live/durable custody an idempotent no-op.
- The parent-LLM substrate choice binds; topology and supervision remain model judgment (P5/P13). Bootstrap never waits/polls: model-chosen `delegate_wait` keeps owner messages, hurry, checkpoints and parallel children live. Add to `subagent_bootstrap._DEFINITE_UNRUN_REASONS` only proof that no run exists; ambiguity wakes the model. Zero-run receipts are `incomplete | unknown`; substrate swaps stay disclosed incomplete execution, never silent fallback.
- Work orders carry the full assignment and host authority, without size cutoffs, forced question/file transport or duplicated objectives; redacted reviews never replace original requirements. `delegate_start_instructions.access_instruction` states typed native access once; per-call access may only narrow it, never derive it from prose. `delegate_message` uses the operation catalog and route `liveInput`, not a harness name; its host-minted `message_id` is the Idempotency-Key, reused only after `delivery_unknown`, without retry/stall machinery.
- `subagents.route_health` is the route reader for every consumer; quota readers project one `ClaudexorGateway.quota_state()` envelope, and a fully-used ratio without a valid future reset neither refuses dispatch nor certifies quota, because final admission is the engine's. Lifecycle facts are visibility only: acceptance judges quality, never the route; an unreadable custody log reads `evidence_read_failed`, never proven-empty. The coordination poll is read-only of task state and writes nothing beyond the canonical usage-ledger reader's bounded maintenance; every ledger state, absence included, goes through that reader (`usage_attempts.lock` recovery: ARCHITECTURE §1 "Platform substrate"; pre-send policy: `_usage_wait.py`).
- `task_constraint` booleans parse strictly (`"false"` is false); deadlines only narrow, delegation budgets only reduce, and persisted depth facts are never recomputed from current Settings. `active_tool_profile` fails closed to read-only, never to `self_modification`/`operator_control`; an explicit read-only assignment stays read-only. Only `schedule_subagent` creates subagents (`delegation_role=subagent` is refused at the gateway task route and the CLI); live `memory_mode=shared` stays disabled. The Cyber acting-tool catalog and the subagent browser boundary: CHECKLISTS item 17 and ARCHITECTURE §6 "Tool capability and execution".
- Acting children return `workspace.patch`; only the parent commits the live body, through `integrate_subagent_patch` then its own `commit_reviewed`; a capture base proves no authorship (use `vcs_diff`). One pure reducer owns canonical/replica terminal fields; changes need stale-replica tests at both seams. A custody row carries its owner's kind and every sweep, audit and counter states which kinds it covers: a review-owned run (`RunCustody.review_owned`) belongs to its panel, never to the task's open delegation, so a task that finishes under a running panel keeps its reviewer alive. The delegated Git/payload lane edits a private snapshot and reaches a tree only through `integrate_delegated_patch`; `delegate_shared.orphan_apply_target_ok` is the one predicate for the apply gate, the health invariant and the tool description; keep snapshot preparation's tree walks and per-file git work outside the worktree ops lock.
- `continue_from` enforces the four floors of `delegate_continuation` (own task line through recorded relations, settled, no pending-ambiguous apply, access not wider); same-tree custody also refuses `continuation_snapshot_missing`, `continuation_snapshot_released` or `continuation_handover_busy`, and an engine lacking `continueFrom` refuses `continuation_engine_unsupported`. Other facts are advice in the child's prompt, never gates or `instructions`.
- Outcome honesty: a delegating parent never produces a clean no-tool final answer while direct children run undecided; reminder counts never terminate the task. `wait_tasks` stays batch-compact; `control_task_results._wait_for_tasks` owns its projection, documented under ARCHITECTURE's "Waiting on children"; `get_task_result` explicitly reads full terminals; every wait handoff is bounded and source-linked. Push/live events are wakeups, not terminal authority: a lifecycle change exercises lost/reordered terminal frames.
- Ordinary-directory sessions use the engine-owned file work product: keep the parent-selected direct/copy strategy, never initialize Git or change run mode as a workaround, carry full file artifacts beside source patches (deletion included: an empty text diff cannot certify no work), apply through the engine CAS, retain unselected results, and never relabel direct effects or a discard as an undo.

- Vendor maintenance shares engine-owned capability/request identity across UI and tools, never a harness-specific installer or task replay (ARCHITECTURE §6 Vendor program maintenance). Preserve selected/baseline, rejoin and partial/cancel facts; verify both authority directions and desktop/mobile rejoin (`test_harness_maintenance_host`, `test_harness_maintenance_transport`, `test_harness_maintenance_browser`).

Enforcement: `tests/test_acting_subagents.py` (profiles and creation), `tests/test_delegate_continuation.py` (`continue_from`), `tests/test_custody_owner_kinds.py`, `tests/test_delegated_directory.py`; `tests/test_tool_api_v2_public_surface.py` pins the schema/handler derivation.

### Cancellation and effective status

Mechanism: ARCHITECTURE §5 "Supervisor Loop" (`supervisor/queue_transitions.py`, `supervisor/cancel_publication.py`, `supervisor/owner_stop.py`); invariants: ARCHITECTURE §10 "Key Invariants" 14 and 15. The imperatives:

- Effective task status belongs in `ouroboros/task_status.py`; never duplicate child-drive merge or terminality logic in gateways or tools. Waits use `SETTLED_STATUSES` and structured facts plus queue-heartbeat freshness, never keyword matching.
- Waits use the shared mailbox-attention predicate: owner/control, typed attention and explicitly selected senders wake; routine task mail stays unread. Early returns ACK nothing; the resumed round drains originals, then the saved working checkpoint permits ACK. A failed or torn read never proves an empty mailbox.
- Terminal quiz reconciliation closes the paired wait even when the answer arrived before worker capacity. A failed loop without captured evidence reports unknown counts, never zero work or an unverified checkpoint.
- `task_status.observe_cancellation_target` precedes intent writes and reports physical target, result/queue freshness and delegated custody separately. Caller reason and request origin differ: HTTP ingress proves no personal owner intent. Preserve `cancel_origin` through publication, history, cards and conditional result reads; unknown actors stay unknown; keep the whole reason and label a shortened presentation as preview. Unconfirmed terminal sends are disclosed as "not confirmed" with saved copies named as copies; only a same-delivery receipt for the recorded destination retires the notice.
- Cancel intent is never a status value: every cancel ingress writes a durable intent through `ouroboros/cancel_intents.request_cancel`, fails closed when that write fails, checks live physical ownership (a settled result does not mean a dead worker) and keeps the recorded scope widen-only. Natural completion wins a late cancel (discarding is the parent's separate `discard_child_result`); timeout reaping is not a cancel ingress. The intent and delivery registries read strict to rows and `task_done` validates through the durable result unconditionally; only `interrupted` keeps its restore-path exemption.
- `stop_policy` is an axis on the durable intent; the owner hurry control is a typed task-local owner-mailbox control, never a chat message, settings mutation or review-gate weakening. Every same-id requeue producer calls the one shared `owner_hurry.retry_reset`; the hurry projection writes only via `update_json_locked` on `owner_hurry` keys, never `write_task_result`; UI surfaces share `web/modules/task_control_menu.js`; terminal rows win.
- Keep agent in-band cancel and the periodic cancel/delivery/ref sweep off supervisor drain; reuse durable intent claims and generation checks (local in-flight keys only deduplicate dispatch), and queue no unrelated Stop work behind a new general-purpose file executor.

Enforcement: `tests/test_cancel_intents_phase_a.py`, `tests/test_cancel_cascade_v664.py`, `tests/test_cancel_origin.py`.

### Onboarding and Settings surfaces

ARCHITECTURE §2 owns wizard steps, completion and install-time proofs; §3 owns Settings, accounts and shared controls. Copy and wizard shape are review-only. The imperatives:

- Current tasks read the task-entry settings view: a next-task save never changes an overlapping direct actor's Supervisor, Review, model or key; owner writers and grant classification read current disk state. Cyber selects context, review scope/enforcement, models and Supervisor configuration through the existing settings writer under effective Access; permission is not a review verdict.
- One wizard host, the served `GET /onboarding` page, serves subscriptions, API keys and mixed installs; its frame keeps the `allow-popups allow-popups-to-escape-sandbox` sandbox tokens, without which the sign-in click is blocked silently. Completion is one transaction, `GET /api/onboarding` never persists, and the client treats only the exact success envelope (`ok`/`runtime_mode`/`restart_required`) as completion, because a silent success discards the restart receipt. Only declared raw-model sources supply Main, never agent-only connections; "Without an API key" never means free (ARCHITECTURE §2).
- Settings validates the complete draft before any Save: never drop an invalid custom-key row and save the remainder; a failed save/refresh preserves edits; leaving a dirty draft asks first. Saved intent, generated drafts and live status are different axes: a status/catalog failure annotates a loaded row and never erases it; only explicit Save or onboarding completion materializes a GET-returned candidate; a late preview never absorbs owner edits.
- Model-role and actor/reviewer adapters use `model_chooser.js`, which owns suggestions/keyboard/position only, never route identity or entitlement. Models, actors and reviewers share source/model/account controls: exact pins survive save/reload and catalog failure; a source's credential harness comes from its metadata, never an assumed equal name; delivery follows the row's surface and reference, not its model or account: a session row retrieves, an API row keeps its saved `delivery` (native by default, `review_native_episode.py`), and model/account edits never silently turn it into a packet.
- One capability, one section: the task-actor story lives in Agents → Available subagents (`web/modules/subagents_settings.js`), editing one canonical `OUROBOROS_SUBAGENTS` object of at most `MAX_CONFIGURED_SUBAGENTS` rows. The review pool is the same list: the Reviewer mark (`review_eligible`) and an API row's `delivery` are row fields, never a second editor; `GET /api/review-pool` is the read side. Name a row by its route-derived handle, never a stored label or ordinal; never render a second control over the same settings key (`OUROBOROS_MAX_WORKERS` stays in Advanced). Routes serialize `api_model` + `credential_profile_id` through the neutral primitives (`route_editor_primitives.js`); an empty managed pin means engine rotation; saved-but-undiscovered choices stay visible and editable; a compound effort slug plus a conflicting separate effort is a validation error. Owner switches expose the semantic choices: `OUROBOROS_ALLOW_MUTATIVE_SUBAGENTS` presents Off / Auto / On, Auto being the unset default saved as the empty value (`config.get_allow_mutative_subagents`).
- Install-time defaults compile from live discovery with typed refusals: never guessed, half-applied, re-derived after onboarding or decided on a moment-in-time reading. Compilation stays linear and split by semantic owner (`ouroboros/subscription_install_presets.py`); API-only/local-only compilation performs zero Claudexor reads; `POST /api/onboarding/subagents/preview` is the read-only compiler surface. Agent sign-in consumes the harness row's `setupLogin` as four states (absent, null, a valid object selecting `in_app` or `external_terminal`, malformed data as a gap), never a harness-name branch; external-terminal commands use `claudexor_daemon.py`. Additive response fields are mirrored in Python TypedDicts and `web/modules/api_types.js` together.

### LLM call rules

Call-site rules and what enforces each. Mechanism is ARCHITECTURE's and is pointed to, not restated: the subscription transport (§6 "Caller-owned subscription model calls"), accounting (§6 "Budget tracking", "Usage ledger substrate vs. accounting policy"), route contracts (§6 "Context fitting, retry, and compaction"; DEVELOPMENT §2 "Provider Independence").

#### Subscription transport

- Claudexor preserves model content and native continuation bytes: no credential injection, tools, adapter compaction or silent regeneration. A lost control reply rejoins the same operation ID, and an unknown outcome stays unknown, because a second generation can double-charge. Only the engine classifies model substitution — no host model-string matching — and a local rejection never rotates accounts. A complete but unusable terminal settles as `stream_rejected`, never as unknown or not-dispatched, across sync, async and process boundaries.
- Caller hints name capabilities; an explicitly unsupported option refuses. Record the submitted options and the provider's `appliedOptions` echo; an absent key stays unknown. Effort appears in usage, events and Logs, never as automatic chat, toast, incident or a mismatch gate.
- `effort_evidence.py` validates the model's `effortResolution` (stored as `effort_resolution`); the Claudexor gateway (`gateways/claudexor.py`) reads the unique final session telemetry attempt. A null `submitted` means omitted, not `none`; keep engine-native effort tokens in engine order, never re-ranked by host preference.
- The engine's active-turn token is transport, owned by the caller's `llm_claudexor.ModelTurnState` slot; only the engine boundary writes it. Never derive it from messages (BIBLE P5), copy it on reprepare or offload, checkpoint it, or publish it in usage, events or cards. Opt in by the last successful handshake version, never a next-spawn pin or a failed probe (ARCHITECTURE §6 "The live turn slot"; `llm_claudexor.py` docstring).
- Pass `model_role` and the captured account at every helper and reviewer seam: shared model names share no pins, and account evidence stays source/profile/fingerprint-bound. Manual context sizing grants no scope authority; ACK binds the actual route; density evidence never crosses models.
- A resource refusal tries configured routes first, never sleeps to a reset, and waits inside the live call on the existing task owner, mailbox, clocks and settings writer; a reviewer call waits in its panel's operation wait. Reprepare wake input from canonical messages against the new route's tools, capacity and image policy. No parked rounds, compensation processes or replay of completed tools and reviews (ARCHITECTURE §6 "Quota and auth waits").

On the OpenAI family and the Claudexor route the leading system message's declared mutable blocks also travel as one such notice before the first user turn, so the marker has these two meanings (ARCHITECTURE §6 "Prompt caching").

Per-family session identity and the message-side seal: ARCHITECTURE §6 "Prompt caching"; Claudexor's shared `cache_key_for_model`: §6 "Caller-owned subscription model calls". A model handover keeps the finalization checks (ARCHITECTURE §6 "Task lifecycle"; `tests/test_authoring_handover_loop.py`).

A Skill Review usage row carries its exact wave/slot identity, never reconstructed by time or model (`tests/test_skill_review_usage_accounting.py`).

#### Timeout & Wait Control

- A required owner wait keeps the original execution RUNNING: the worker lends only active capacity, and waiting exempts only the idle timeout — Stop, deadline, absolute ceiling and monetary admission still bind. A wait is dated by its own `parked_at`, never by the task start; a warm wake changes no attempt, start time, completed effect or usage; cold recovery needs the acknowledged planned-restart handoff, and a direct-actor checkpoint alone grants none (ARCHITECTURE §5 "Supervisor Loop"). Enforced by `tests/test_owner_wait_pool.py` and its `test_owner_wait_*` siblings.
- Default child waits park warm; any unminted ID returns a repair snapshot, not a slot hold. All wait handoffs are bounded and source-linked; `get_task_result` explicitly reads full terminals. Nanny `delegate_wait` renews transport windows without LLM calls; only terminal/interaction/fault, typed attention, owner/control input or a one-shot checkpoint wakes it. No caller `wait_sec`, repeating/progress wakes or semantic stall detector (BIBLE P5).
- Wake facts are measured over the interval the actor experienced (whole-call `sleep` stamped at the one publication point, never a tick's `waited_sec`); the acked child cursor is task-scoped.
- Wait/continue/stop is a structured fact — terminal status plus heartbeat freshness from `queue_snapshot.json` via `task_status.py` — never a keyword or regex over content (BIBLE P5). Fixed kill-timeouts (hard task/tool ceilings, watchdog) stay the outer safety bound; progress-aware waiting tunes only the passive wait.
- Raw terminal model or salvage bytes stay separate from the host-authored `terminal_provider_notice`; a renderer never changes raw answer bytes, and a retained answer must not hide wait or unknown-attempt evidence or invite a blind rerun. Owner Wrap up is distinct from deadline/budget finalization and sends no new summary request (ARCHITECTURE §6 "Task lifecycle").
- Transport-wait notes use the progress seam with `incident=None`; never infer urgency or valence from a task's prose; the frozen `ToolContext.emit_progress_fn` takes one argument, never an incident pair (`tests/test_loop_transport_wait_interactive.py`).
- Timeout classes are separate axes. The transport timeout (`OUROBOROS_LLM_TRANSPORT_READ_TIMEOUT_SEC`) bounds only a dead socket — never a reasoning cutoff or evidence of a stall; a delegated agent session inherits the task operation window because the paid run can outlive an HTTP read; the owner deadline narrows every window; provider transport defaults are ceilings, not promises. Pool seats have no short cognition cap; `plan_task` and `web_search` size their outer envelopes for the whole session or the complete paid cascade (ARCHITECTURE §6 "Context fitting, retry, and compaction").
- An env-tunable timeout is a `SETTINGS_DEFAULTS` key in `settings_defaults.py` plus a clamped getter in `runtime_limits.py`; a fixed structural bound (`WORKER_READY_*`, `EXTERNAL_PLATFORM_UPDATE_TIMEOUT_SEC`) lives in `runtime_limits.py` alone. Both are re-exported through `ouroboros.config`, the sole import surface; register each env key; no call-site magic waits. The clamped getters are pinned by `tests/test_timeout_policy.py`; the placement rule is review-only.
- Worker readiness, process liveness and idle deadlines stay independent: a child's own `worker_starting` row permits one readiness extension to `WORKER_READY_CEILING_SEC` from birth, never a sliding deadline; a failed terminal-file write keeps terminalization retry, never a false Done or a fresh startup budget (ARCHITECTURE §5 "Supervisor Loop").
- Order wrapper bounds provider, then killable child, then ToolEntry, using config's settlement margin. The test budget belongs to `commit_reviewed`; standalone `preflight_review` runs no tests and shares the `review_change` ToolEntry envelope (task/transport settlement plus finalization grace). The plan/acceptance `ReviewRequest.drain_deadline` barrier may return early but retains worker custody; collection carries the reviewers' own verdicts through the existing mailbox (`plan_review_collect`, `acceptance_settlement.announce_acceptance_settlement`, host-only `review_dispatch.reconcile_pending_acceptance_runs`), never an instruction to collect, and neither path buys another panel.
- Every physical LLM, review, VLM or tool operation that can outlive a logical wait emits typed `cognitive_operation` start/terminal facts matched on task-attempt plus execution/round/call identity; the supervisor uses them only to spare the idle rail. A logical timeout over a live paid worker is custody/reconciliation-pending, never a blind paid retry; a late result settles the original attempt. An owner terminal that is not a deliberate verdict is no permission to cancel the paid run it held.
- A refusal that spent nothing is a typed `$0 not_dispatched` row with its cause, never a verdict or a synthetic actor: a review row unstarted once the owner deadline minus finalization reserve is spent, a `pending_dispatch` row released at the barrier, a zero-physical acceptance refusal (which folds the aggregate to `DEGRADED`). An in-flight reviewer never counts as final quorum under either enforcement mode (ARCHITECTURE §6 "Review stack"; "Task acceptance").
- A returned provider response (empty body included) or a typed terminal 408/429/5xx is settled and may use the surface's bounded retry rail; `dispatched`/`unresolved` without a typed terminal stays custody-lost/no-resend. A new logical request needs a unique host-attested input the unknown one lacked: the managed upstream-recovery notice or the nanny-leaf wake in `ouroboros/delegate_hold.py`. A custody retry key names semantic material and an admitted cycle, never its rendered prompt; an unstarted chunk cannot authorize PASS (ARCHITECTURE §6 "Physical custody"; "Late completion and typed refusals").
- A reviewed mutative wrapper keeps foreground custody until the workflow settles; never abandon a live reviewer or commit pipeline on the generic `OUROBOROS_TOOL_TIMEOUT_SEC` default or a guessed ceiling.
- Cooperative cancellation exists only where the route supports it (delegated sessions); API/thread routes disclose an in-flight custody state until the result settles. Once a delegated run has an id, a typed transport failure is unknown: replay that run through its durable invocation token on the permitted retry, never post a second paid run; a token without a valid durable invocation is `review_custody_lost`; elapsed TTL never authorizes a resend, and owner death is proven only by pid death (ARCHITECTURE §6 "Paid stamp and owner custody").

### Loop and acceptance state machines

The loop, delivery, acceptance and plan-review state machines live in `loop.py`, `loop_delivery.py`, `loop_acceptance.py` and `tools/plan_spec.py`; their mechanism is ARCHITECTURE §6 "Task lifecycle", "Task acceptance" and "Plan construction and review". Below: the invariants a change must keep and the failure paths it must test.

#### Loop / State-Machine Changes

- Changes to `loop.py` or other task state-machine logic include failure-path tests — malformed output, false-completion prevention, replay/log durability, failure modes — not just the happy path. Audit/checkpoint rounds never silently reuse the normal final-answer path unless that invariant is explicitly tested and documented.
- Keep a complete loop-local `DeliveryCandidate` (`ouroboros/loop_delivery.py`); sticky host-control provenance survives replacement. Forced resolution is pure, with no retry: the same action/answer/hash request selects complete bytes; malformed or historical controls stay private and retain the candidate. Controls never bypass verification, acceptance, safety, skill finalization, deadline, child handoff, the unconditional `FINAL ANSWER:` latch or the task-level answer protocol. Host notices stay outside answer bytes and identity; an unchanged answer never revives a superseded verdict (ARCHITECTURE §6 "Task lifecycle").
- Plan review verdict: GREEN means a quorum answered and no blocking finding or undispositioned `need_evidence` remains; notes never change it. `plan_spec.closure_after_disposition` is the one closure table; a closed REVIEW_REQUIRED is written as GREEN with a closure note on every write path, and the control validators keep accepting older closed rows. An author-selected revised plan publishes the critic wave's real pair labelled `historical_critic`, never an invented verdict. An envelope `reviewer_effort` orders plan review only, under `row_effort`'s rule (Auto rows clamped, pins kept outside Cyber Pro). Pass it through `plan_review_slots`, never a contextvar (`review_change`'s composed panel is the one disclosed contextvar seam: ARCHITECTURE §6 "Change review on any root"). Enforced by `tests/test_plan_spec.py` and `tests/test_plan_review_engine_quorum.py`; mechanism: ARCHITECTURE §6 "Plan construction and review".
- Keep delivered result, unresolved tool-call evidence and host acceptance separate: error count alone neither degrades execution nor establishes objective acceptance. Retain `execution.unresolved_tool_errors` and the cosmetic bucket, expose the existing no-review warning when the canonical objective is `not_evaluated`, and test every verdict and the no-review case (`tests/test_outcome_tool_error_axes.py`).
- Every direct child result needs an exact-hash disposition through the existing `tree_note(kind="decision")` payload (`type=child_result_disposition`). The typed task-tree row is the sole authority; task-result disposition fields are derived reads, never a mirrored write. The SHA-256 binding means a parent cannot claim it integrated a result that later changed; `deferred` suppresses only the reminder and forces an honest degraded/best-effort terminal until resolved; the payload schema is the SSOT for the value. A child whose `cancel_requested` latch file is set carries intent, not outcome: cancel stays pending until custody settles it (`tests/test_child_result_disposition.py`).
- Host acceptance is root-only: structured `outcomes.turn_has_reviewable_effects` plus a typed deliverable or criterion, never keywords or agent authority (BIBLE P3/P5). Waiting, fences, `previous_revision_accepted` and `late_settlement` are ARCHITECTURE §6 "Task acceptance". Workers never author Main's candidate or decision, or make reviewers open delegations; subtree, status, findings and Cyber authority stay distinct (BIBLE P0). Enforced by `tests/test_review_operation_source_closure.py` and `tests/test_review_operation_collection.py`.
- One completion request serves native tools, explicit review actions, Presence and pure forced extraction; retention leaves tools available. Changed criteria or material evidence make a new subject even with kept text, never old verdict authority. File/diff requests impose no commit-or-revert rule; self-modification keeps reviewed commits (BIBLE P0/P3).
- Freeze `review_evidence.task_inputs` and `completion_observations` before cleanup (ARCHITECTURE §6 "Post-task reflection"): origin, the whole owner Q/A, peer provenance and canonical split-root verification receipts. Keep first/latest usable author inputs as a separate `historical_author_inputs` sibling, never directives or criteria. Reuse selected observations, with no live-source reconstruction, excluded-input exposure claim or failed-response anchor; prove evaluator source reads and retention after cleanup (`tests/test_historical_inputs.py`, `tests/test_historical_input_consumers.py`). Zero exit is positive, absence unknown; unrelated passes erase no failure. `OWNER_DELIVERY_TOOL_NAMES` counts sends, never global skill state. Transport receipts stay out of that snapshot: only a newly written reflection reads them, once after admission (`presence_delivery.task_delivery_receipts`), with a captured window, named gaps and a non-exhaustive disclosure; no fold, wait or store (`tests/test_reflection_delivery_receipts.py`). Plan-review facts reach the reflection as one bounded slice with a source pointer (`plan_review_facts.py`), never a score; a panel that settles after the task ended appends one bounded row through `append_reflection_routed`.
- Lifecycle identity fields (host-minted root id and role, `started_at` from the actual `_task_started_ts`, existing `queued_at`, call/execution/round ids, root/parent ids on delegated rows) are observation links, never new accounting or zero-price rules; a missing historical start fact stays missing.
- Hash identity before history budgeting; recording changes no reviewed fact. Retain full review runs before compact publication; copy and hash before the short artifact lock and never take a result lock inside it; context checkpoints are neither deliverables nor acceptance manifests; a repeated edge cannot turn a deduplicated failure into success (ARCHITECTURE §10).
- Mirror an actual split-root or split-subagent start, attempt and binding into the canonical result through its terminal-preserving writer; a start written without the named attempt stays unknown, never permission to resume. `headless.prepare_terminal_task_files` adopts answer, output files and receipt union after blocking post-work and before worker `task_done`; an I/O failure or a lost event never authorizes model replay. Health owns file recovery, the existing reaper owns execution and deferred-job replay, and the normal terminal event owns queue release and project/evolution hooks — never a second crash executor (ARCHITECTURE §5 "Supervisor Loop").

Reuse the existing subject and paid-identity owners — no second hash, no cosmetic edits. Task-acceptance actors are the review pool's rows (`reviewer_slot_config.review_pool_slots`; a malformed catalog refuses typed); format-repair resends are packet-row only; child and `off`-mode acceptance preserve delivery, a child selecting at most one configured row.

A new writer adds its reason to the set and checks every value-keyed reader — `outcomes.derive_loop_outcome` keys on status+reason pairs, and a broken pairing is a silent false green. Every forced rail closes a dangling `revision_requested` via `loop_acceptance.terminalize_dangling_revision`. `PASS|FAIL|DEGRADED` is not narrowable; `adaptive_quorum` applies, any contributing FAIL fails and DEGRADED abstains in the critic aggregate. Apply qualified Advisory author completion separately, never rewriting criticism or hiding independent failed effects, unaccepted review or unfinished stops (DEVELOPMENT §5; ARCHITECTURE §6 "Task acceptance"). No coupling question or commit-gate reuse.
- Plan-review answers are durable statements merged by `finding_id`: a later answer supersedes only its own id, and two entries for one id in one call stay contradictory and open. The unchanged envelope asks only the named slots and replays every other slot's recorded row at $0 (`not_dispatched` + `replayed_from`, never a send); an addressed slot without a parseable answer keeps its findings; a quiz answer never closes a finding; no host path buys a panel the mind did not send (`tests/test_plan_review_answer_channel.py`).
- Keep reviewer dialogue evidence: typed `disposition_kind`/`obligation_id` identify obligations; an unknown re-raise id is disclosed as `new`; a reopened row keeps its arguments. A terminal critic vote cannot deny author reaction or choose its stop; Blocking may save corrections and stop, but advancement needs fresh reviewer authority; Advisory may explicitly finish after exposed feedback or disclosed unavailability without another panel. Queueing is not exposure; a predeclared finish cannot authorize unseen feedback; `author_action=stop` grants neither completion nor permission. No semantic counters or keyword gates (BIBLE P5). Test malformed output, unknown/stale ids, partial failures, disagreement, obligation replay/restart, false completion and missing fields.

Otherwise `OUROBOROS_REVIEW_MAX_CYCLES` limits paid panels, not author responses: the last feedback permits work within ordinary task time, budget, cancel and round rails, and the reviewer admission floor applies only to new critics. Settings load migrates the alias `OUROBOROS_ACCEPTANCE_MAX_IMPROVEMENT_PASSES` into it; the alias never binds at runtime.

A terminal custody obligation is disclosed additively (objective warning plus reason code); turning a custody fact into a review, objective or execution verdict is the defect this rule prevents.

### Android platform development

Android keeps the common source, update and review authority. Its runtime layout, launcher/seed distinction, native artifact receipt and lifecycle owners are ARCHITECTURE §1 "Android host (experimental)"; the user procedure is `docs/ANDROID_INSTALL.md`; the CI lanes are ARCHITECTURE §8. Rules:

- Describe experiments as rooted ARM64 Android, physically tested on Pixel 10a only. Do not turn that tested model into a runtime allowlist or treat the manifest's minimum SDK as a proven support matrix.
- Native changes use ordinary Android source, reviewed commits and the persistent per-install signing identity. Never copy the publisher private key, runtime credentials, memory or a live rootfs into release assets. Verify official bytes before trusting their source, and record a publisher-signed reference APK and the locally built installed APK as distinct artifacts. Restore the original personal key after loss; never silently generate another identity for an installed package.
- Dependency changes reach the same source-selected `ensure_platform` hook that serves first installation and later updates, with tracked recipes and patches; a group stays `platform_preparing` until completion so an interruption or a Git rollback cannot reuse a partially changed SDK as current. Use the existing verified download cache, Node manager and Playwright installer; start no second daemon. Preparation completion is not HTTP or native-success evidence, and the contained preparation's `EXTERNAL_PLATFORM_UPDATE_TIMEOUT_SEC` bound is neither an environment setting nor a harness deadline.
- Before claiming native adoption, exercise source → dependency preparation → build → install → readback → restart, and cover a failed native build beside a still-usable core, an older immutable seed with newer source, a local APK modification followed by an upstream source merge, bootstrap-only changes, rollback to older native source with a newer versionCode, bridge loss and recovery, and Panic versus automatic entry. Core HTTP health is separate from native artifact and bridge readiness; checks use their existing owners and preserve incomplete outcomes.
- Delegated access keeps the common actor/delegation owners (ARCHITECTURE §6 "Delegated subagents (Claudexor transport + the nanny)"); Android acquires no second access default, trust policy or retry implementation, and a sandbox failure is not a successful run or permission to disguise a retry.
- `enter-linux` sets this entry's defaults for the existing `OUROBOROS_PREFLIGHT_TEST_WORKERS` and `OUROBOROS_PREFLIGHT_TIMEOUT_SEC` levers and preserves explicit overrides; they change test concurrency and time, not test content, review models or context. Measure memory and swap and confirm process cleanup before running full preflight on a phone; do not deliberately reproduce a kernel panic; keep reusable large downloads in the installer's durable cache.
- `android-test` explicitly collects `android/tests`; ordinary `pytest tests/` does not cover that directory. Portable fixtures and host compilation are separate from physical root, boot, permissions, hardware and battery evidence, and the emulator job certifies neither the phone bootstrap nor the owner consent UI. Release SBOMs describe shipped source/APK bytes; installed pins describe the provisioned phone; neither invents the other. Only the tag-only `android-build` job reads the publisher signing secrets (`ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`); branch and PR Android jobs sign with a disposable key they never publish, so a PR is source/build evidence, not a publisher-signed release claim.
