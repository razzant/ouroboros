# Gateway Boundary Pattern

This chapter owns the direction of dependency at the browser boundary: inbound routes enter through `ouroboros/gateway/`, outbound provider and harness adapters live in `ouroboros/gateways/` and carry no domain policy, and the frontend calls the one typed client (why the facade exists: ARCHITECTURE §1 "Gateway Boundary v1").

Browser-facing backend work enters through `ouroboros/gateway/` and frontend calls go through `web/modules/api_client.js`; the endpoint index is `ouroboros/gateway/endpoint_index.py`, re-exported by `contracts.py`. Outbound adapters belong in `ouroboros/gateways/`: do not copy policy into an adapter, do not promote the `gateway/host_service.py` callback surface into a general owner/task API, and do not require a class where established function owners already preserve the boundary. Enforcement: CHECKLISTS item 27 (`gateway_parity`) and `tests/test_gateway_parity.py`.

Named skill chat ingress writes through the message-bus canonical writer before enqueue and correlates reads and cancel by `operation_ref` (custody, replay and the 409 rules: ARCHITECTURE "12. Host Service, Companion Processes, and Chat IDs"). A cancel or intent write addresses the same installation root as the operation being read, and operation reads and cancel verify the complete source against actual task or direct-turn ownership; presentation annotations are discovery hints only. Tests: `tests/test_host_service_operation_identity.py`, `tests/test_host_service_operations.py`.
