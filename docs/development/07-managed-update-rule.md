# Managed Update Rule

Managed updates rewrite the live tree under owner authority alongside other work. Each step needs custody: targets, writer admission, local work, resolver authority and recovery.

- Separate the local work branch and official feed: ARCHITECTURE §8 (`ouroboros/update_channels.py`).
- Preflight selects one exact target. Apply binds base/target, closes new writers, drains direct turns, stops workers/services and re-plans before mutation. Write the transaction first; reopen only after verified abort/rollback or healthy restart. Evolution cleanup shares that lock/admission.
- Conversation and repo-writing differ. Destructive apply/replace/rollback/materialization refuses turns; while the authorized assisted resolver owns `assisted_resolution`/`committing_assisted`, Main answers but other tasks’ repo tools remain refused. Steering uses `steer_task`; admission: `worker_chat_lane.conversation_admitted_during_update`. `preload_owner_control_path` imports server packages before conflict markers enter the materialized checkout.
- Keep dirty work out of merge history: stash, then restore uncommitted. Never automatically drop update stashes, even after success. `rescue-local-*` pins the exact object; explicit Git cleanup is available. Only a real Git conflict invokes the reviewed resolver; filenames create no policy. Internal materialization/rollback reset without interactive confirmation; the generic owner-facing Restore retains its confirmation.
- Record restoration intent in the existing transaction BEFORE apply. Every completion consumes restored/preserved/incomplete; failed persistence retains the marker. Interrupted replay neither resets nor reapplies over returned or later work: once storage works, record a handoff of the saved backup, preserving current files without claiming clean/successful apply. Failure captures rc/stdout/stderr and NUL-separated unmerged paths before verified cleanup; release carries one recovery note to Main/Updates and supervisor events. Unreadable census differs from empty; neither counts successful files or enumerates untracked collisions.
- Schema 1 is the default; stash restoration and rollback carrying stashed work require schema 2 before checking out old code. Older strict readers refuse an interrupted new state without reset; recovery needs a capable reader or deliberate action. Completed rollback retains schema-1 `marker_cleanup_retry` through one re-exec: bootstrap preserves current files, then old/new finalizers only clear the marker. `stash_restored` still means recorded successful apply, never intent. Restart the actual desktop app, Docker/service or direct server, not its browser tab. In-app Restart refuses pending restoration before checkout/reset.
- The resolver stages the full merge, tracked binaries included; review gets exact staged mode/blob/size and parent object IDs. Missing metadata blocks; ordinary commit binary policy is unchanged.
- Managed merge commits require a green full suite on the exact candidate (DEVELOPMENT “The commit gate mirrors the CI split”). Any non-commit resolver terminal rolls back and best-effort preserves the attempt on its deterministic failed-update branch. Recovery needs the fresh rescue, not that branch.
- Fresh rescue precedes every destructive rollback and boot re-materialization. Capture failure is fail-open but durably disclosed, with a transaction pointer; ARCHITECTURE §2 owns the choke point and need for fresh rescue.
- Manual Restore fences writers and pins HEAD before reset. Promotion resolves one development SHA for local QA and remote push.

Tests: `tests/test_update_merge_policy.py`, `test_update_dirty_stash.py`, `test_update_stash_recovery.py` (real Git, crash/replay, consumers, Restart), `test_update_hardening.py`, `test_update_tx_corrupt_quarantine.py`.

Native hosts add no source updater: the launcher hook verifies its installed artifact before core start; post-boot readback precedes finalization. Failure uses rollback; worker self-restart retains incomplete native adoption despite matching core SHA.
