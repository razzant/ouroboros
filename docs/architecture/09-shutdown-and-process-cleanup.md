# 9. Shutdown & Process Cleanup

This chapter separates window close (preserving the shared daemon), manual Restart (stopping generation-owned work before re-exec), and Panic (complete explicit stop). Their signal, unconfirmed-outcome and next-boot reconciliation contracts differ: confusing them can kill another client's paid run or falsely report its death.

On Windows, automatic sign-in starts hidden; if its icon fails, GUI startup shows the window (or exits after failed display), and pump death restores it. X hides only with a live icon; tray Open or a second launch restores the window. The lock loser signals a named auto-reset kernel event tied to the installation's PID-lock path, not a durable file; if the owner has not published that event within the bounded retry, the old already-running notice remains. Tray Exit attempts synchronous icon disposal on its STA thread before ordinary launcher shutdown (a disposal failure is logged, not treated as proof); Panic requests disposal before orphan cleanup, but does not wait for the STA pump before `os._exit`; an unresponsive pump can leave icon removal unconfirmed rather than delay emergency stop. Pump failure restores a hidden window and leaves ordinary X-close available. macOS/Linux retain normal close.

Ordinary window close preserves this installation's shared Claudexor daemon and work submitted by other clients, on graceful and forced launcher cleanup paths alike. It stops the server generation's workers and services, waits for its process group or Job, performs owned cleanup and releases the PID lock; the Windows daemon lives outside the launcher Job, and an old immutable launcher needs a later package update for this guarantee. The graceful phase of `launcher.stop_agent` signals ONLY the server PID (`proc.terminate()`, on every platform) and waits `LAUNCHER_STOP_GRACE_SEC`; the group SIGKILL fallback after it and the post-exit group sweep remain. The server is the custody owner of its multiprocessing Manager and pooled workers, and a group-wide SIGTERM at t=0 killed them before the server's own teardown began (issue #1142: `BrokenPipe` on `EVENT_Q` and a false `supervisor_failure` alarm). The server half is self-sufficient against an old launcher that still SIGTERMs the group: `server_process._SignalStopServer.handle_exit` sets `_supervisor_stop` at the signal, so the loop leaves its tick and a torn-Manager error is never counted as a crash, and `uvicorn.Config(timeout_graceful_shutdown=SERVER_GRACEFUL_SHUTDOWN_TIMEOUT_SEC)` bounds the open HTTP/WS drain that otherwise parked the lifespan teardown past the launcher budget (the pair is one budget in `runtime_limits.py`). Two guards keep that ownership: the embedded Host Service server is built by `server_process._embedded_uvicorn_server`, whose instance-level `capture_signals` is a `nullcontext` — a uvicorn server serving on the main thread otherwise takes the process handlers and forwards a signal only after its own drain — and the never-cleared `_exit_signalled` latch refuses `_start_supervisor_if_needed`, ends a generation admitted a moment before the signal (`_supervisor_generation`, the thread body) and is read by the loop's own condition and crash branch, so a settings save landing mid-teardown cannot revive a generation behind `kill_workers` (§5 keeps `_supervisor_stop` revivable for crash revival and a fresh lifespan; `tests/test_shutdown_signal_1142.py` drives a real server through the old group SIGTERM with an in-flight request open). A same-pin planned restart retains the daemon; a planned restart after a changed engine pin stops it in lifespan teardown (`server_restart._stop_owned_daemon_for_new_pin`: the landed `load_runtime_pin` compared with the serving engine through attach-only `read_owned_gateway`, then the explicit stop below), and an unpublished or unreadable pin or an unreachable, foreign or stopped daemon leaves the handoff unchanged. An unconfirmed stop keeps custody and diagnostics and the restart proceeds; the next generation reconciles old runs without inventing spend. In lifespan teardown the ONE irreversible durable write goes first — the stop flag, the bounded supervisor join, then `kill_workers`, which terminalizes every interrupted task — ahead of the best-effort extension-reconcile and host-service waits and the kill-all sweeps, because that order keeps the write reachable inside the launcher's force-exit budget (an external SIGKILL can still cut it short, and the later bridge and event-bus teardown can lose a late frame). A stop that never reaches that write leaves it to the next generation's snapshot restore; queue init hands the direct-chat roster `state/direct_roots.json` to it in the step that clears it, so listed roots are fenced like any surviving RUNNING row and end Cancelled, not as infra-failed orphans. Ordinary server shutdown closes its own Host Service listener; reserved-port sweeps remain separate launcher/recovery/Panic behaviour: they are not PID-identity proof and can terminate an unrelated listener on a reserved port.

Manual Restart (`/restart`, the chat button) stops this generation's owned work, then re-execs. The bridge delegates to `server_restart._perform_owner_restart` (re-exported by `server`) with its transport notice callback. HTTP/WS Restart buttons use the direct owner until the supervisor is alive and ready. Typed WS chat first retains its canonical row/echo; Host Service retains correlation and checks the current owner pair. Ready dispatch keeps its envelope. Panic's early bypass stays separate. That common operation is checkout-first: `_safe_restart_serialized` (update lock, strict managed-update transaction gate, then `safe_restart`'s checkout, dependency sync, import test and stable fallback) runs before anything is stopped, so every refusal — an assisted-update merge mid-resolution, a failed checkout, an unwritable no-resume flag — leaves the server intact and is answered with one "Restart cancelled" line. Past that point the restart always follows: the durable no-resume intent (`state/owner_restart_no_resume.flag` plus the `panic_stop.flag` compatibility pair, consumed by `auto_resume_after_restart`), then `server_restart._stop_owned_work` — one immediate cancel intent per RUNNING task, live direct activity and in-flight post-task synthesis (`cancel_intents.request_cancel`, source `owner_restart`, full stated reason kept), `kill_workers` (a recorded `cancel_origin` kept by `_intent_outcome_fields`, none invented), delegated-run cancellation through the owner-gone seam `reconcile_orphaned_runs(running_task_ids=set())` over `read_owned_gateway`, and the attested owned-daemon `stop_outcome()` exactly as Panic makes it. Everything between the cancel intents and the daemon stop is attach-only: an `ensure_owned_gateway` there would start a dead daemon. Nothing is a veto or a deferral: an unconfirmed or raising worker shutdown leaves a critical log, an unconfirmed or raising daemon stop the `process_stop_unconfirmed` supervisor row; custody stays retained and the restart proceeds. At the next startup, owner restart is a no-resume cause (`delegate_recovery.NO_RESUME_CAUSES`), so nothing is adopted; the custody sweep reconciles every open delegated run as owner-gone (a run the stopped daemon took down answers absent → `close_absent_run`, no invented spend; a journal-recovered terminal settles; a pending invocation replays under its own key), and an in-flight owned model operation stays a `dispatched`/`unresolved` physical-attempt row that already counts as spend upper bound. After an unconfirmed stop the new generation attaches to the still-live daemon rather than spawning a second one, and the lifespan's one background `warm_owned_daemon()` (provisioned homes only) makes the first delegation after a Restart find the daemon serving. The explicit stop is installation-wide — manual Restart ends runs served by the owned daemon, another client's included — deliberately unlike ordinary window close; planned self-restart, managed-update handoff and Panic keep their separate contracts.

Panic requests owned stops before I/O or cleanup. The worker socket gives local owners 250 ms; its lifeline bounds the callback at 500 ms. The parent retains native Popen and requests worker kill after 750 ms, even on Darwin without a responsive lifeline, before settlement and server exit. Published separate-session children retain local ownership during that window; unpublished spawns, inaccessible owners and escaped/backend-only children remain unconfirmed. Delivery, signal request and proven death stay distinct. Attached Linux targets use their pidfd; Darwin watches cannot signal or authorize numeric PID/group guesses. Ordinary EOF/parent loss skips Panic callbacks. Settlement includes existing port sweeps; bounded flag/control writes follow. Queue/custody reconcile at boot. Live local WS/HTTP Panic reaches the existing emergency owner through `LocalChatBridge.panic` without waiting for supervisor intake or state/chat I/O. External Host Service ingress authenticates the skill, then matches a positively pinned immutable owner pair without a new state read; unknown or foreign identities never gain a binding there, and Reset invalidates the bridge generation before deletion. Boot/ticks/wakes respect the flag; boot consumes it only after disabled controls persist. OPEN: if that persistence fails, the retained flag also aborts reviews of owner work explicitly admitted later; its legacy bytes carry no generation and an old immutable launcher compares them exactly to `panic`, so they are neither ignored nor rewritten. After storage recovers, another explicit Restart consumes the flag once controls persist but revives no stopped review; no compatible typed generation fact exists yet.

`stop_outcome` returns `stopped`, `nothing_to_stop` or disclosed `unconfirmed`. With a valid owned marker and an authenticated same-home endpoint it first invokes the installed managed CLI `daemon stop --json` (read-only `resolve_cli_command(require_npm=False)`, reason in DEVELOPMENT's Process Custody Rule); it never ensures a runtime, wakes a daemon or probes accounts. Exit 0 plus the typed terminal CLI receipt is required — an RPC acknowledgement or a clean lease release does not prove the captured OS processes have exited — and a surviving authenticated endpoint is disclosed without chasing a successor. The pre-request custody snapshot limits forced fallback to those original rows, and forced signalling still requires both measured birth and command identity or the manager's own Popen; legacy Windows empty-birth rows cannot authorize signals, though a healthy attached daemon can still stop cooperatively through the CLI. Token refusal, invalid discovery, malformed responses and a matching error-code string alone never provide stop authority. Only confirmed death permits signal-stop custody removal; concurrent rows survive.

The short manager lock retires the local startup generation before waits and never spans runtime preparation, network or process-exit work. CLI RPC, termination confirmation and startup slack use `config.CLAUDEXOR_OPERATOR_STOP_TIMEOUT_SEC`; captured-process observation uses `config.CLAUDEXOR_STOP_EXIT_WAIT_SEC` (both owned by `runtime_limits`); the phases promise no absolute total stop duration. A live startup outlives its caller's window (20 seconds by default, independently narrowable): `daemon_starting` invites joining the same work, whereas `daemon_spawn_failed` identifies the exited child/build/log interval. Native Windows and frozen-import evidence: DEVELOPMENT's Process Custody Rule.

**Startup failure: typed classification, one durable row, the spawn latch.** When this manager's own child exits without a control endpoint, `claudexor_startup_failure.py` classifies the failure from the child's own identity-checked `daemon.log` interval into `heap_exhausted` (V8's fatal heap-limit banner), `writer_lease_contended` (the engine's single-writer refusal), `engine_floor` (the root-authority version-floor refusal) or `unclassified`. The classification is diagnostic only — it names the failure in the typed `daemon_spawn_failed` detail, in `last_error` and in one durable `claudexor_daemon_start_failed` supervisor row (pin, exit code or signal, descriptor written or not, classification, log interval, `latched`, `ts`) — and never selects behaviour. The latch keys on the typed exit fact alone: the child exited by signal or non-zero and wrote no control descriptor during that spawn; a clean exit or a crash after publishing control is rowed with `latched=false`, and a joined peer startup that vanished is not rowed. While latched, every ordinary caller (delegation, model calls, review, warmup) receives the same immediate `daemon_spawn_failed` refusal, before runtime preparation and without a new spawn — unless a live startup exists, which it joins, because refusing there would hide a daemon that may come up. Releases — three are rowed as `claudexor_daemon_start_latch_cleared`, the fourth is not: attaching to a live authenticated daemon (`cleared_by=live_daemon_attached`); the ~600 s periodic supervisor sweep (`cleared_by=supervisor_sweep`), itself off the loop thread and attach-only once a stop is in flight, which only when it actually released a latch makes exactly one zero-wait ensure on a short-lived background thread, so a healthy install never spawns or waits in the sweep and a persistently crashing engine costs one spawn per period; the owner's explicit Refresh (`/api/claudexor/wake`, `cleared_by=owner_wake`), one spawn per press; and the owner's Restart or Panic, which release it without a row by constructing a new manager. The latch is per-manager state and the manager is a process global: the sweep and the Refresh release the server process's latch, while a task worker holds its own, released only by a live-daemon attach or the worker's respawn. There is no backoff, counter, cooldown, heap policy or new timing constant: the host neither derives the engine's heap from host RAM (V8's default old space is 4096 MiB from 8 GiB up: a guess only moves the crash; the engine's bounded replay removes the need) nor touches the writer lease. `NODE_OPTIONS` set on the server process is inherited by the spawned daemon unchanged — the operator's documented escape hatch (for example `NODE_OPTIONS=--max-old-space-size=8192`), not a product mechanism. The registration pass of the same sweep (`retire_settled_registrations`) reaches the daemon only for a registration every sharer has settled. Its typed `PROJECT_RETIRED`/`PROJECT_RETIRE_FAILED` discharge, the harvest cadence and the two disclosed residuals are stated once, in DEVELOPMENT's Process Custody Rule.

Foreground `run_command`/`run_script` uses the in-memory `_active_subprocesses` Panic registry. Services, executor processes, companions and delegated runtimes use durable exact-identity `spawn_supervised` custody (§1). Unix process groups/Windows Jobs clean trees; executor/service records support recovery after worker death. Normal cleanup may archive logs; Panic skips nonessential finalization and cannot wait on wedged cleanup. Tool results distinguish timeout, signal and success.
