# 3. Web UI Pages & Buttons

One build-free SPA serves desktop, browser, Docker, Telegram, phone and Linux fallback. The browser paints host-stamped placement, outcome, receipts and liveness; text, timing and client lists grant no authority.

### SPA shape and host bridges

The inspectable, editable, build-free vanilla-JavaScript SPA (`web/index.html`, CSS, `web/modules/*`) uses no TypeScript/bundler. `web/app.js` owns page/Project/mobile navigation; feature modules own presentation/disposers (DEVELOPMENT "UI resources carry a disposer"). Linux fallback changes only presentation; the owner's browser is outside process custody (§1). One WebSocket serves all rooms; REST recovers durable truth (§4).

The desktop shell exposes `MainApi` (`window.pywebview.api`, `launcher.py`): native confirmations (runtime mode, reviewed-skill auto-grant, skill key grant), the alert and shell half inherited from `launcher_background.DesktopApi` (`request_attention`/`notify_owner`, `shell_info`, `request_native_notifications`, `show_native_notification` via `desktop_notifications.py`, `set_native_appearance`) and the file and URL helpers (`download_file_to_downloads`, `open_file_with_default_app`, `open_external_url`, `save_bytes_to_downloads`). Loopback-file methods accept only the server's own host/port and paths under `/api/files/download`, `/api/extensions/...` and `/api/tasks/...`. For a newer frontend/older shell (§2), `ui_helpers.js` detects bridge methods per call, falling back to file helpers or copy-link/toast. Its link interceptor also serves framed onboarding (`OnboardingHostApi`). The Telegram proxy's `X-Ouroboros-Telegram-MiniApp: 1` marker makes `server_web.make_index_page` include the Telegram SDK: presentation, never authentication.

### Navigation and shared UI contracts

Appearance is client-local, not a runtime setting; same-origin windows share the stored choice. `web/theme.js` runs before CSS in both first-party documents and owns `ouroboros.theme` (`light`, `dark` or `system`); `[data-theme-control]` is one shared radiogroup (Settings → Appearance and onboarding) owning no `s-` input, so the Settings collector never posts it, and `ouro:theme-changed` fires only on a resolved palette change. On the Windows desktop the system caption takes the painted palette's tint: the top-level page, never a framed copy, reports to its window's `set_native_appearance(theme, page, sequence)`, and `ouroboros/launcher_appearance.py` keeps only the request newer by that pair: bridge calls arrive out of order on worker threads; the page's stored choice is the one authority. A dark caption under a light system mode, and on Windows 10, is unverified natively; an accepted call does not prove pixels.

`web/modules/notifications.js` owns one client-level subscription on `app.js`'s shared socket, outside room lifetimes. Only live frames arrive, so replay safety is structural; the room gate mirrors `chat_activity.mainThreadAccepts`, and classification uses lifecycle facts/`system_type`, never text (DESIGN §9; DEVELOPMENT "notifications ring for live events only"). Activation resolves the Project from the full registry, not sidebar rows; failure says unavailable, never substitutes Main. Telegram and other Main transports stay Main; numeric chat-id ranges never infer Project identity.

Independent iframes inherit no host tokens/stored choice; modules declare `render.appearance` (`host`, `independent`, `fixed`; CREATING_SKILLS). First-party `webview.start(private_mode=False)` requests persistent storage; pywebview's default private mode erases it on window opening. Launchers without that flag keep erasing until a new build installs or updated launcher source re-executes at restart (§2; native Windows unqualified). `desktop_shell.js` discloses this in Settings → Appearance.

Navigation exposes Chat (Main), collapsible Projects, Files, Skills, Widgets, Dashboard and Settings (including About). `syncNavigationState()` owns page, Project, expansion, drawer and backdrop together, preventing conflicting selection; sidebar/panel widths are owner-local. A `#<page>` fragment is honoured once, never written back: desktop/Linux fallback lack an address bar and Telegram loads `/`. Projects are panels, not routes; the sidebar is the sole `<nav>`. Rows open/rename/delete by pointer and keyboard; backend `PROJECT_NAME_MAX` and lifecycle govern names and access. Unread sorts first; deleting rooms cannot open until registry publication. Narrow screens use an explicit drawer and full-width Project overlay, preserving scroll, selection and software keyboard without gesture-only controls.

Shared primitives prevent competing contracts: no page reimplements supervisor, review, marketplace, extension or provider semantics.

Opaque additive `cursor` selects older or (`after_cursor`) newer rows; `around=task:<id>` reads the page around a task's first room row (`anchor` found/moved/absent), never the present; `has_more` follows conversation, membership changes return `history_view_changed`, never mixed views. `window.complete` means all reachable history, independent of `has_more`; `coverage` v1 reports source spans/witnesses/gaps (`history.py` mapper, `history_paging.py` mechanism). Lineage, task order and Main's newest result are indexed store selects (`task_store.py`, §1); `history_gap.lineage_incomplete` is nonfatal.

Read-only SSE v2 `POST /api/tasks/{id}/events` reads progress/chat/events/tools/supervisor sources. `validate_ingress` checks `TaskEventsRequest` `{v:2, wait, cursor}` before cursor semantics; cursor offsets address each root/source across archives/live. Physical source order, never timestamp ranks, preserves retroactive inserts; rows carry stable `event_id` and next cursor. Frames: filter-change `cursor_replay`, wait-expiry `cursor_checkpoint` (skipped bytes, no progress), immutable-malformed-line `history_gap`, unreadable/shortened-chain `cursor_unavailable`, never reset. Offsets require retained immutable archives; only explicit pre-preparation `created_at` may skip older ones. GET/`iter_task_events` retain timestamp-sorted integer ranks; CLI falls back to GET only on first-connect HTTP 405 (`gateway/task_events.py`, `cli.py`). Agent `chat_history` reads the same rotated/live timeline with provider/account/conversation/thread/actor/date filters.

History adds an inert `task_evidence` carrier for represented tasks or unanswered current work, only in the task's own room; it spends no conversation quota, supplies no row identity or liveness, keeps all terminal truth, so reload settles the card if it is the task's only terminal row in the window. Quiz-bound `owner_wait` facts, including their `quiz_id`, project apart from Project question details, so Main and Project waits end on one recorded answer; confirmed pauses leave task-keyed System rows through `pause_notices` (§5).

#### Widgets page

Widgets is a separate page because extension UI is an execution surface, not catalogue metadata. It renders only the UI tabs of reviewed live extensions from the passive projection `GET /api/widgets` (a card's `revision` is the owning skill's `content_hash`, a change signature, not an ETag; Skills stays on `/api/extensions`). The framed render modes share one capability set (`sandbox="allow-scripts allow-pointer-lock allow-downloads"`, `allow="autoplay; fullscreen; clipboard-write"`, never `allow-same-origin`; author contract: `docs/CREATING_SKILLS.md`). A route iframe (`kind: iframe`) is the skill's bridgeless page declaring its `route`; host-owned code renders a declarative widget from a validated schema; a module widget uses an opaque-origin `srcdoc` iframe with a CSP built by `web/modules/widget_module.js` from the page origin (`default-src 'none'`, no `connect-src`); height bounds and geometry keys: `extension_ui_validation.py`. Card order, widths (`widget_size`) and per-card launch-policy overrides (`widget_start_mode`) are host UI state in `/api/ui/preferences`; `masonry.js` packs cards through `--masonry-*` custom properties alone, so reorder or resize never moves a node or reloads a frame (DESIGN "Widgets board"). Framed cards have one Start/Stop control and launch-policy precedence: owner override, author's `render.start`, kind default (`widget_card.js`); `retain` keeps a framed card mounted while Widgets is hidden and ends it on Stop, on skill removal from the live list, changed `revision` or window closure, never on the server's word alone. A module widget stops in order with acknowledgement (`ouro-widget-disposed`, else `WIDGET_DISPOSE_ACK_TIMEOUT_MS`); a route iframe disposes synchronously. Chart.js is bundled locally, never a third-party CDN. Engineering rules: DEVELOPMENT "Embedded surfaces declare geometry and refresh semantics", "UI resources carry a disposer", "Declarative widgets".

A module widget gets one parent-mediated I/O bridge on a per-mount nonce (`widget_frame.js`), the frame's only scriptable network path since `connect-src` is closed, giving reviewed skill JavaScript route I/O without SPA cookies, DOM or broad API authority. `OuroborosWidget.fetch` relays only to the owning `/api/extensions/<skill>/...` prefix with same-origin credentials, refusing redirects; WS events arrive through `onEvent` filtered by `ws_prefix`; external links use the host bridge; opted-in modules get the resolved theme through `onTheme`, never palette or theme-setting authority. #### Settings save effects

Settings save reports three effect classes, not universal immediate effect (membership: `settings_scales.py` `IMMEDIATE_SETTINGS` / `RESTART_REQUIRED_SETTINGS`, applied by `gateway/settings.py`).
