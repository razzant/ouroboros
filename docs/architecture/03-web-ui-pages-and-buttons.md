# 3. Web UI Pages & Buttons

One build-free SPA serves every surface — desktop shell, browser, Docker, Telegram mini app, phone and the Linux fallback — and this chapter maps its pages (Chat and Projects, Files, Skills and Widgets, Dashboard, Settings and onboarding), the frontend contracts they share (navigation, appearance, notifications, dialogs, primitives, host bridges) and how each page projects runtime truth. The decision that shapes every section: the browser paints facts the host stamps (row placement, outcome phase, receipts, liveness census) and derives none of them from text, timing or a client-side list.

### SPA shape and host bridges

The Web UI is a build-free vanilla-JavaScript SPA (`web/index.html`, shared CSS, `web/modules/*`): no TypeScript or bundler, so the running interface stays inspectable and editable by Ouroboros without opaque build artifacts. `web/app.js` owns top-level page, Project-panel and mobile-navigation state; feature modules own their presentation; every long-lived UI acquisition carries a disposer bound to the lifecycle that created it (DEVELOPMENT "UI resources carry a disposer"). The Linux browser fallback changes presentation only, and the browser stays the owner's application outside process custody (§1). One shared WebSocket serves the whole application, Projects open no sockets of their own, and REST is the recovery and durable-read path (§4 WebSocket protocol).

The desktop shell exposes `MainApi` (`window.pywebview.api`, `launcher.py`): native confirmations (runtime mode, reviewed-skill auto-grant, skill key grant), the alert and shell half inherited from `launcher_background.DesktopApi` (`request_attention`/`notify_owner`, `shell_info`, `request_native_notifications`, `show_native_notification` via `desktop_notifications.py`, `set_native_appearance`) and the file and URL helpers (`download_file_to_downloads`, `open_file_with_default_app`, `open_external_url`, `save_bytes_to_downloads`). Loopback-file methods accept only the server's own host and port and paths under `/api/files/download`, `/api/extensions/...` and `/api/tasks/...`. The served frontend can be newer than the shell (older packaged launchers change only on reinstall; newer ones re-execute changed launcher source at restart, §2 Body switch at entry), so `ui_helpers.js` feature-detects every bridge method per call and falls back to file helpers or copy-link-plus-toast; its link interceptor serves the SPA and the framed onboarding wizard alike (`OnboardingHostApi`). The Telegram proxy's `X-Ouroboros-Telegram-MiniApp: 1` marker makes `server_web.make_index_page` include the Telegram SDK; it is presentation only and grants no authentication authority.

### Navigation and shared UI contracts

Appearance is client-local, not a runtime setting; same-origin windows share the stored choice. `web/theme.js` runs before CSS in both first-party documents and owns `ouroboros.theme` (`light`, `dark` or `system`); `[data-theme-control]` is one shared radiogroup, mounted by Settings → Appearance and the onboarding document, that owns no `s-` input, so the Settings collector never posts it, and `ouro:theme-changed` fires only on a resolved palette change. On the Windows desktop the window's system caption takes the tint of the painted palette: the top-level page, never a framed copy, reports to its own window's `set_native_appearance(theme, page, sequence)`, and `ouroboros/launcher_appearance.py` keeps only the request newer by that pair, because bridge calls arrive on worker threads out of order; the page's stored choice is the one authority. Whether Windows honours a dark caption under a light system mode, and on Windows 10, is unverified on native Windows; an accepted call is not proof of pixels.

`web/modules/notifications.js` is the one notification owner: one client-level subscription on the shared socket in `app.js`, never inside a chat instance, which dies with its room; only live frames reach it, so replay safety is structural; the room gate mirrors `chat_activity.mainThreadAccepts`; classification reads lifecycle facts and `system_type`, never text (policy: DESIGN §9; rules: DEVELOPMENT "notifications ring for live events only").

Independent iframe documents inherit neither the host's tokens nor its stored choice; a module declares its intent in `render.appearance` (`host`, `independent`, `fixed`; CREATING_SKILLS). Every first-party `webview.start(private_mode=False)` requests persistent website storage, because pywebview's default private mode erases the WebView's website data whenever a window opens; a packaged launcher built without that flag keeps erasing until a new desktop build is installed or re-executes updated launcher source at restart (§2 Body switch at entry; not yet qualified on native Windows), and `desktop_shell.js` discloses such an app in Settings → Appearance.

Primary navigation exposes Chat (Main), a collapsible Projects group, Files, Skills, Widgets, Dashboard and Settings; About is a Settings sub-tab. `syncNavigationState()` is the single presentation state machine for active page, active Project, Projects expansion, mobile drawer and panel backdrop, so independent toggles cannot leave two rows active or a hidden surface looking selected; sidebar and panel widths are owner-local preferences. The application has one client-side route, a `#<page>` fragment honoured once on load and never written back, because the desktop shell and the Linux fallback have no address bar and the Telegram mini app always loads at `/`; Projects are panels, not routes, and the sidebar is the document's one `<nav>` landmark. Project rows open, rename and delete by pointer and keyboard; the backend owns the name limit (`PROJECT_NAME_MAX`) and lifecycle truth, unread Projects sort first, and a deleting Project is non-openable until the server publishes registry state. On narrow screens navigation is an explicit drawer and the Project chat a full-width overlay; no gesture-only layer competes with scroll, selection or the software keyboard.

### Chat and Projects

#### Timeline ownership and ordering

`web/modules/chat.js` owns the canonical message timeline, drafts, attachment staging, runtime controls, budget projection, routing annotations, task and child cards, WebSocket subscriptions, thread routing, insertion order, unread state and reconnect reconciliation; `chat_media.js` (per instance) owns delivered-media presentation and the composer's paste and drop targets, `chat_attachments.js` staged files and the owner's attachment block. Every ordinary message has one canonical durable chat row; Project views are lenses over those rows and task bindings, so conversion creates no second message, unread event or cost record. Routing acknowledgements live in a sidecar keyed by `client_message_id` and update the existing owner message without a synthetic assistant bubble.

Messages, media bubbles and task-card roots order by raw numeric timestamps (ties keep arrival order; band anatomy: `docs/DESIGN.md`). History reconciliation is one synchronous transaction over keyed records that preserves timeline and Review nodes, disclosure, focus and selection; a child keeps one keyed lifecycle row across live delivery and replay, older pages cannot regress it, and a task's current result outranks its historical terminal observation; `LIVE_CARD_CAP` bounds live accumulation. `chat_history.js` bounds rendered pages (`maxPages`); `historyCoverage` is proof of byte delivery, and an unhealed gap stays partial, because EOF, shared IDs and chronology prove nothing. `chat_reading_position.js` owns the viewport: it follows explicit live-edge intent near the bottom, otherwise keeps the reader's anchor; every room opens on its newest message (`showLatest`), and only an archive-edge gesture reads older pages (`createHistoryControls`; `Load more history`: DESIGN "History edges"). `createHistoryControls` keeps one disabled initial-loading pill at the feed edge and a persistent Main/Project header note for gaps, errors and approximate positioning; only Main’s floating header adds a reading backing. Origin adoption uses `project_dialogue.project_origin_identity`.

#### Main rows and host-stamped card rows

Progress callbacks capture address, lineage and attempt at binding, so a late review cannot inherit another turn; unkeyed progress and summary rows never mutate a live card. `terminal_projection.py` owes the Project row and the deferred Main mirror together: `write_task_result` stamps `canonical_terminal_projection_origin=terminal_transition` only on an accepted root terminal transition, so markerless historical rows are never replayed; publication and retirement require `headless.terminal_task_files_ready`, because synthesis alone does not prove artifact completion; publication errors are isolated from task-done and retried at checkpoint, startup and the `server_maintenance.py` sweep; the bounded outbox and at-least-once transport preclude exactly-once.

Main receives its own dialogue, Project quiz mirrors and `project_dialogue.MAIN_PINNED_ROW_TYPES` (`project_handoff`, `project_started`, `project_completion_summary`, and a root's `main_notice` from `send_user_message(destination="main")`), pinned at supervisor send and `room_membership` replay; other Project traffic stays in its room. `projects_registry.mirrored_answer` carries the whole `completion_answer` only for a nonempty `model_final` in a settled phase within `MIRRORED_ANSWER_MAX_CHARS`; otherwise it is absent, never cut (`project_answer.js::decorateProjectRow`; DESIGN "Project completion mirror"). `ORIGIN_ADDRESSED_NOTICE_TYPES` (`task_not_started`, `task_start_unconfirmed`, `steer_not_delivered`) stay in their issuing chat on replay despite target binding.

Every unanswered Project quiz is mirrored into Main from one keyed pointer, without a second durable message: `chat_decision.buildQuizCard` renders the Project's own form plus the Project reference (DESIGN "Project question mirror") over the existing decision ingress; only Main's copy retires after the first confirmed `answered` observation, and a settled question never reopens. `project_dialogue.project_question_pointer`, live `message_bus.send_quiz` and the census `required_question` carry the same question fields, so a narrower redelivery never blanks a known field; `question_presentation.js` owns the lifecycle wording, with the Python twin `project_dialogue.QUESTION_STATUS` pinned by `question_presentation_parity.json`. Waiting requires positive evidence, carried by history too, because ordinary input can resume a task without a `quiz_state` frame.

A host fact about a task is a row of that task's card, never a standalone bubble beside it: the producer stamps `card_row` (`timeline` or `reviews`) and `card_row_id` (§11.1), and the browser attaches the row to the card record; only a row whose task has no card record in the page renders as a standalone System row with the same words. Finality metadata is row-specific: durable `task_summary` rows carry `outcome_phase` (`project_dialogue.outcome_phase` mirrors `log_events.js`; headline from `OUTCOME_PHASE_HEADLINE`), the pre-finalization row carries `outcome_final=false` and no verdict, only terminal `task_summary` rows append the host verdict clause (`_completion_verdict`), and the Main `project_completion_summary` carries headline and verdict in plain text with no `outcome_phase`. A verdict is one owner sentence from `project_dialogue.TASK_CAUSE_PHRASES`, keyed by the typed reason code (a code without a sentence stays raw): the execution reason, or the decision's reason when the host's acceptance decision is anything but accepted; the reviewer rationale stays on the task result and in Logs, so a host-authored row never presents an unaccepted claim as the whole story.

#### Project handoff receipts

`project_handoff.py` owes a Main transfer receipt through the terminal outbox after durable binding. `handoff_id` binds the captured ingress message and Project: technical retries share a receipt, independent requests do not. `RECEIPT_STATES` separates binding from receipt durability; `durable`/`already_delivered` prove the Main row owed/delivered, `origin_unproven` writes none, and other states name a gap. Main is never a default destination. `POST /api/projects/from-task` returns `handoff_receipt` and `handoff_id`; a non-durable result warns on the card without inventing history.

`project_handoff.js` owns creation/transfer layout, live and replayed, with `formatMsgTime` and chat copy controls. Folding supplies the matching receipt time; anchors and task outcomes stay separate. Structured `task_name` follows producers, bus and history. `task_phase_chip.censusTaskPhase`/`paintTaskPhase` share outcome and motion with tasks and Project summaries (DESIGN "Project work entries"). Only explicit technical retry follows work; owner Continue starts a new root, and reconnect must re-prove activity.

#### Composer, attachments and delivered media

The Main composer exposes one-shot Swarm planning, the owner Nano/Low/Max context choice and effort range, file attachment and Send. Swarm places a structural `force_plan` fact on the next message and disarms after it, never inferred from keywords. The host admits one managed root in the sending room without a model call, carrying the verbatim objective, origin, surface and attachments; the root may choose its Project via `ensure_project_scope` (§6). `composer_owner_controls.js` owns both (DESIGN "Composer owner controls"), each posted to its owner endpoint (`/api/owner/context-mode`; `/api/owner/effort-range` with the `{min, recommended, max}` triple on gesture end, serialized, Send waiting for a pending save) read back from `/api/state` into every open composer; a derived Low fit is never an owner choice; the mode sizes Ouroboros's window, not review authority. Project panels omit the global Restart, Panic, evolution, consciousness, review and budget controls.

Attachments stage via paperclip, paste or drag-and-drop with no count or size rejection; upload begins on Send, and offline handling is the WebSocket queue contract (§4). The canonical writer claims the frame's uploads in the ingress critical section and records server-measured refs on the row; upload response, echo and history carry the same `chat_uploads.attachment_view` (DESIGN "Chat attachments"). Delivered documents capture immutable task-owned bytes and carry a verified `file_ref` plus canonical download URL, rebuilding from history without persisting base64; files above `core_artifacts._MAX_DOCUMENT_FILE_BYTES` are file-backed, photos and videos keep base64 only in the live frame, and supported media is stored under the canonical task artifact root with a content-addressed URL so replay restores the same bubble. Structured `links` rows render at most `MAX_LINK_ACTIONS` revalidated HTTP(S) buttons. The supervisor transport owns durable media copies; failed persistence stays an honest caption row and cannot finalize a task card.

#### Direct turns and the activity block

Ordinary Main and Project conversations use complete native execution even while other work runs: each turn owns its agent and creates no supervisor queue record. The process-local `supervisor.active_activity.DirectActivityRegistry` retains the private actor handle from preparation through result delivery; Stop, Hurry, quiz and steering resolve that exact actor, while `active_direct_turns` and typing frames expose presentation fields only. The managed-update writer drain, custody maintenance and the restart census include these turns, and the consciousness alarm clock starts no wake while an owner direct turn is live.

`_is_direct_chat` is one fact carried by the durable result, the terminal event, the rebuilt `task_done`, the authored `task_summary` row, the history terminal-truth annotation (`gateway/history.py`) and the census `kind`, so a late or replayed Project completion stays in its room without a Main summary. Every worker progress frame carries the typed `narration` fact (`ouroboros/agent.py::_emit_progress`): `True` only for the model's own words, `False` for every host note; `gateway/history.py::_PROGRESS_META_FIELDS` whitelists it into history, so only narration reaches the card title and collapsed activity line while a host note stays a visible timeline row.

`chat.js::blockVisible` reevaluates content, open attention and work at every mutation (predicate: DESIGN "Conversation activity block"); successful tool calls fold into one `chat_activity.js::toolEvidenceView` row, failures keep their own counted rows, and host metrics replace live call facts. `blockHasWork` decides task-card chrome; `_is_direct_chat` drives only the client header pill. Addressing calls carry host `routing_action` frames and `routing_tool_calls` metrics from `tool_capabilities.ROUTING_VERBS`, completion acts `completion_control` and `completion_tool_calls`; these receipt rows render inside an existing block but never create one, so live, reload and reconnect need no client tool-name list. A refused addressing act states the host's `cause` verbatim (`routingAnnotationText`); a host-issued act refused before starting adds one `📋 System` row (`task_not_started` / `task_start_unconfirmed`) keyed to the never-started task, and replay neither creates nor finishes its card.

#### Liveness census and the chat header

`GET /api/state` combines direct turns and managed root tasks in `active_chat_activities` with the frozen status vocabulary (§11.1 What is frozen); parked direct turns keep their ID and `kind="direct_chat"`, and `pause_cause` names budget, owner, restart, sleep or unknown without granting execution. Only the census inserts live entries; finals and census delete them, and absent IDs clear only with `active_chat_activities_complete === true` and `supervisor_ready === true`, so an incomplete read retains positives. One shared `/api/state` sequencer (`chat_activity.js::createStateSnapshotSequencer`) serves the Main chat's short poll and `app.js`'s longer one.

Typing is a submission receipt: it matches `client_message_id`, retires the local `Sending...` bubble and requests a census; it never inserts, revives or extends liveness. The header reducer reads connection, census, unconfirmed owner sends and live managed cards; a direct block is not a managed card, and terminal failure remains a task result, never a reasonless header `Attention`. A typed `ingress_accepted` echo adds `Input saved` without implying task admission; the badge is `Starting…` until `supervisor_ready` is true (re-proven per reconnect), then `Online`. `web/modules/project_activity.js` groups census rows by `project_id` for the Project dots; partial positives stay current, an unreadable question detail (`required_question_unavailable`) stays static unknown, and only a complete supervisor-ready snapshot clears an absence.

Owner rows and routing annotations stay in the bounded local journal until history returns their `client_message_id`. Early root answers carry `task_phase="finalizing"`, also derived on replay from the open checkpoint; `task_cost_finalized` never closes a card; `log_events.taskTerminalSummary` projects settled task-scope status as `observedOutcome`, the outcome owns the chip and `task_phase_chip.paintTaskPhase` adds a quieter `Finalizing…`.

Two invariants close the class of liveness the server cannot name. The history window is lineage-closed (`ouroboros/gateway/history.py`): subagent lineage older than the window's recency floor is kept only while the child runs or finalizes or its parent is represented or alive, a nested swarm is kept or dropped whole, and a final row failing that test is emitted without lineage fields, so replay cannot mint an unfinishable parent card. Liveness reconciles over the card set, not only the census: only an id the census actually lists shields a card, an unvouched connected root card is finished only by proven durable terminal detail, and a card without a current result stays unconfirmed until a complete fresh snapshot excludes it, then uses the retained typed terminal fact or a neutral `Outcome unavailable` anchor without phase or controls. A root proven terminal settles descendant cards from each child's own durable result, never by cascade from the parent's outcome.

#### Task cards, errors and reason lines

`log_events.js` keeps the live task card and grouped task cards on one reducer in Chat and Dashboard Logs. Nonterminal LLM, tool and checkpoint failures stay in details without promotion; only authoritative task truth changes terminal status, and unknown Chat names gain no severity from keywords. `task_checkpoints.js` owns the typed checkpoint vocabulary (`log_events.taskCheckpointLabel`); checkpoints and `context_reclaim` appear in the expanded card, never as titles, collapsed narration or toasts. Replayed `tools.jsonl` uses the same typed facts (`ok`/`level` outrank names); a call's start row is its live frame, never liveness; keyword matching remains only the non-expanding fallback for untyped unknown Logs events. A `swarm_fanout` with `role="delegated_run"` names a delegated run, not a child; failed children keep local `Failed` while their root continues; cards navigate results rather than own them, and only explicit `task_incident` facts raise urgent toasts.

`taskReasonDetail` joins recorded causes once with ` · `: a soft stop adds none, a hard failure names the execution reason, and a cancellation names its source and flattened cause. Only `request_origin.kind="agent_task"` identifies an actor; `requested_by` alone cannot. Lineage supplies parent/ancestor wording without IDs; `cancel_task` uses the asker's relation (`cancel_presentation.cancelCauseClauses`, Python twin `supervisor.cancel_publication.cancel_cause_clauses`). Non-accepted acceptance uses cause-table text without status or rationale; deferred children (`outcome_axes.objective.deferred_count`), open review (`terminal_plan_review_open`) and custody debt stay beside the cause; unknown codes stay raw.

#### Child cards and executor presentation

Subagents render as child cards keyed by child task ids; a parent holds lineage references and never duplicates the child's answer. Nested children collapse by default; the headline is the explicit role or neutral `Subagent`, a short task id tells identical siblings apart, and metadata labels Agent model or Coordinator beside the executor observation and the effort chip (`effort_chip.js` from the frame's effort scalars; no level, no chip; layout: DESIGN "Conversation activity block"). A refused harness pin shows `{harness} · blocked` beside the typed `subagent_executor_unavailable` terminal, never `dispatched` or `no run yet`. Reviews are not lineage: a reviewer run's receipt lives in the owning card and mints no child. Selected `subagent_id`, requested route, effective route/model/account and terminal evidence stay separate facts (`executor_observation`, `execution_evidence`, `actual_substrate`: §11.1), so intent never passes for proof of where the run settled; `harness_presentation.js::executorIdentityMarkup` alone renders Coordinator, Agent model and observed-model identity; `delegated_activity.js` projects executor speech, thinking, problems and technical counts in root and child cards, live and on replay (§6), never narration, title or proof.

#### Reviews projection

The task card's `Reviews` section is a read-only projection over independent domain authorities — skill review history, typed plan-review state, task-acceptance evidence, repository-review records — each keeping its own lifecycle, verdict and enforcement. The admitted rows are task-bound Skill Review, plan review, task acceptance and, once the task ends, the task's own review-ledger records (commit gate, `review_change`, preflight, `/review`): the result's `review_projection` carries the five newest as panels in one `Review records` group, and `review_records_omitted` says `0`, `1+` or `unknown`. A record's panel and reviewer lines are one pure projection, `review_record_card.js`, printed alike by a Reviews attempt and a Logs review event. The projection synthesizes no task-wide verdict and changes no routing, status, attention or enforcement; there is no review inbox, generic review endpoint or second state machine, and task-result `plan_review_state` stays the plan-review authority. A `review_reference` row is addressed to the task's bound Project chat, else the chat its caller named, else the hidden partition; Main is never its default. When review history is the only retained fact for an owner, Chat renders an inert owner anchor with `Reviews` and no task phase or liveness (DESIGN "Reviews inside task cards"; renderer `review_presentation.js`).

#### Card cost

A card's cost is one scope's accounting facts (amount, finality, subtree, reservation, unknown) bound by `cost_presentation`, never a per-call `cost_usd` alone (producer: §6 Budget tracking; words: DESIGN "Conversation activity block"). Root-tree evidence outranks own scope; no attributable subtree rows means absent, not zero. Dashboard and task detail read the ledger, not cards; compact Reviews carry no money, while exact-job Skill Review detail reads it from the ledger. Precedence and the live-root feed: `cost_projection.py`.

#### Stop and cancel controls

Cancel appears only on unfinished, unconverted root cards whose host attests `cancelable=true`; card shape grants no control, and native direct tasks follow §5 custody. The shared dropdown sends `cascade:true`: hard stop waits for teardown or refusal, Wrap up records durable finalize intent and returns 202 pending. Completion wins, a missing live task reconciles from durable state, and unproven death stays a visible refusal. Reason lines: `log_events.taskReasonDetail` over `cancel_origin` (§3 Task cards, errors and reason lines).

#### Turning a card into a Project

A Main managed or Swarm root card becomes a Project in one click. Conversion creates the Project or adopts the one the task's owner message already has (`adopted: true`), binds the task and its origin message, moves live work onto the Project lane and swaps the Main action for a Project pointer. A fresh conversion also binds the origin's live sibling roots and direct turns (`project_origin_siblings_bound` in `events.jsonl`), to avoid duplicate Projects for one owner message; an adopting conversion binds only the clicked card, and `task_bindings` in `/api/state` marks the message's other live tasks `origin_bound`, whose button closes and whose pointer opens the Project. A request naming a different `project_id` is an explicit choice and keeps the 409. No button on tasks already bound, on children (they inherit their root's Project by lineage) or on blocks that have done no work; a direct-turn card is convertible, its durable bind is its commit point. Mechanism: §6 Project binding by task and by origin.

The Project reference (`project_reference.js`; DESIGN "References and actions") appears only on Main root cards and opens or focuses the panel, never closes it; the client has no naming authority. Project-scoped is not project-bound: a headless/CLI run carries a `project_id` for lease and memory without a durable binding, is addressed to the Project thread at admission (§5), never mints a Main card and needs no conversion button.

#### Project rooms

A Project chat's status bar carries one navigation pointer (`project_work_pointer.js`) to the latest unfinished non-child card, else the latest root; it creates no card or execution state and never selects the next message's recipient (labels: DESIGN "Project work pointer"). The New Project dialog takes exactly one source: no folder, a fresh managed genesis workspace, an attached existing folder or a cloned Git URL; Attach uses a server-side directory browser so the flow works in web and Docker, Git-specific operations require a Git worktree, and every folder source discloses that Project tasks get read, write and shell access there (`project_create.js`). Deleting a Project is lifecycle work, not filesystem deletion (§6 Project registry and lease): the server fences new admission, cancels and quiesces the Project task subtree, then tombstones the registry entry; the UI never claims completion early, and Project id, canonical history, task bindings, memory, provenance and the working folder remain.

Project unread is `visible_revision > project_seen_revision` (DESIGN "Project unread dot"): standalone messages advance it, a child's media and questions included; card rows and progress do not. `project_read_state.js` acknowledges a revision after a covering history read paints in the visible room with the newest message in view; the server clamps and max-merges ACKs (`gateway/ui_preferences.py`). `app.js` keeps at most one live Project chat instance and destroys it on close or switch; the one exception is client state the server cannot rebuild (staged `File`s or an upload in flight), whose instance is hidden until its work settles. Unsent text survives in per-thread session storage; hidden rooms accumulate no listeners and acknowledge nothing (DEVELOPMENT "UI resources carry a disposer").

#### History reads and the SSE v2 transport

Interactive Chat history (`GET /api/chat/history`) pages a room in its own rows, not in bytes of the shared chain, so a Project's newest messages stay reachable however far back they sit; a Project read skips closed archives whose cached summary (`gateway/history_segments.py`) rules the room out. An opaque additive `cursor` selects older ranges, `has_more` follows the conversation, and changed room membership returns `history_view_changed`, never a mixed view; `window.complete` means complete reachable history, independent of `has_more`, and additive `coverage` v1 reports per-source delivered spans, witnesses and gaps (one mapper in `history.py`; mechanism: `history_paging.py`). Lineage discovery, task-list ordering and Main's newest-result selection share `task_result_facts.py`'s stat-invalidated memo (§1); `history_gap` frames with `lineage_incomplete` are nonfatal diagnostics.

`POST /api/tasks/{id}/events` is the read-only SSE v2 transport over the task's progress, chat, events, tools and supervisor sources (`TaskEventsRequest`, checked by `validate_ingress` before cursor semantics): JSON `{v:2, wait, cursor}`, the cursor holding one byte offset per root/source across the complete archive-plus-live chain. Events follow physical root/source order, never timestamp ranks, because ranks mis-order retroactive inserts across reconnects; each row carries a stable `event_id` and the cursor after that row. Frames: `cursor_replay` on a filter change, `cursor_checkpoint` at wait expiry (skipped bytes advance, no progress claimed), `history_gap` for an immutable malformed line, `cursor_unavailable` for an unreadable required segment or a shorter chain, never a reset. The offset guarantee needs archives immutable and retained; only an explicit creation fact (`created_at` stamped before preparation) may skip older archives. The GET form and `iter_task_events` keep timestamp-sorted integer ranks; the CLI uses POST and falls back to GET only on a first-connection HTTP 405 (`gateway/task_events.py`, `cli.py`). The agent-facing `chat_history` tool reads the same live-plus-rotated timeline with provider, account, conversation, thread, actor and date filters.

History adds an inert `task_evidence` carrier for represented or addressed tasks, in the task's own room only; it spends no conversation quota and supplies no row identity or liveness, yet keeps the whole terminal truth, so reload settles the card from it when it is the task's only terminal row in the window. Quiz-bound `owner_wait` facts project independently of Project question details, so Main and Project waits end on the same recorded answer; confirmed pauses leave task-keyed System rows through `pause_notices` (§5).

### Files

Files is a full gateway-backed file manager, not a chat attachment picker: navigation, preview (image, sandboxed PDF, text with an explicit binary/unsupported state), editing, create, upload, download, open in the OS, copy, move, paste and recursive delete; the desktop host bridge and the web fallback share one download contract. Save exists only for a writable complete text read, and unsaved text is guarded on selection, directory change, navigation and unload. The backend is the path authority (root confinement and symlink policy: §4); UI path strings and disabled buttons are presentation only.

### Skills and Widgets

Skills has three views: installed, ClawHub and OuroborosHub. The installed view merges extension truth with the serialized lifecycle queue, so queued and running install, update, review, dependency work, enable/disable, repair, uninstall and failure stay visible. A failed primary read keeps a labelled previous list or an unavailable state, never an empty success; hub facts on installed rows are `null` until the catalog read lands, so the installed list never waits for the hub. A review run's line names a failed, timed-out, cancelled or interrupted job beside its verdict, so a failed run never reads as `pending`. Hub Updates and Use Hub version confirm before any POST (`skills.js`). Installation, deterministic preflight, LLM review, owner grants, dependency readiness, extension loading, enablement and execution are separate lifecycle facts (§13): a fresh review implies neither granted keys nor installed dependencies, and `enabled=true` does not override a blocked review or a load error. Owner attestation skips only the expensive LLM review. Repair and run is an ordinary managed task entered through owner-message ingress; a later direct owner disable wins over it, and automatic repair carries no enable authority. Hub publication uses the selected-skill preflight and an ordinary managed task; the passive Installed projection neither runs Betterleaks nor claims publication readiness.

#### Widgets page

Widgets is a separate page because extension UI is an execution surface, not catalogue metadata. It renders only the UI tabs of reviewed live extensions from the passive projection `GET /api/widgets` (a card's `revision` is the owning skill's `content_hash`, a change signature, not an ETag; Skills stays on `/api/extensions`). Cards reconcile by key on a visible `extension_lifecycle` event, on every WebSocket (re)connect and from the Retry of a failed read; an unchanged card is never remounted, and a changed one is stopped before its replacement mounts. There is no list polling and no global Refresh, because retrying discovery must never stop a kept-running program behind the owner's back; a failed read keeps the last good cards, and `WIDGET_REQUEST_TIMEOUT_MS` bounds the list and preferences reads (`widget_list.js`, `widget_job.js`).

The framed render modes share one capability set (`sandbox="allow-scripts allow-pointer-lock allow-downloads"`, `allow="autoplay; fullscreen; clipboard-write"`, never `allow-same-origin`; author contract: `docs/CREATING_SKILLS.md`). A route iframe (`kind: iframe`) is the skill's own page with no bridge and declares the `route` it loads; a declarative widget is rendered by host-owned code from a validated schema; a module widget runs in an opaque-origin `srcdoc` iframe under a CSP that `web/modules/widget_module.js` builds from the page origin (`default-src 'none'`, no `connect-src`); height bounds and geometry keys: `extension_ui_validation.py`. Card order, widths (`widget_size`) and the per-card launch-policy override (`widget_start_mode`) are host UI state in `/api/ui/preferences`; `masonry.js` packs cards through `--masonry-*` custom properties alone, so a reorder or resize never moves a node or reloads a frame (DESIGN "Widgets board"). Framed cards start under a launch policy (the owner's override over the author's `render.start` over the kind default; `widget_card.js`) with one Start/Stop control; `retain` keeps a framed card mounted while Widgets is hidden and ends it on Stop, when its skill leaves the live list, on a changed `revision` and with the window, never on the server's word alone. A module widget is stopped in order with acknowledgement (`ouro-widget-disposed`, else `WIDGET_DISPOSE_ACK_TIMEOUT_MS`); a route iframe disposes synchronously. Chart.js is bundled locally, so rendering never depends on a third-party CDN. Engineering rules: DEVELOPMENT "Embedded surfaces declare geometry and refresh semantics", "UI resources carry a disposer", "Declarative widgets".

#### Declarative widgets

Declarative widgets cover forms and actions, status, data, text, code, markdown, tables, tabs, charts, polls, jobs, streams, subscriptions, progress, media, files, maps, calendars and kanban, composed through `group`, `metric` and `callout`; one recursive validator bounds the tree and reports the exact failing path (limits and identity: `docs/CREATING_SKILLS.md`). Within one mount, data updates reconcile nodes in place, preserving input identity, selection and live password text. `subscription.render` stays transitively passive, so an incoming event cannot smuggle a new active control tree past validation; text, attributes, links, media routes and field values are escaped or constrained for their actual sink.

#### Module widget bridge

A module widget receives one parent-mediated I/O bridge on a per-mount nonce (`widget_frame.js`), the frame's only scriptable network path since `connect-src` is closed, so reviewed skill JavaScript keeps useful route I/O without the SPA's cookies, DOM or broad API authority. `OuroborosWidget.fetch` relays only to the owning `/api/extensions/<skill>/...` prefix with same-origin credentials and redirect refusal; WS events arrive through `onEvent` filtered by `ws_prefix`; external links go through the host bridge; an opted-in module subscribes to the resolved theme through `onTheme`, and the parent injects no palette or theme-setting authority. The module endpoint serves only live reviewed registration text, and its opaque-origin response carries `Access-Control-Allow-Origin: *`. Script and CSP faults and content-height reports travel on the same nonce into the card status.

#### Author UI kit

Optional author controls reuse the installed `web/ui.css` and `modules/ui_primitives.js` rather than a second declarative renderer: `server_web.read_author_kit_assets()` reads them through the serving-root resolver and creates no endpoint, cache or state; recipes: `docs/examples/author_ui_kit/`. Authors may override or omit the kit; a failed kit load stays inside the author application.

#### Out-of-process extension responses

An out-of-process extension response streams through `extension_route_stream.py`: process and bundle contexts live across asynchronous startup and teardown, blocking work runs off the ASGI loop, and `runtime_limits.py` owns the chunk and cleanup bounds, which are not response deadlines (extension runtime: §13).

### Dashboard

Dashboard groups Logs, Evolution, Costs, Updates and Activity under the common tab binder; each sub-tab owns its loading and refresh policy instead of running every expensive reader while hidden. Charting uses the bundled Chart.js (§3 Widgets page).

Logs merges live WebSocket log frames with bounded REST backfill from the events, tools, progress and supervisor logs: chronological order, dedupe across live and reconnect overlap, bounded grouped task cards, raw record on demand, and the shared presentation of `log_events.js`. A failed backfill names the unavailable sources in a separate status row while live events continue; clearing the panel deletes no log. Mounted unfinished child cards refresh their holds through `/api/tasks?queue_only=1`. `project_admission_hold` (a gateway contract field) carries the host's label, reason and detail, not a phase; a missing or unreadable queue never proves recovery, and parked phases, Stop and terminal outrank it (`chat_activity.js`).

Activity joins queue entries with the same refresh's `/api/state` census; a partial census cannot prove idleness, and an unavailable queue never renders empty. Independent sections show the consciousness alarm and schedules; a failed read keeps the others. Authoritative controls are cascade cancellation, consciousness start/stop and schedule enable/disable/delete/restore; every schedule button sends action and reason to the audited `POST /api/schedules/{id}/action`, never a stale record rewrite (`activity.js`).

Costs is a projection of the physical-attempt ledger: known spend (confirmed plus estimated, both shown) against the limit, then reserved and unresolved upper-bound holds that do not count as spending, unknown/unmetered usage, open rows and finality; unavailable data renders as unavailable, not `$0`. Breakdowns by model, key, model category and task category are views over the same ledger. Total budget hot-applies; the per-task value is a hard cap over the whole root tree of the next task, not an own-task soft warning (§7 Default settings), and raising a cap does not resume work that already finalized or paused.

Evolution shows the evolution state, the consciousness alarm clock, campaign objective and progress, queue/failure/budget information and durable history; starting a campaign uses the shared input dialog, where confirmed empty input selects the backend's default autonomous objective. Light runtime mode disables self-modifying campaigns rather than offering a control the backend will refuse.

#### Updates

Updates separates passive status from explicit mutation. Opening the page reads cached local update and git state without touching the network, carrying the last real check's timestamp and a minimal `update_tx` projection so a re-opened panel sees an assisted resolution in progress. One pure verdict (`updates.js::updateVerdict`) renders one primary action whose label is the real next continuation, from Check for updates to Restart now; "Up to date" is claimed only over an actual check result. Apply confirms before acting and names the path: a clean update restarts the server, a conflicting one starts the reviewed assisted task (model spend disclosed) whose progress lands in chat. The served-SHA decision is the only page-reload authority; the boot-owned `pending_boot_smoke` and `applying_replace` phases keep the synthetic `restarting` state until a post-reconnect `update_status_ready` proves boot finalization returned. Recovery holds "Save recovery point" (moves only this installation's local `ouroboros-stable` fallback, never the official QA feed — §8) and one restore list labelled by local tags; unavailable, divergent, dirty, unsafe, failed-check, rollback and restart-required are states, not extra buttons. Passive Git reads take no optional index lock, so they cannot contend with the update writer. The Markdown `letter` reuses the status payload without another poll; `server_process.capture_server_source_baseline` pins the startup source before any mutation, so the letter tells the server baseline from the caller checkout: landing is not adoption, and unknown never becomes disk HEAD (`update_letter.py`). The lock-owning apply executor publishes stage observations through `gateway/update_progress.py` into the status payload (`update_progress`): real stages without percentages or timers, never an authority for mutation or recovery.

#### Available subagents and the review pool

**Available subagents** is the single task-actor editor, its rows the reviewers too: the list-level Delegation switch (`enabled`) and up to `MAX_CONFIGURED_SUBAGENTS` stable rows are the saved `OUROBOROS_SUBAGENTS` intent. Each card is an open editor (`subagents_settings.js`; anatomy: DESIGN §6): its `enabled` switch and Reviewer mark; Source and Model, account pin (empty = rotation), effort (Auto = the chat range; a level in the model name is read-only, follows the model in place and retires a pin), a session's Access (Full system access by default or Working files); Description (`recommended_use`, the one prose field); Processing; Details & history. Drafted until the section's one Save; switched off, still editable. A row is named by its handle (route target plus effective non-default facets, as `codex=gpt-6-astra/xhigh`; `subagent_handle`), never a stored label that rots on re-pointing; `subagent_id` is a hidden join key. Twin engines save only when both rows are marked Reviewer or exactly one carries a `minted_from` origin.

The review pool is the enabled rows marked **Reviewer** (`review_eligible`), in catalog order, read from `GET /api/review-pool` (§4); no second reviewer editor. Delegation governs delegation only (review stays on, said while off); a marked row switched off leaves the pool and says so. A marked API row chooses its delivery (Reads the work itself or Packet) beside the price of one full call, every row's Review cost in Details: the route's known tariff (`review_helpers.review_row_call_usd`, as `## Review` shows), else "cost unknown"; a reading row makes several calls, a session row "uses a session seat and time". A marked Auto row's effort select says it reviews at the top of the chat range; a second marked row on one engine is "another independent run of the same model, not a different reviewer". Emptying the pool saves only once the owner ticks Save without reviewers (`allow_empty_review_pool`, never stored; why: §7); a saved catalog retires a stored `OUROBOROS_REVIEWER_SLOTS`. The standing note states the rule, not status: reviews follow the marked rows and wait for subscription capacity, never API spend.

Saved intent and live evidence are separate axes: a card head shows availability (`rowStatus`), the toolbar the one intent word; a row that will not run prints its reason under its head when it names more than the word (`rowStatusReason`): a phone has no hover. A Claude `[1m]` with a usable listed base reads Available, qualified on the meta line (`sessionModelMatches`). History is not status: Details & history keeps Last review apart from Last task run (`rowTaskRun`, qualified when other settings ran); a completed lanes migration waits behind Reviewer origin, a failed one stays visible. A mark patches its card in place; disclosures, focus and caret survive repaint and reload; lines an edit toggles sit below the rows. A failed status, catalog or accounts read annotates rows, never erases them; requested and observed model/account stay distinct, and historical failure neither disables a row nor ranks alternatives (§6 Route health). A generated default candidate from Settings GET is materialized only on Save, never replacing an owner-edited draft; the save applies from the next task (Settings save effects).

Mutative subagents use Off, Auto and On: explicit values apply to every acting surface, Auto follows runtime mode, and Light allows external work (external workspace, isolated project copy, genesis); why: §6 Safety and runtime mode; matrix: `ouroboros/config.py`. Prompt Cache TTL is one global owner choice (`OUROBOROS_PROMPT_CACHE_TTL`, §7 Default settings) shared by task, review and safety builders, so they cannot drift into conflicting cache horizons.

#### Settings save effects

Settings save sorts keys into three effect classes instead of claiming everything became live (membership: `settings_scales.py` `IMMEDIATE_SETTINGS` / `RESTART_REQUIRED_SETTINGS`, applied by `gateway/settings.py`). Hot-apply: total budget, tool timeout, MCP configuration; a failed hot-reconfigure is a save warning. From the next task: models, credentials, the subagent catalog and its review pool; a running task keeps its start snapshot, and a failed task-start reload is the chat-visible `task_start_settings_reload_failed` event. Restart-required: `restart_state` on GET and Save compares saved intent with the boot-pinned runtime mode, the bound host and port and the worker-pool startup inputs, never the mutable environment; a pending mismatch clears only on a confirmed new process or a saved revert, not on sending `/restart` (bind-host provenance: `server_process.py`). A changed skills path or runtime mode also reloads the extension loader at save time, and each pooled worker adopts the server's published extension generation before a task (`extension_reconcile_queue.py`; events `extension_generation_adopted` / `extension_generation_adoption_failed`), a bounded attempt, not a convergence guarantee. The local-model manager publishes applied values only after its owned process passes health. In Cyber Pro, Ouroboros configures context, review and Supervisor through the same audited writer, including while a task is active, while Access stays pending until restart; a saved choice never rewrites an existing task snapshot or physical request. Every in-process owner-settings writer holds `settings_document_mutation()` across read, merge and write (§7 Reading and writing the settings document). Absence of a successful status read is never evidence that a runtime is healthy.
