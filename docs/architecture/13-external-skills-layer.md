# 13. External Skills Layer

The skill plane outside the runtime package lives here: where native and marketplace payloads live, the independent gates between installation and execution, and how archive installs, declared dependencies, extension staging and the bundled Telegram transport are admitted. Discovery, review, grants, dependency readiness and enablement stay separate facts, because collapsing any two of them turns a UI toggle into execution authority.

### Skill gates

Native and external payloads live in separate data-plane buckets under `data/skills/`, with review, grants, enablement, dependencies, tokens and health under `data/state/skills/<name>/` (§1 Data layout). Discovery confers no trust (§6 Skills and extensions); a conflict declared by either enabled peer is enforced symmetrically without deleting either payload. The executable sequence is install → deterministic preflight → hash-bound multi-model review → grants → dependency readiness → enablement → execution, and the gates stay independent (§10, invariant 8): a review PASS installs no dependencies, `enabled=true` does not prove readiness, and an extension additionally needs host registration. Mutating lifecycle work flows through one deduplicated queue (`skill_lifecycle_queue.py`); review jobs keep their full record privately, and the compact UI history projects a `running` job with a dead process or stale heartbeat as `interrupted` without writing, while the Skills list read heals and syncs nothing. Review ordinals are allocated only after a job starts under the lifecycle lock, so retry history stays explainable without a UI counter becoming review authority.

Execution resolves one selected canonical directory through the full loader on every request. Conflict checks use a fresh immutable peer projection (`skill_peer_inventory.py`); peer payloads are not hashed and no partial executable object is synthesized. The verdict is one duck-typed function (`skill_conflicts.py`), so the full loaded skill and the cheap peer descriptor cannot reach different answers. Selected payload and peer projection are refreshed again after slow lifecycle reconciliation, so a cross-process disable, revoke or same-size restored-mtime edit takes effect on the next request; a valid manifest keeps its declared conflicts even when its payload is unreadable.

### Skill review authority

Skill review combines deterministic preflight with independent multi-model feedback; an optional advisory cannot replace that feedback, and a deterministic preflight failure persists as PENDING, not as advisory-overridable BLOCKERS. Official catalog payloads get their reduced-noise profile only when sidecar, catalog and local file sets and every SHA-256 match a fresh catalog read exactly; the `official_hub_verified` hint in the listing and manifest runs the same match against the display-plane catalog memo (`marketplace/ouroboroshub.py`) and is never authority. Under Advisory an explicit author finish may accept current bytes after prior substantive feedback, or with an exact returned terminal job/hash reference carrying partial feedback or disclosed review unavailability; each finish runs current preflight and records its proof in `author_disposition.review_reference`, and a running critic without feedback is not "unavailable". `SkillReviewState.gate_for` supplies the same current authority to readiness, grants, extension and Host Service consumers; the original critic hash, status and findings never change. Blocking always needs fresh critic approval; Cyber keeps its P0/P3 judgment. Hub publication reuses this authority (§6 Skill publication).

### Telegram seed

`skills/telegram/` bundles an in-process bridge (binding, polling, injection, settings) and a supervised companion (sidecar, tunnel, menu rollback, heartbeat, singleton); text works without the Mini App or tunnel. It is a native hash-bound seed that stays disabled until grants, not a marketplace install; Colab requires fresh native discovery and seed authority, grants only missing grantable items under the owner's auto-grant policy, then enables. State under `data/state/skills/telegram/` separates binding, companion, menu rollback, delivery cursors and tunnel cache. Files ride `/chat/inject` from confined skill state to host `data/uploads`; quiz answers use `/chat/decision` like web cards. Oversized outgoing files stay saved in the app; delivery points to an already-running Mini App or the app itself without starting a tunnel or publishing an artifact URL. The bridge speaks the install's interface language (`OUROBOROS_UI_LANGUAGE`, §7): its own lines are translated tables (`lib/telegram_i18n.py`), a host-composed sentence it only relays stays as the host wrote it, and `/language` hands any new choice to the Host Service `/ui/language`. Skill-local `TELEGRAM_PROXY` covers all Telegram API egress; without it companion calls stay direct, and Host, Mini App and tunnel routes are unaffected. The seed needs `httpx[socks]` in the core lock. Size limits, status words and proxy forms: `skills/telegram/SKILL.md`.

`list_skills` projects lifecycle state through `skill_catalogue.py`: without a name, sorted pages of whole compact records include disabled, unreviewed, broken and colliding skills, with counted preview omissions. Its snapshot detects membership changes, not payload or state edits; pages are not an atomic state view. `list_skills(name=...)` returns full diagnostics and the exact `manifest.read` call for the loader-selected physical `SKILL.md` or `skill.json`; instructions stay at that source. An unreadable extra payload file does not hide a readable manifest, while an unparsed manifest or colliding name has no manifest address. Unknown names return `found: false`, and oversized details use the generic result source. `model_experience` also reaches the bounded installed-skills context; each `SkillManifestError` carries its repair `fix_hint`.

### Marketplace installs and dependencies

Marketplace installs are bounded archives staged privately and landed atomically with per-file hash checks; archive validity, extraction paths, checksum and actual loader support remain separate facts, inert resource bytes need no suffix allowlist, and Cyber policy findings are warnings. Install metadata drives isolated dependencies (`marketplace/install_specs.py`); manual instructions remain guidance, not execution. Fresh review and hash-covered declarations authorize literal build/check argv; verified resources and package caches survive under `state/skills/<name>/dependency_cache`, and `deps.json` records resolved package metadata, bytes, outputs and diagnostics. Delivery is distinct from a declared executable check: an absent check stays unknown, and declared-output drift invalidates installed readiness. Updates keep the selected version through retries and show exact version strings without inferring order. `install.PayloadRollbackSnapshot` restores payload, environment and affected lifecycle state for update and adopt; `rolled_back` requires verified restoration and reload, owner enablement and history survive, and a state-write retry keeps already-restored bytes. `marketplace/provenance.py` clears only the local publication record, never a GitHub PR or installed bytes. Script runtimes: `tools/skill_exec.py`, `docs/CREATING_SKILLS.md`.

### Tool result views

Result composition and the `PRODUCER_RESULT_SOURCE_JSON` / `FULL_RESULT_SOURCE_JSON` distinction: `tools/tool_result.py` and `loop_tool_execution.py`.

### Extension import and isolation

Extensions import through staged trees (`_stage_extension_import_tree` under `__extension_imports/`), so concurrent workers cannot remove a peer's live import and stale trees stay reclaimable. Per-call child processes may proxy tools, routes, WS, UI, settings and companion descriptors, while persistent subscriptions and supervised tasks need in-process or companion lifecycle; the generic capability matrix reports which, never a platform name. Isolated children run the same staged loader in a private base with a scrubbed env, so native crashes cannot kill `server.py`. In-process extensions are the powerful path, so namespacing, declared permissions, per-skill tracking and atomic unload are an executable contract, not convention. Skill repair enqueues an ordinary managed task admitted against one exact payload revision (`skill_repair_admission.py`; §6 Skills and extensions); a `skill_repair` constraint, still produced by the bucket + skill-name short form and canonicalized to `normal` at promotion, selects the payload only and grants no reduced tool profile. An installed payload needs no Git copy, and review never forces unload merely because the caller is repairing it.
