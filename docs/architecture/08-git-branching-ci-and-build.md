# 8. Git Branching, CI, and Build

This chapter owns release topology: the branch and channel model behind the three official update feeds, the CI job graph with its trust boundaries, the keyless system-E2E suite, the build scripts, the dependency-lock authority and the release proof for seven required desktop assets and an optional verified Android pair. It exists because every guarantee here is a rule about what a published artifact may claim, not a build convenience.

`ouroboros` is the local working branch; the runtime setting independently selects one official feed: Stable is the newest plain release tag reachable from both `main` and `ouroboros-stable`, QA is the `ouroboros-stable` tip, Development is the `ouroboros` tip. Promotion and rollback are owner-controlled exact-SHA movements; ordinary restart preserves the local tip, while explicit update owns fetch, target validation, rescue, apply and rollback. `managed` is the official read/update remote; `origin` is optional personal persistence. Desktop and Colab reject a target without a regular non-empty `BIBLE.md`. External pull requests target `ouroboros`, allocate no release version, and receive the collision-free version when maintainers land them (procedure: CONTRIBUTING.md, docs/DEVELOPMENT.md).

Body candidates commit on local `candidate/<task>` branches; a version-neutral candidate commit carries no tag and may be adopted locally as it is, a numbered one is tagged at commit. `refs/ouroboros/candidates/*` and `refs/ouroboros/adoption/*` are private pins. The serving auto-push sends the working branch and only the annotated tags reachable from it (`--follow-tags`): linked worktrees share one tag namespace, so a candidate's tag is published when its commit is the serving line, and a candidate branch only through the explicit Git/PR tools.

The local `ouroboros-stable` ref is also a recovery fallback maintained by explicit promotion; that local role does not select the official QA feed. Launcher metadata is bootstrap provenance only — status, preflight, Colab bootstrap and apply resolve the selected channel and exact fetched SHA themselves, so an older frozen launcher cannot silently redirect updates. Stable additionally requires the shared plain release tag; QA and Development use no version comparison as an admission gate.

Quick and full jobs run blocking `size_ratchet` pytest steps — the only enforcement of repository size gates (local runs exclude the marker and warn): the manifest matching the tip plus the pairwise shrink-only transition against the event base in `OURO_SIZE_RATCHET_BASE_REF`. An unresolvable base degrades to the tip's parent manifest verified against the parent's own tree, never a skip (an unreadable parent fails closed), while a resolvable base without a manifest fails closed, because accepting a copied manifest would allow debt laundering. Both jobs also run the browser-module suite (`cd web && node --test tests/*.test.js`), the node lane the hermetic commit gate executes through `ouroboros/preflight_node.py`. Secret-bearing skill review runs before any step that imports downloaded plugin code — untrusted payload code must never share a process with provider credentials — and a missing required key is red rather than skipped.

Shared UI and keyless wait/repair browser fixtures run the dirty Git candidate in an independent checkout (`tests/candidate_checkout.py`): source and copy identities are verified, and each boot and restart binds the serving PID to unique static sentinel bytes and a VERSION suffix reported by `/api/health`, proving both served assets and imported Python came from this copy (inputs and safe recipe: DEVELOPMENT "Safe local verification and dirty browser candidates"). `ouroboros/test_environment.py` gives pytest, preflight and server children scrubbed temporary roots before imports; dependency sync installs nothing under the test marker. Both `direct_server_with_data` and `KeylessIsolatedServer` with a `CandidateCheckout` use one `ProcessContainer` per incarnation. Teardown reaps and closes it; restart receives a fresh container, and unconfirmed cleanup fails and retains the checkout. Plain-path keyless E2E callers keep their mutable HEAD clones. A POSIX pytest process killed before `finally` cannot perform cleanup.

Tool-schema compatibility has two layers. Fork-safe PR tests build the complete shipped catalog without MCP or extensions, validate every schema as general JSON Schema plus the cross-provider subset (no empty enum, no root `anyOf`/`oneOf`/`allOf`), and require the OpenRouter/function, direct-Anthropic, GigaChat and direct-OpenAI projections to preserve the complete tool-name set. Trusted `integration-test` sends that full registry, fitted to the route's schema ceiling as Main does (direct OpenAI: 128), in one bounded, unexecuted `delegate_start` canary per route: the OpenRouter families, the three shipped direct-OpenAI defaults, direct Anthropic, and optional MiniMax/DeepSeek/Cloud.ru/GigaChat; Direct-OpenAI Main and DeepSeek also test continuation (DeepSeek requires `reasoning_content` replay). Each canary requires positive usage, exact provider/model identity and a normalized schema-valid call carrying exactly the requested arguments; quota/billing, 429, 5xx and timeout outcomes stay typed inconclusive while contract/auth/model/tool/reasoning 4xx are red, and one same-route resend is allowed only for a semantic-empty response that the runtime classifier, reading the host usage fact `response_finish_reason`, would retry (never output exhaustion).

Informational test reports, safe artifacts, step ceilings and partial UI checks: DEVELOPMENT "Reading CI failure evidence".

A push to a pull request cancels the `CI` run of that request's previous head. Every other event, and every re-run, has its own concurrency group: release, scheduled and landed-commit runs are never cancelled, and a re-run of an old head cannot displace a pending run.

`claudexor-platform-gate.yml` also runs credential-free `scripts/claudexor_lifecycle_smoke.py` on ubuntu/macOS/Windows for its fixture triggers. The witness fetches the checksum-verified pin into a disposable HOME/data root, uses production exact-start, cancel, wait and custody, then proves cancel → continuation, owned-daemon kill → host respawn → interrupted settlement → continuation, normal owner completion → swept retirement → typed predecessor refusal, and retention for an open owner Continue offer. It checks engine heap argv against the plain probe when available, old-engine unknown memory otherwise, and reaps its exact owned children in `finally`. Its sole transport substitution projects addressed fake manifests into the capability catalog, which the engine intentionally omits there; continuation keys are fixture intent proven by admission. It proves neither vendor sessions nor child-process containment.

`claudexor-platform-gate.yml` proves the managed Claudexor runtime on three OSes: fixture (fake harness, offline, $0) and toolchain (`scripts/claudexor_toolchain_smoke.py`: production `ensure_cli_command()` installs the pinned official Node/npm with no ambient Node/npm or harness override; no harness install is claimed) lanes always, a Windows consumer lane (same script, `--harness-install codex`: the production `install_missing_harness_cli` really installs the engine-pinned Codex, whose native image must resolve directly, by bare name and in doctor; no login or task; red until the pin carries Windows native install), and a live lane only on explicit API keys — subscription auth stays deliberately out of CI, because an interactive machine-bound token must not enter CI secrets. `dependency-graph.yml` reads `ouroboros/claudexor_runtime_pin.json` and submits that direct runtime relationship to GitHub's dependency graph (runs only on pin/workflow changes on `main`/`ouroboros`, plus manual dispatch; `contents: write` only) without presenting Claudexor as a Python or Node package dependency. The Scorecard workflow (`.github/workflows/scorecard.yml`) runs on `main` pushes and weekly, pins every action by full commit SHA, defaults permissions to read-only, and adds only `security-events: write` + `id-token: write` for SARIF upload and OpenSSF publication. `CODE_OF_CONDUCT.md` owns community rules; `CITATION.cff` owns the software and preferred technical-report citations; `site/paper/index.html` owns the canonical paper landing page; `docs/benchmarks/evidence.json` holds the release-bound public benchmark projection; README remains the claim SSOT (guarded by `tests/test_trust_metadata.py` and `tests/test_public_site_metadata.py`).

Dev-facing release/review scripts: `scripts/safe_test.py` (stdlib verification boundary), `scripts/browser_ci_scope.py` (documentation-only browser selection), `scripts/run_tests.py` (test battery; DEVELOPMENT Build & CI), `scripts/run_external_review.py` (two lanes over the runtime's own review flow, on an isolated whole data root under an explicit `--run-cap-usd`, attach-only to the host engine: by default the commit gate's non-committing cycle over the staged index, run in the runtime's isolated checkout of the staged patch (`review_subject.isolated_checkout`; `--no-isolated-checkout` reviews the worktree in place); with `--contributor` a committed `base..head` proposal — its own hermetic tests first in an isolated checkout of the same frozen subject, then the `review_change` operation under the installed body's review flow and rules; `READY_FOR_INTEGRATION` is evidence, never merge authority), `scripts/contributor_review_evidence.py` (contributor-packet binding), `scripts/run_plan_review.py` (the `plan_task` engine; review-exempt), `scripts/validate_scope_receipt.py`, `scripts/claudexor_platform_smoke.py`, `scripts/claudexor_toolchain_smoke.py`, `scripts/fetch_claudexor_runtime.py` (pin SSOT: `claudexor_runtime_pin.json`), `scripts/cleanup_test_pollution.py` (dry-run-first). `site/` is the Vite source of the public pages (`site/scripts/sync-assets.mjs`); `skills/telegram/` and `skills/unix_computer_use/` are the bundled skills; `packaging/cli/` holds the CLI wrappers and installers; `packaging/appimage/` the AppRun dispatch + desktop metadata; `packaging/systemd/` the opt-in user unit (no-restart rationale: §1 Runtime topology).

### System E2E suite (`tests/system_e2e/`)

The deep-integration suite drives a REAL `server.py` per scenario — an isolated repo clone, data root and free loopback port through `KeylessIsolatedServer`, whose child environment can never carry a provider credential — and asserts DURABLE artifacts through `ArtifactOracle` readers (`task_results/`, `logs/*.jsonl`, `state/*`), never an HTTP 200 or a harness exit code. Synchronization is durable-event polling (`wait_until`), never bare sleeps; a scenario that must act MID-ROUND holds the loopback model on an event-gated `ModelGate` instead of racing a latency sleep. Two loopback models share one HTTP base (JSON for non-streaming, complete SSE framing for streaming): `ScriptedStubModel`, an ordered per-scenario tool script whose review-organ calls are classified by prompt markers and answered with canned parse-clean verdicts, and `ReplayModel`, deterministic fixtures bound by `(lineage, slot, attempt)` where a miss or an unconsumed row is red. A `ReviewScript` overrides the canned verdicts for exactly the scripted red rounds, and review calls never consume agent script steps. The prompt markers are VERBATIM literals grepped back out of their source files by a default-lane pin, so drift is a named failure rather than a silently mute stub. Reviewer routing is pinned through an `OUROBOROS_SUBAGENTS` catalog whose Reviewer-marked rows are the whole pool (`keyless_review_catalog`), because a never-configured catalog reads the factory reviewers — live routes that block keyless at pack assembly. `FakeClaudexorDaemon` imitates the exact `gateways/claudexor.py` client contract — authenticated handshake reporting the TREE'S OWN runtime-pin identity, capability/quota answers, idempotency-keyed project registration and run creation with the engine's replay semantics, run detail and cancel — and records every wire request for scenario assertions.

The scenario inventory is DATA (`SCENARIOS` in `harness.py`) with a two-direction pin over every `test_*.py` module of the package: a manifest row without a test is red, and a scenario test without a manifest row is red. It covers boot and identity, the review organs (the commit wave — both questions — in both enforcement classes, plan review, the acceptance loop), egress hardening, typed tool safety, honest cost names, subagent trees, cancellation with its cascade and the owner stop of a direct-chat turn, managed update (fast-forward, carrier transfer, conflicting refusal, crash mid-apply, rollback), delegated transport including the mutating pull-in and its refusal, and the whole skills lifecycle. Scenario tests carry BOTH the `integration` and `serial` markers plus the `OUROBOROS_E2E_DEEP=mock` env gate, so neither the default local run nor either CI pytest pass executes them; the keyless lane is `OUROBOROS_E2E_DEEP=mock pytest tests/system_e2e/ -o addopts=""`, and in CI it is the secret-free `system-e2e-mock` job — manual dispatch and `v*` tags, where `release-preflight` needs it. The paid owner-shaped stand that runs real servers against a real provider is operator tooling: `devtools/e2e_live/README.md`.

### Build scripts

`build.sh` (macOS → .dmg), `build_linux.sh` (→ .AppImage + .tar.gz), `scripts/build_appimage.sh`, `scripts/build_linux_packages.sh` (.deb/.rpm/.red80.rpm), `scripts/smoke_linux_packages.sh`, `build_windows.ps1` (→ .zip), `scripts/pack_windows_archive.ps1` (hidden-file-preserving ZIP), `scripts/sign_windows_release.ps1` (eSigner invocation), `scripts/verify_windows_signature.ps1` (signer/timestamp verification), and `scripts/build_repo_bundle.py` (writes `repo.bundle` + `repo_bundle_manifest.json`, the manifest `launcher.py` bootstrap validates) are the release-invariant owners. Linux PyInstaller runs under the same pinned portable Python shipped in the payload, so its bundled libpython keeps the payload's glibc floor instead of inheriting the release runner's newer ABI. The AppImage builder wraps that payload with digest-pinned tool and runtime bytes; the native Linux builder wraps the same x86_64 payload without replacing its runtime. Native packages declare the external Git bootstrap requires, keep bundled Python/Node/browser under `/opt/ouroboros`, and install the opt-in user unit at `/usr/lib/systemd/user/ouroboros.service` with no activation scriptlet. The release-gating package smoke installs through `apt`/`dnf` and proves Git resolution, desktop files, the user unit's launcher/cgroup/no-restart contract, the packaged CLI and a bounded desktop-launcher start on Ubuntu 22.04/Fedora 42; Astra Linux and RED OS vendor-image runs stay informational, because third-party registry availability cannot block publication. Release tag prerequisite: `scripts/build_repo_bundle.py` is the release-tag SSOT and verifies the annotated `v$(cat VERSION)` tag points at `HEAD` before packaging.

Betterleaks follows the same release-resource discipline: packaged builds stage the pinned binary and license under `betterleaks-standalone`, source checkouts install the exact managed runtime explicitly under `data/state/betterleaks/`, and the Publish path never downloads it (§13).

Python dependency resolution has one authority: direct requirements and group membership live in `pyproject.toml`, `uv.lock` records the universal solution under the pinned `tool.uv.required-version`, and source/CI sync with `--locked` so metadata drift is an error. The two-interpreter packaging boundary rides projections: build scripts export their PyInstaller input directly from `uv.lock`, the committed `requirements-runtime.lock` supplies embedded `python-standalone` and managed updates (pip, no bundled uv), and a one-line `requirements.txt` pointer serves already-released updaters; CI regenerates the export and requires a clean diff, so neither file becomes a second dependency authority.

Platform builds precompile bundled Python with unchecked-hash bytecode: sealing valid bytecode prevents runtime `__pycache__` writes from invalidating a macOS signature, and runtime children route caches outside the bundle. When signing is enabled, hardened runtime, notarization, xattr hygiene, and strict verification remain part of the stable-release path; prerelease artifacts may be unsigned and their evidence must report the actual signing state.

The release proof begins with the final DMG/AppImage/tarball/ZIP, never its staging directory — validating a staging tree does not establish that the published bytes contain or execute the same payload. Each platform shard checks the embedded repository bundle, packaged CLI and managed Claudexor seed + Node by starting the owned daemon, completing a fixture task and verifying an identity-bound stop. The AppImage is extracted for metadata/SBOM inspection, then run FUSE-independently to prove version output, CLI dispatch, browser-fallback readiness, payload lifetime and clean shutdown (browser-fallback evidence, not a claim of a native GTK/Qt backend). The proven Linux tarball payload is wrapped into the three native packages, each with its own digest-bound package-manager smoke receipt and provenance attestation; a digest-pinned Syft build produces CycloneDX inventories from extracted payload bytes. The release job requires seven desktop assets and accepts the optional Android pair only after verification, recalculates digests, verifies both predicate types, writes the checksum/evidence capsule, and rechecks the remote annotated tag immediately before publication. Signing credentials stay step-scoped and absent from SBOM/attestation steps. Windows signing is selected by the `ESIGNER_CERT_SHA1` repository variable. Unset, no job sees a signing secret and the build shard's ZIP is proven and published as explicitly unsigned; set, a fresh runner bound to the `windows-release-signing` Environment signs `Ouroboros.exe` with a digest-pinned SSL.com CodeSignTool, verifies signer and timestamp and repacks the ZIP, and any failure blocks the seven-asset release. Each handover is checked against its producer's job-output digest before extraction; a secret-free proof runner smokes the final ZIP and records its signing state, which the release assembly matches against the variable. Neither intermediate reaches the release download; setup lives in DEVELOPMENT § Build & CI. Configured signing deliberately accepts only tag-push events and their reruns, not a new manual dispatch against a tag; that dispatch can build diagnostics but fails signing and cannot publish. This narrows the unsigned manual-tag path to avoid an additional certificate-use trigger.

Public installer naming and links ride the same projection: `release_sync.py::RELEASE_ASSET_TEMPLATES` is the filename SSOT shared by the proof builder, README, and the install pages. A version bump rewrites only named download references and `data-release-download` anchors to immutable `/releases/download/v{VERSION}/...` URLs; the `/releases/latest/download/...` shape is forbidden because GitHub excludes prereleases from `latest`. Generated release notes link only proof-accepted assets: seven required desktop installers plus an optional Android pair and its USB setup guide; the APK alone is not the runtime. The default README and GitHub Pages deployment use the stable `main` boundary (`main:/docs` for Pages); stable promotion advances `main` only after the release is published with all seven required proof-bound desktop installers, so an unreleased development VERSION never exposes dead installer links and an omitted promotion leaves the previous working release public.

`scripts/build_android_release.py` binds a source archive/common Git seed and publisher-signed reference APK to the tag SHA, package/version/certificate and smoke/SBOM/attestation proof. SBOMs describe shipped source/APK bytes; the phone provisioner owns dependency pins and installed-package records. Experimental Android is nonblocking: `release_proof.py` preserves the observed build outcome; failed/cancelled/skipped builds, partial pairs or failed digest/smoke/SBOM/attestation exclude BOTH Android artifacts. Required desktop failures remain fatal. Upload and exact uploaded-set checks use proof-accepted records, never directory globs. Notes disclose unavailability with its CI run rather than dead links. Compilation does not certify physical root, boot, hardware or runtime behavior; [CI follow-up](https://github.com/razzant/ouroboros/issues/1036) tracks future mandatory gates.

### Docker

Docker runs the web and server runtime without PyWebView. The image binds `0.0.0.0` and sets no network password by default: a missing password only warns, and `NetworkAuthGate` permits requests when no password is configured — publishing the container port without setting `OUROBOROS_NETWORK_PASSWORD` therefore exposes the owner surface. Set the password (or keep the port unpublished); packaging adds no stronger boundary of its own.

The root `.dockerignore` filters `COPY . .`: secrets, host virtualenvs, `node_modules`, caches and runtime/review/operator state stay out of image layers; `.git`, `tests/` and sources stay in, because CI runs pytest inside the image.

The image is one self-contained `Dockerfile` built with Docker's default BuildKit builder: `python:3.10-slim` with the pinned `uv`, then git plus Playwright's native libraries and the Chromium/WebKit binaries for the Playwright version `uv.lock` pins, installed from an ephemeral `uvx` tool environment into `/ms-playwright` (the `PLAYWRIGHT_BROWSERS_PATH` the runtime honors as-is), then `uv sync --locked` into `/app/.venv`, then the sources. Browsers and apt packages sit above the lock copy because every release rewrites `pyproject.toml`/`uv.lock`, and `RUN --mount=type=cache` keeps the uv and apt caches out of the layers. `tests/test_build_scripts.py::TestDockerfile` pins the version match, the order, the shared browser path and the absence of a runtime `UV_PROJECT_ENVIRONMENT` (a baked one would let an agent's `uv sync` in a task workspace rewrite the runtime venv); the tag-only `docker-ui-smoke` and `docker-portable-test` lanes exercise the shipped browsers without a download. Trust anchors are not baked into the image: a deployment that needs an extra CA sets `OUROBOROS_EXTRA_CA_BUNDLE` (§7; `docs/DEPLOYMENT.md`).
