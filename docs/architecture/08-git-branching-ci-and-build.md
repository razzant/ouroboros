# 8. Git Branching, CI, and Build

Release topology: the branch and channel model behind three official update feeds, the dependency-lock authority and the release proof for seven required desktop assets and an optional verified Android pair. Every guarantee here is a rule about what a published artifact may claim, not a build convenience.

`ouroboros` is the local working branch; the runtime setting selects one official feed independently of it: Stable is the newest plain release tag reachable from both `main` and `ouroboros-stable`, QA the `ouroboros-stable` tip, Development the `ouroboros` tip (`update_channels.py`). Promotion and rollback are owner-controlled exact-SHA movements; ordinary restart preserves the local tip, while explicit update owns fetch, target validation, rescue, apply and rollback. `managed` is the official read/update remote, `origin` optional personal persistence. Desktop and Colab reject a target without a regular non-empty `BIBLE.md`. External pull requests target `ouroboros`, allocate no release version and get the collision-free version when maintainers land them (CONTRIBUTING.md).

Body candidates commit on local `candidate/<task>` branches; `refs/ouroboros/candidates/*` and `refs/ouroboros/adoption/*` are private pins (§6 Own-body candidates). The serving auto-push sends the working branch and only the annotated tags reachable from it (`--follow-tags`), never `--tags`: linked worktrees share one tag namespace, so a candidate's tag is published only once its commit is on the serving line, and a candidate branch only through the explicit Git/PR tools.

The local `ouroboros-stable` ref is also a recovery fallback maintained by explicit promotion; that local role does not select the QA feed. Launcher metadata is bootstrap provenance only: status, preflight, Colab bootstrap and apply resolve the selected channel and exact fetched SHA themselves, so an older frozen launcher cannot redirect updates. Stable additionally requires the shared plain release tag; QA and Development use no version comparison as an admission gate.

### CI topology

Ordinary cloud CI runs only on dispatch or `v*` tags, not branch pushes or PRs: later cross-platform feedback buys runner capacity, not weaker local tests or review. `ci.yml` retains the full release graph; UI/provider wrappers are manual-only with unchanged filenames. Claudexor integration and non-test publishing keep their triggers; Hub-repository validation is separate.

Quick and full-test runners enforce `size_ratchet` (local runs warn): tip manifest exactness and shrink-only transition against `OURO_SIZE_RATCHET_BASE_REF`. An unresolvable base uses the tree-verified parent; a resolvable base without a manifest fails closed, since copying one would launder debt. Each composed book is also compared with the event base; only that check skips if no base resolves. `scripts/book_growth_mode.py` derives `OURO_BOOK_GROWTH_MODE` (`block|warn|approved`) from PR metadata with `pull-requests: read` (DEVELOPMENT "Documentation contract"). Both tiers run the complete Node lane (`preflight_node.py`). Skill review precedes downloaded plugin imports: untrusted payload code must never share provider credentials; a missing required key is red.

Shared UI and keyless wait/repair browser fixtures run the dirty Git candidate in an independent checkout (`tests/candidate_checkout.py`); `/api/health` and static sentinels prove that copy supplies served assets and imported Python (recipe: DEVELOPMENT "Safe local verification and dirty browser candidates"). `ouroboros/test_environment.py` gives pytest, preflight and server children scrubbed temporary roots before imports.

Tool-schema compatibility has two layers. Local and manual/tag tests build the complete shipped catalog without MCP or extensions, validate every schema as JSON Schema plus the cross-provider subset, and require every provider projection to preserve the complete tool-name set. Trusted `integration-test` sends that full registry, fitted to the route's schema ceiling as Main does, in one bounded, unexecuted `delegate_start` canary per route and requires positive usage, exact provider/model identity and a schema-valid call carrying exactly the requested arguments; quota, 429, 5xx and timeout outcomes stay typed inconclusive, while contract, auth, model, tool and reasoning 4xx are red (DEVELOPMENT "Provider Independence").

Informational test reports, safe artifacts, step ceilings and partial UI checks: DEVELOPMENT "Reading CI failure evidence".

Each manual/tag `CI` run and re-run has its own concurrency group: one qualification cannot cancel or replace another. Dormant branch/PR predicates grant no trigger; re-enabling automatic CI is a separate policy change.

`claudexor-platform-gate.yml` retains path-filtered branch/PR triggers, tags and dispatch. It proves the managed Claudexor runtime on three OSes: a fixture lane (fake harness, offline, $0) and a toolchain lane (`scripts/claudexor_toolchain_smoke.py`: production `ensure_cli_command()` installs the pinned Node/npm with no ambient toolchain) always, a Windows consumer lane where `install_missing_harness_cli` really installs the engine-pinned Codex (resolves directly, by bare name and in doctor; no login or task), and a live lane only on explicit API keys. Subscription auth stays out of CI: an interactive machine-bound token never enters CI secrets. Fixture triggers also run the credential-free `scripts/claudexor_lifecycle_smoke.py` on all three OSes: a real pinned engine under production custody proves cancel, daemon-kill respawn, completion and retirement each settle and continue, but neither vendor sessions nor child-process containment. `dependency-graph.yml` submits the `ouroboros/claudexor_runtime_pin.json` runtime relationship to GitHub's dependency graph (`contents: write` only) without presenting Claudexor as a Python or Node package. `.github/workflows/scorecard.yml` runs on `main` pushes and weekly, pins every action by commit SHA, defaults permissions to read-only and adds only `security-events: write` + `id-token: write`. `CODE_OF_CONDUCT.md` owns community rules, `CITATION.cff` the software and technical-report citations, `site/paper/index.html` the paper landing page, `docs/benchmarks/evidence.json` the release-bound public benchmark projection; README stays the claim SSOT.

`scripts/` is operator and release tooling, each script documented by its own docstring: `safe_test.py` (stdlib verification boundary), `book_growth_mode.py` (official contribution growth mode), `browser_ci_scope.py` (documentation-only browser selection), `run_tests.py` (test battery), `run_external_review.py` (the runtime's own review flow over the staged index or, with `--contributor`, over a committed `base..head` proposal under the installed body's review flow and rules; `READY_FOR_INTEGRATION` is evidence, never merge authority), `contributor_review_evidence.py`, `run_plan_review.py` (the `plan_task` engine; review-exempt), `validate_scope_receipt.py`, `claudexor_platform_smoke.py`, `claudexor_toolchain_smoke.py`, `fetch_claudexor_runtime.py` (pin SSOT: `claudexor_runtime_pin.json`), `cleanup_test_pollution.py` (dry-run first). `site/` is the Vite source of the public pages (`site/scripts/sync-assets.mjs`); `skills/telegram/`, `skills/unix_computer_use/`, `skills/meeting_audio/`, `skills/meeting_browser/` and `skills/zoom_meeting/` are the bundled skills; `packaging/cli/`, `packaging/appimage/` and `packaging/systemd/` hold the CLI wrappers and installers, the AppRun dispatch and the opt-in user unit (§1 Runtime topology).

### System E2E suite (`tests/system_e2e/`)

Each deep-integration scenario drives a real isolated `server.py` (`KeylessIsolatedServer`, whose child environment can never carry a provider credential) and asserts durable artifacts through `ArtifactOracle` readers (task store, `logs/*.jsonl`, `state/*`), never an HTTP 200 or harness exit code. Synchronization is durable-event polling, never bare sleeps; a scenario that must act mid-round holds the loopback model on an event-gated `ModelGate`. Two loopback models share one HTTP base: `ScriptedStubModel`, an ordered per-scenario tool script whose review-organ calls are classified by prompt markers, and `ReplayModel`, deterministic keyed fixtures where a miss or an unconsumed row is red. A default-lane pin greps the prompt markers back out of their source files verbatim, so drift is a named failure, not a silently mute stub. Reviewer routing is pinned through an `OUROBOROS_SUBAGENTS` catalog (`keyless_review_catalog`), because a never-configured catalog reads the factory reviewers, live routes that block keyless runs. `FakeClaudexorDaemon` imitates the exact `gateways/claudexor.py` client contract and records every wire request.

The scenario inventory (`SCENARIOS` in `harness.py`) is data pinned to the package's `test_*.py` modules: a row without a test or a scenario test without a row is red. Scenario tests carry the `integration` and `serial` markers plus their row's `OUROBOROS_E2E_DEEP` lane gate, so neither the default local run nor either CI pytest pass executes them: keyless `mock` is `OUROBOROS_E2E_DEEP=mock pytest tests/system_e2e/ -o addopts=""`, in CI `system-e2e-mock`; S39's operator-run `container` lane needs one named Docker daemon (`test_managed_container.py` docstring). The paid owner-shaped stand against a real provider is operator tooling: `devtools/e2e_live/README.md`.

### Build scripts

`build.sh` (macOS → .dmg), `build_linux.sh` (→ .AppImage + .tar.gz), `scripts/build_appimage.sh`, `scripts/build_linux_packages.sh` (.deb/.rpm/.red80.rpm), `scripts/smoke_linux_packages.sh`, `build_windows.ps1` (→ .zip), `scripts/pack_windows_archive.ps1` (hidden-file-preserving ZIP), `scripts/sign_windows_release.ps1` (eSigner invocation), `scripts/verify_windows_signature.ps1` (signer/timestamp verification) and `scripts/build_repo_bundle.py` (writes `repo.bundle` + `repo_bundle_manifest.json`, the manifest `launcher.py` bootstrap validates) are the release-invariant owners. Linux PyInstaller uses the payload's pinned portable Python, keeping bundled libpython at the payload's glibc floor, not the release runner's newer ABI. AppImage wraps that payload with digest-pinned tool and runtime bytes; native Linux packages wrap the same x86_64 payload, keep bundled Python/Node/browser under `/opt/ouroboros` and install the opt-in user unit without activation scriptlets. The release-gating package smoke installs through `apt`/`dnf` on Ubuntu 22.04/Fedora 42; Astra Linux and RED OS vendor-image runs stay informational: third-party registry availability cannot block publication. `scripts/build_repo_bundle.py` is also the release-tag SSOT: before packaging it verifies the annotated `v$(cat VERSION)` tag points at `HEAD`.

Betterleaks follows the same release-resource discipline: packaged builds stage the pinned binary and license under `betterleaks-standalone`, source checkouts install the managed runtime explicitly, and the Publish path never downloads it (§6 Skill publication).

`pyproject.toml` owns Python requirements/groups; `uv.lock` resolves them under `tool.uv.required-version`. Source/CI use `--locked`. Builds export PyInstaller inputs; `requirements-runtime.lock` supplies embedded Python and managed updates (pip, no bundled uv); `requirements.txt` points older updaters there. CI regenerates the export and rejects drift. Desktop builds also install the locked desktop extra into embedded Python before sealing: source handoff cannot import the private PYZ. Final DMG/tar/ZIP smoke checks that interpreter's desktop imports with `-I -B`, without user-site or GUI startup. Linux still needs a GUI backend or browser fallback.

Platform builds precompile bundled Python with unchecked-hash bytecode: sealing valid bytecode prevents runtime `__pycache__` writes from invalidating a macOS signature, and runtime children route caches outside the bundle. When signing is enabled, hardened runtime, notarization, xattr hygiene and strict verification are part of the stable-release path; prerelease artifacts may be unsigned and their evidence must report the actual signing state.

Release proof uses the final DMG/AppImage/tarball/ZIP, never its staging directory: validating staging cannot prove published bytes contain or execute that payload (`scripts/release_proof.py`). Each platform shard checks the embedded repository bundle, packaged CLI and managed Claudexor seed + Node by starting the owned daemon, completing a fixture task and verifying an identity-bound stop; the three native packages wrap the proven Linux tarball payload, each with its own digest-bound package-manager smoke receipt and provenance attestation. The release job requires seven desktop assets, accepts the optional Android pair only after verification, recalculates digests, writes the checksum/evidence capsule and rechecks the remote annotated tag immediately before publication. Signing credentials stay step-scoped and absent from SBOM/attestation steps.

Windows signing is selected by the `ESIGNER_CERT_SHA1` repository variable. Unset, no job sees a signing secret and the Windows ZIP is proven and published as explicitly unsigned. Set, a fresh runner bound to the `windows-release-signing` Environment signs `Ouroboros.exe`, verifies signer and timestamp and repacks the ZIP, and any failure blocks the release; the secret-free proof runner smokes the final ZIP and records its signing state, which the release assembly matches against the variable. Configured signing accepts only tag-push events and their reruns, not a manual dispatch against a tag, to avoid an additional certificate-use trigger. Setup: DEVELOPMENT "Build & CI".

Public installer names and links share one projection: `ouroboros/tools/release_sync.py::RELEASE_ASSET_TEMPLATES`, the filename SSOT for the proof builder, README and install pages. A version bump rewrites only named download references and `data-release-download` anchors to immutable `/releases/download/v{VERSION}/...` URLs; the `/releases/latest/download/...` shape is forbidden because GitHub excludes prereleases from `latest`. Generated release notes link only proof-accepted assets: seven required desktop installers plus an optional Android pair and its USB setup guide; the APK alone is not the runtime. The default README and GitHub Pages deployment use the stable `main` boundary (`main:/docs` for Pages); stable promotion advances `main` only after the release is published with all seven proof-bound desktop installers, so an unreleased development VERSION never exposes dead installer links and an omitted promotion leaves the previous working release public.

`scripts/build_android_release.py` binds a source archive, a common Git seed and a publisher-signed reference APK to the tag SHA, package/version/certificate and smoke/SBOM/attestation proof. Android is nonblocking: a failed, cancelled or skipped build, a partial pair or a failed digest/smoke/SBOM/attestation check excludes both Android artifacts, while required desktop failures stay fatal. Compilation certifies no physical root, boot, hardware or runtime behavior.

### Docker

Docker runs the web and server runtime without PyWebView, bound to `0.0.0.0` (exposure, passwords and both modes: DEPLOYMENT); `--target managed` hosts the common launcher over a released seed, body and `--runtime-venv` on volumes (§2 Packaged seed).

The root `.dockerignore` keeps secrets, host environments, caches and runtime/review/operator state out of `COPY . .` layers; `.git`, `tests/` and sources stay: CI runs pytest inside the image.

The image is one self-contained `Dockerfile`: `python:3.10-slim` with the pinned `uv`, git, Playwright's native libraries and the Chromium/WebKit of the `uv.lock` Playwright in `/ms-playwright` (the `PLAYWRIGHT_BROWSERS_PATH` the runtime honors as-is), then `uv sync --locked` into `/app/.venv`, then the sources; browsers and apt packages sit above the lock copy that every release rewrites. No runtime `UV_PROJECT_ENVIRONMENT` is baked, or an agent's `uv sync` in a task workspace would rewrite the runtime venv; the tag-only `docker-ui-smoke` and `docker-portable-test` lanes exercise the shipped browsers without a download. No trust anchor is baked in (`OUROBOROS_EXTRA_CA_BUNDLE`: DEPLOYMENT).
