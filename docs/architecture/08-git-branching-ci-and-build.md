# 8. Git Branching, CI, and Build

This chapter owns release topology: the branch and channel model behind the three official update feeds, the CI job graph with its trust boundaries, the keyless system-E2E suite, the build scripts, the dependency-lock authority and the release proof for seven required desktop assets and an optional verified Android pair. Every guarantee here is a rule about what a published artifact may claim, not a build convenience.

`ouroboros` is the local working branch; the runtime setting selects one official feed independently of it: Stable is the newest plain release tag reachable from both `main` and `ouroboros-stable`, QA the `ouroboros-stable` tip, Development the `ouroboros` tip (`update_channels.py`). Promotion and rollback are owner-controlled exact-SHA movements; ordinary restart preserves the local tip, while explicit update owns fetch, target validation, rescue, apply and rollback. `managed` is the official read/update remote, `origin` optional personal persistence. Desktop and Colab reject a target without a regular non-empty `BIBLE.md`. External pull requests target `ouroboros`, allocate no release version and get the collision-free version when maintainers land them (CONTRIBUTING.md).

Body candidates commit on local `candidate/<task>` branches; `refs/ouroboros/candidates/*` and `refs/ouroboros/adoption/*` are private pins (§6 Own-body candidates). The serving auto-push sends the working branch and only the annotated tags reachable from it (`--follow-tags`), never `--tags`: linked worktrees share one tag namespace, so a candidate's tag is published only once its commit is on the serving line, and a candidate branch only through the explicit Git/PR tools.

The local `ouroboros-stable` ref is also a recovery fallback maintained by explicit promotion; that local role does not select the QA feed. Launcher metadata is bootstrap provenance only: status, preflight, Colab bootstrap and apply resolve the selected channel and exact fetched SHA themselves, so an older frozen launcher cannot redirect updates. Stable additionally requires the shared plain release tag; QA and Development use no version comparison as an admission gate.

### CI topology

`.github/workflows/ci.yml` has 21 jobs, grouped by trigger and secret exposure:

| Tier | Jobs | Trust boundary |
|---|---|---|
| Fork-safe PR validation | `quick-test`, `betterleaks-platform-smoke`, `benchmark-methodology` (also `ouroboros-stable` pushes and `v*` tags) | `ouroboros` pushes, pull requests into `ouroboros`, manual runs; read-only, no provider secrets, never `pull_request_target` |
| Android source/build proof | `android-test` | Every run; `android/tests`, release tests and disposable-key APK compilation; no publisher secrets |
| Android emulator proof | `android-emulator-smoke` | Tags or verified `android/` changes; install/start and same-UID PackageInstaller readback on an x86_64 API matrix; no publisher secrets |
| Browser consumer proof | `ui-browser.yml`, called by `ci.yml` and `ui-browser-push.yml` | One reusable complete lane: PRs, manual runs and `v*` tags via `ci.yml`; every `ouroboros` push via `ui-browser-push.yml`, which alone owns the partial diagnostic scenario. No path filter, because Makefile-, spec- and requirements-only merges are read by tests. Four `ui-shard` jobs, one `ui-manifest` collection and the `ui-smoke` verdict, which reconciles the shards against the manifest and refuses a red session. No schedule, no provider secrets |
| Opt-in lanes, no schedule | `system-e2e-mock` (keyless; manual runs and `v*` tags, on the release bar), `e2e-live` (`OUROBOROS_E2E_LIVE_OPENROUTER_KEY`, `$30` cap) | `e2e-live` starts only from a dispatch that opts in through the `e2e_live` input; without the secret it is one summary line and green, never a pretend run. Both upload their servers' journals, never a settings file |
| Ordinary desktop tests | `full-test` (no secrets) | Every PR into `ouroboros` and every `ouroboros` push in this repository run Windows/macOS beside the Ubuntu quick-test, so the landed commit shows which merge broke a desktop system; stable pushes, manual runs and `v*` tags keep the full three-OS matrix. The Windows leg also runs the Chromium attachment-route cases and fails when none ran |
| Trusted skill matrix | `skill-smoke` (`OPENROUTER_API_KEY`) | `ouroboros-stable` pushes, manual runs, `v*` tags; never pull requests |
| Trusted provider run | `integration-test`, body in `provider-canary.yml` | Provider secrets; manual runs and `v*` tags via `ci.yml` (the release chain needs it), `main`/`ouroboros`/`ouroboros-stable` pushes via `provider-canary-push.yml` under its own result, so a provider outage does not redden `ci.yml`; never pull requests |
| Tag-only gates and release chain | `marker-guards`, `docker-ui-smoke`, `docker-portable-test` (manual runs or tags, no secrets); `release-preflight` waits for `full-test` + `integration-test` + `system-e2e-mock` and fails closed when any required result is not `success`; a valid tag may still run the desktop `build` diagnostically, while `release` requires a successful preflight, the desktop build, `skill-smoke`, `ui-smoke` and the three smoke gates. `android-build` needs the Android proofs, so a failed Android proof excludes both optional Android assets. `windows-sign` holds the signing Environment only when signing is configured; the secret-free `windows-proof` checks and attests the final Windows ZIP either way, and `release` also requires it. `vendor-package-smoke` stays informational | Tag-triggered; a reproducible provider-contract failure blocks publication without hiding desktop build diagnostics, and a typed inconclusive provider outage blocks only a release tag, where every required canary must pass |

Quick and full jobs run blocking `size_ratchet` pytest steps, the only enforcement of module size gates (local runs warn): the manifest matching the tip plus the shrink-only transition against the base in `OURO_SIZE_RATCHET_BASE_REF`; an unresolvable base never skips, and a resolvable base without a manifest fails closed, because a copied manifest would launder debt. The same lane compares each composed book against the event base; only that comparison skips when no base resolves. `scripts/book_growth_mode.py` sets `OURO_BOOK_GROWTH_MODE` (`block|warn|approved`) from PR metadata under the jobs’ `pull-requests: read` permission (policy: DEVELOPMENT "Documentation contract"). Both jobs also run the browser-module suite (`cd web && node --test tests/*.test.js`), the node lane the hermetic commit gate runs through `ouroboros/preflight_node.py`. Secret-bearing skill review runs before any step imports downloaded plugin code, because untrusted payload code must never share a process with provider credentials; a missing required key is red, not skipped.

Shared UI and keyless wait/repair browser fixtures run the dirty Git candidate in an independent checkout (`tests/candidate_checkout.py`) and prove through `/api/health` and static sentinels that the served assets and imported Python came from that copy (recipe: DEVELOPMENT "Safe local verification and dirty browser candidates"). `ouroboros/test_environment.py` gives pytest, preflight and server children scrubbed temporary roots before imports.

Tool-schema compatibility has two layers. Fork-safe PR tests build the complete shipped catalog without MCP or extensions, validate every schema as JSON Schema plus the cross-provider subset, and require every provider projection to preserve the complete tool-name set. Trusted `integration-test` sends that full registry, fitted to the route's schema ceiling as Main does, in one bounded, unexecuted `delegate_start` canary per route and requires positive usage, exact provider/model identity and a schema-valid call carrying exactly the requested arguments; quota, 429, 5xx and timeout outcomes stay typed inconclusive, while contract, auth, model, tool and reasoning 4xx are red (DEVELOPMENT "Provider Independence").

Informational test reports, safe artifacts, step ceilings and partial UI checks: DEVELOPMENT "Reading CI failure evidence".

A push to a pull request cancels the `CI` run of that request's previous head. Every other event and every re-run has its own concurrency group: release and landed-commit runs are never cancelled, and a re-run of an old head cannot displace a pending run.

`claudexor-platform-gate.yml` proves the managed Claudexor runtime on three OSes: a fixture lane (fake harness, offline, $0) and a toolchain lane (`scripts/claudexor_toolchain_smoke.py`: production `ensure_cli_command()` installs the pinned Node/npm with no ambient toolchain) always, a Windows consumer lane where `install_missing_harness_cli` really installs the engine-pinned Codex (resolves directly, by bare name and in doctor; no login or task), and a live lane only on explicit API keys. Subscription auth stays out of CI, because an interactive machine-bound token must not enter CI secrets. Fixture triggers also run the credential-free `scripts/claudexor_lifecycle_smoke.py` on all three OSes: a real pinned engine under production custody proves cancel, daemon-kill respawn, completion and retirement each settle and continue correctly, but neither vendor sessions nor child-process containment. `dependency-graph.yml` submits the `ouroboros/claudexor_runtime_pin.json` runtime relationship to GitHub's dependency graph (`contents: write` only) without presenting Claudexor as a Python or Node package. `.github/workflows/scorecard.yml` runs on `main` pushes and weekly, pins every action by commit SHA, defaults permissions to read-only and adds only `security-events: write` + `id-token: write`. `CODE_OF_CONDUCT.md` owns community rules, `CITATION.cff` the software and technical-report citations, `site/paper/index.html` the paper landing page, `docs/benchmarks/evidence.json` the release-bound public benchmark projection; README remains the claim SSOT.

`scripts/` is operator and release tooling, each script documented by its own docstring: `safe_test.py` (stdlib verification boundary), `book_growth_mode.py` (official contribution growth mode), `browser_ci_scope.py` (documentation-only browser selection), `run_tests.py` (test battery), `run_external_review.py` (the runtime's own review flow over the staged index or, with `--contributor`, over a committed `base..head` proposal under the installed body's review flow and rules; `READY_FOR_INTEGRATION` is evidence, never merge authority), `contributor_review_evidence.py`, `run_plan_review.py` (the `plan_task` engine; review-exempt), `validate_scope_receipt.py`, `claudexor_platform_smoke.py`, `claudexor_toolchain_smoke.py`, `fetch_claudexor_runtime.py` (pin SSOT: `claudexor_runtime_pin.json`), `cleanup_test_pollution.py` (dry-run first). `site/` is the Vite source of the public pages (`site/scripts/sync-assets.mjs`); `skills/telegram/` and `skills/unix_computer_use/` are the bundled skills; `packaging/cli/`, `packaging/appimage/` and `packaging/systemd/` hold the CLI wrappers and installers, the AppRun dispatch and the opt-in user unit (§1 Runtime topology).

### System E2E suite (`tests/system_e2e/`)

The deep-integration suite drives a real isolated `server.py` per scenario (`KeylessIsolatedServer`, whose child environment can never carry a provider credential) and asserts durable artifacts through `ArtifactOracle` readers (`task_results/`, `logs/*.jsonl`, `state/*`), never an HTTP 200 or a harness exit code. Synchronization is durable-event polling, never bare sleeps; a scenario that must act mid-round holds the loopback model on an event-gated `ModelGate`. Two loopback models share one HTTP base: `ScriptedStubModel`, an ordered per-scenario tool script whose review-organ calls are classified by prompt markers, and `ReplayModel`, deterministic keyed fixtures where a miss or an unconsumed row is red. A default-lane pin greps the prompt markers back out of their source files verbatim, so drift is a named failure, not a silently mute stub. Reviewer routing is pinned through an `OUROBOROS_SUBAGENTS` catalog (`keyless_review_catalog`), because a never-configured catalog reads the factory reviewers, live routes that block keyless runs. `FakeClaudexorDaemon` imitates the exact `gateways/claudexor.py` client contract and records every wire request for scenario assertions.

The scenario inventory is data (`SCENARIOS` in `harness.py`) with a two-direction pin over every `test_*.py` module of the package: a manifest row without a test, or a scenario test without a manifest row, is red. Scenario tests carry the `integration` and `serial` markers plus the `OUROBOROS_E2E_DEEP=mock` env gate, so neither the default local run nor either CI pytest pass executes them; the keyless lane is `OUROBOROS_E2E_DEEP=mock pytest tests/system_e2e/ -o addopts=""`, in CI the secret-free `system-e2e-mock` job that `release-preflight` needs. The paid owner-shaped stand against a real provider is operator tooling: `devtools/e2e_live/README.md`.

### Build scripts

`build.sh` (macOS → .dmg), `build_linux.sh` (→ .AppImage + .tar.gz), `scripts/build_appimage.sh`, `scripts/build_linux_packages.sh` (.deb/.rpm/.red80.rpm), `scripts/smoke_linux_packages.sh`, `build_windows.ps1` (→ .zip), `scripts/pack_windows_archive.ps1` (hidden-file-preserving ZIP), `scripts/sign_windows_release.ps1` (eSigner invocation), `scripts/verify_windows_signature.ps1` (signer/timestamp verification) and `scripts/build_repo_bundle.py` (writes `repo.bundle` + `repo_bundle_manifest.json`, the manifest `launcher.py` bootstrap validates) are the release-invariant owners. Linux PyInstaller runs under the same pinned portable Python shipped in the payload, so its bundled libpython keeps the payload's glibc floor, not the release runner's newer ABI. The AppImage builder wraps that payload with digest-pinned tool and runtime bytes; the native Linux packages wrap the same x86_64 payload, keep bundled Python/Node/browser under `/opt/ouroboros` and install the opt-in user unit with no activation scriptlet. The release-gating package smoke installs through `apt`/`dnf` on Ubuntu 22.04/Fedora 42; Astra Linux and RED OS vendor-image runs stay informational, because third-party registry availability cannot block publication. `scripts/build_repo_bundle.py` is also the release-tag SSOT: before packaging it verifies the annotated `v$(cat VERSION)` tag points at `HEAD`.

Betterleaks follows the same release-resource discipline: packaged builds stage the pinned binary and license under `betterleaks-standalone`, source checkouts install the managed runtime explicitly, and the Publish path never downloads it (§6 Skill publication).

Python dependency resolution has one authority: direct requirements and group membership live in `pyproject.toml`, `uv.lock` records the universal solution under the pinned `tool.uv.required-version`, and source/CI sync with `--locked` so metadata drift is an error. The two-interpreter packaging boundary rides projections: build scripts export their PyInstaller input from `uv.lock`, the committed `requirements-runtime.lock` supplies embedded `python-standalone` and managed updates (pip, no bundled uv), and a one-line `requirements.txt` pointer serves already-released updaters; CI regenerates the export and requires a clean diff, so neither file becomes a second dependency authority.

Platform builds precompile bundled Python with unchecked-hash bytecode: sealing valid bytecode prevents runtime `__pycache__` writes from invalidating a macOS signature, and runtime children route caches outside the bundle. When signing is enabled, hardened runtime, notarization, xattr hygiene and strict verification are part of the stable-release path; prerelease artifacts may be unsigned and their evidence must report the actual signing state.

The release proof begins with the final DMG/AppImage/tarball/ZIP, never its staging directory, because a validated staging tree does not prove the published bytes contain or execute the same payload (`scripts/release_proof.py`). Each platform shard checks the embedded repository bundle, the packaged CLI and the managed Claudexor seed + Node by starting the owned daemon, completing a fixture task and verifying an identity-bound stop; the proven Linux tarball payload is wrapped into the three native packages, each with its own digest-bound package-manager smoke receipt and provenance attestation. The release job requires seven desktop assets, accepts the optional Android pair only after verification, recalculates digests, writes the checksum/evidence capsule and rechecks the remote annotated tag immediately before publication. Signing credentials stay step-scoped and absent from SBOM/attestation steps.

Windows signing is selected by the `ESIGNER_CERT_SHA1` repository variable. Unset, no job sees a signing secret and the Windows ZIP is proven and published as explicitly unsigned. Set, a fresh runner bound to the `windows-release-signing` Environment signs `Ouroboros.exe`, verifies signer and timestamp and repacks the ZIP, and any failure blocks the release; the secret-free proof runner smokes the final ZIP and records its signing state, which the release assembly matches against the variable. Configured signing accepts only tag-push events and their reruns, not a manual dispatch against a tag, to avoid an additional certificate-use trigger. Setup: DEVELOPMENT "Build & CI".

Public installer naming and links ride the same projection: `ouroboros/tools/release_sync.py::RELEASE_ASSET_TEMPLATES` is the filename SSOT shared by the proof builder, README and the install pages. A version bump rewrites only named download references and `data-release-download` anchors to immutable `/releases/download/v{VERSION}/...` URLs; the `/releases/latest/download/...` shape is forbidden because GitHub excludes prereleases from `latest`. Generated release notes link only proof-accepted assets: seven required desktop installers plus an optional Android pair and its USB setup guide; the APK alone is not the runtime. The default README and GitHub Pages deployment use the stable `main` boundary (`main:/docs` for Pages); stable promotion advances `main` only after the release is published with all seven proof-bound desktop installers, so an unreleased development VERSION never exposes dead installer links and an omitted promotion leaves the previous working release public.

`scripts/build_android_release.py` binds a source archive, a common Git seed and a publisher-signed reference APK to the tag SHA, package/version/certificate and smoke/SBOM/attestation proof. Android is nonblocking: a failed, cancelled or skipped build, a partial pair or a failed digest/smoke/SBOM/attestation check excludes both Android artifacts, while required desktop failures stay fatal. Compilation certifies no physical root, boot, hardware or runtime behavior.

### Docker

Docker runs the web and server runtime without PyWebView. The image binds `0.0.0.0` and sets no network password by default: a missing password only warns, and `NetworkAuthGate` then permits requests, so publishing the container port without `OUROBOROS_NETWORK_PASSWORD` exposes the owner surface. Set the password or keep the port unpublished; packaging adds no stronger boundary of its own.

The root `.dockerignore` filters `COPY . .`: secrets, host virtualenvs, `node_modules`, caches and runtime/review/operator state stay out of image layers; `.git`, `tests/` and sources stay in, because CI runs pytest inside the image.

The image is one self-contained `Dockerfile`: `python:3.10-slim` with the pinned `uv`, git plus Playwright's native libraries and the Chromium/WebKit binaries of the Playwright version `uv.lock` pins installed into `/ms-playwright` (the `PLAYWRIGHT_BROWSERS_PATH` the runtime honors as-is), then `uv sync --locked` into `/app/.venv`, then the sources. Browsers and apt packages sit above the lock copy because every release rewrites `pyproject.toml`/`uv.lock`. No runtime `UV_PROJECT_ENVIRONMENT` is baked, because a baked one would let an agent's `uv sync` in a task workspace rewrite the runtime venv; the tag-only `docker-ui-smoke` and `docker-portable-test` lanes exercise the shipped browsers without a download. No trust anchor is baked in: a deployment needing an extra CA sets `OUROBOROS_EXTRA_CA_BUNDLE` (§7; `docs/DEPLOYMENT.md`).
