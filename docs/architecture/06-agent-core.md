# 6. Agent Core

Task/tool lifecycle, routes, authored context/source recovery, review authority, delegated custody, plans, common story and budgets; `loop.py` runs tasks, direct turns and wakes, with separate review/post-task settlement.

### Task lifecycle

Workers run `OuroborosAgent` (§5); direct chat owns an agent and `DirectActivityRegistry` (§3). `agent_task_pipeline.py` freezes contract/context, runs the loop, stores results/artifacts (the store row is the lifecycle authority, read by `get_task_result` / `query_data`; `task_results/<id>.json` is import input and export output), runs root post-work (`post_task_synthesis.py`, `post_task_checkpoint.py`) and publishes. Admission, completion, satisfaction, verification, review and artifact finality stay separate. `task_result_schema.py` admits rows (§11); usage owns money/tokens. A crash is `failure.kind="runtime"`; lost capture is unknown. `finalization_timing.py` times delivery, sharing child projections per pass until a model wait; lookups use task/root/queue-seed lineage (`task_store`). `supervisor/cognitive_operations.py` keeps typed operations off the idle rail; deadlines, budgets and cancellation stay active.

The loop transcript is append-only for OpenAI-family byte-prefix caching (§6 Prompt caching); `transcript_prefix.py` counts every break by origin (round facts, Health) without blocking sends. Before preparation/pricing it retires signed reasoning from the first change, or all for system/tools changes or no baseline. `model_execution` keeps the last accepted ordinary solve's requested, routed and provider-reported models distinct; empty/forced/review/post-task replies cannot replace it. A host model switch after tool work grants the successor one authorship recovery round; another tool-less reply degrades as `authoring_handover_incomplete`.

`loop_delivery.py` retains the complete `DeliveryCandidate` before verification or review; later failures cannot erase useful work. `outcomes.py` combines execution, objective, review, artifact, child-absorption and custody facts, substituting none for another. Host receipts and exact artifact references prove effects; declarations do not. Failed tools alone do not degrade an answer; an unevaluated objective retains `residual_tool_errors_without_review`. The unconditional `FINAL ANSWER:` latch survives review, nudges and forced finalization though only `task_contract.answer_protocol="final_answer_line"` prompts the marker. A best-effort result may have lifecycle `completed` with an unaccepted objective. Stored reason codes stay unchanged; current owner wording is projected at read time (§3 Task cards, errors and reason lines).

Host disclosures stay beside the answer: `terminal_host_notice` carries plan/orphan limits; the owner's typed `terminal_custody_notice` row omits empty categories. CLI labels these as host status; Presence speech excludes them. A notice changes neither answer bytes/hash nor verdict; identical text never revives superseded approval. Child-result and plan-evidence hashes include notices: a changed limitation voids an old parent disposition. Host salvage is visibly labelled `Preserved intermediate output (not a final answer):`; the durable preview is bounded; `get_task_result` and stop receipts keep the whole copy.

A first reply without a selection episode is a plain final. After substantive host continuation, Main selects complete retained bytes with `finish_task(action="finish"|"stop", answer=...|answer_sha256=...)`; compaction withdraws unavailable selectors. Finish checks children, skills/handover, owner sources, material, services, configured review and admission. Stop retains the selected unfinished work without buying criticism or another answer, cancelling descendants or claiming approval; evidence-only changes cannot undo it. Undispositioned direct children hold finish; reminders and custody disclosures never decide it. Presence completes a send only with host-confirmed delivery. A result review binds the exact delivered subject; a change supersedes it, never deletes it (§6 Result review).

Provider death salvages text but ends `failed`/`infra_failed` with `provider_unavailable` (or `resource_refusal_no_resend`) and an immediate not-completed owner notice. One forced model call runs only while a call can land; wait expiry and `loop_llm_call.provider_no_call_source` forbid another paid window. `terminal_provider_notice` quotes the provider's own words beside the result, never recommends blind replay. The finalization sink stamps `model_final`, `host_notice` (host words) or `host_salvage` (model output kept after provider death); a forced reply still requesting tools is incomplete. Finalization controls are typed mailbox entries. Descendant activity is not the task's own progress; an unkillable process stays visibly running: even a zero, final cost cannot settle `delegated_runs_unreconciled` custody.

#### Result review

A task's result is one subject of the one review machinery: `review_change(subject="result")` (`tools/review_result.py`) asks the review pool whether the result, not the method, does what was asked, by the `Result Review Checklist` of `docs/CHECKLISTS.md` (`result_rubric`, fingerprinted like every checklist). The frozen subject has four parts: what was asked (the request fields, the claims it is held to — `effective_acceptance_claims`: an ingress contract's, else the latest plan revision's `done_when` — and its owner's words), the reply (`answer`, else the latest retained reply), what the task produced (registered artifacts and attributed workspace changes by path and hash, plus declared `observed_effect` receipts, even from failed calls; a failed capture is a named gap) and the host-attested verification receipts. Expected output, inputs and checkpoints are intent, never production. The exact text is retained once (`result-subject-<sha16>`) and its sha is the wave's identity: the same reply, material and request reuse the settled record at $0.

The wave is `review_change`'s own: composed panel (a Required root widens or needs a reason; else the named rows; omitted = the pool), paid stamp, custody and rejoin, leaving on an addressed message or Pause (a left or unwaited wave settles from recorded seat answers into a notice or late mark, `review_pause`), settlement and the ledger record (`surface="result"`). Seats answer one result part (`PART_RESULT`), reduced without coupling under the adaptive quorum; failed rows are infrastructure evidence, a pre-send refusal `not_dispatched`. Findings are `critical` (fails the ask or misstates the delivery) or `advisory`. Result waves count their own paid cycles per root (`review_result` attempt rows); a child may ask its own (`subject=result`).

Modes (`OUROBOROS_TASK_REVIEW_MODE`, §7). Auto forces nothing. Required adds the floor at a ROOT final delivery with produced material (file, effect, adapter answer line): unless a settled record binds the subject sha, the host collects a running review at $0 or seats the pool (`chosen_by=host`). PASS delivers; else findings show once and delivery holds one turn: Advisory and Cyber Pro deliver on the next decision, Blocking holds until a review passes or the task stops. A spent allowance refuses once at $0; Blocking holds while the ceiling stands. A running review (every mode but Off) is awaited unless a nonblocking install chose `finish_task(pending_review="finish")`. An unchanged answer reviewed against an earlier request shows the new owner words once; redelivery keeps it. Presence speech is never held: the owed review runs with a departed author (`review_pause.departed_binding`) as a late mark. Off refuses `subject=result` before payment.

Objective authority. Every mode but Off binds the settled review of exactly the delivered result into the task's review runs (`authority="host_root"`, `binding_hash` = subject sha); every new delivery candidate (on every rail) supersedes earlier runs, never deleting them. `outcomes._review_axis` reads `source: "result_review"`; `_objective_axis` gives the reviewers' PASS/FAIL, PASS with source `author_acceptance` (reason `author_finish`) for an informed finish, and blocked FAIL (`review_cycles_exhausted`) when blocking enforcement could buy no review. `task_acceptance_review` stays a valid source of older records, whose decisions, panels and rows still render read-only. A result PASS never satisfies the commit gate.

Spent allowance and price. When `OUROBOROS_REVIEW_MAX_CYCLES` is spent, Advisory asks the mind whether what was reviewed is enough (finish, or land with a plain statement of what was not reviewed) and Blocking keeps the owner's ceiling menu (3/5/unlimited). One review's price is measured (`review_price.py`): the median of a row's recent waves on its current model, each seat's attempts summed (`usage_store.review_seat_costs`), with count and range; no history is `cost unknown`, a session row `uses a session seat and time`, a local route `no API cost per review`. `## Review`, `GET /api/review-pool` (`basis: observed_reviews`), Settings and onboarding print the same words; the table is cached per process for half an hour.

Root admission seal (`delivery_seal.py`, re-exported from `loop`). Sealing closes the root's admission (no new subtask under it) and catches by generation an owner message that arrived between "decided" and "delivered". It runs only at an author stop, right before the stop is delivered (`loop_delivery._seal_admission_before_delivery`); a plain finish never opens it, so during a plain finish only the local admission-lock drain catches an owner message routed at the supervisor. Born as the task-acceptance fence, it keeps the persisted names (`acceptance_fences`, the `acceptance_fence` event, `state/acceptance_fence_acks/`, the `_task_acceptance_*fence*` context fields). The supervisor owns the row under Q (`queue_transitions.transition_acceptance_fence`: end compares `owner_message_generation` and seals or releases) and clears it at `task_done`; pooled fences bind attempt/PID (unanswered begins release, ended owners retire at handoff, consumed Resume rebinds park fences). `ok` seals; only owner facts revise, a generation mismatch (also one seen locally) or pending owner mail: `_release_for_owner_followup` pops `task_completion` and ends the fence with `revision` (and serves a follow-up after the seal, `_owner_generation_changed`); a begin refused `sealed` is the worker's own lost ack, and a pooled attempt refused `stale_attempt` lost its queue ownership and never publishes. Any other refusal, like `unknown`, is a gap, never a refusal of the answer: it is delivered with `admission_released=False` and the durable `supervisor_ack_unavailable` row is the record (§10 invariant 25).

Owner-source acknowledgement (the completion protocol of `finish_task`, argument `acceptance_subject`). While delivery control asks Main to select a completion, `loop_messages.prepare_acceptance_observation` appends the `[ACCEPTANCE_SUBJECT_OBSERVATION]` row when the owner-source facts changed (earlier rows stay for prefix caching). `acknowledge_acceptance_observation` advances only consumed ingress, never criteria or a verdict; it refuses with a typed `ACK_*` cause when the named source was not observed, owner input is unread or the owner source or queue generation changed (an unknown queue state is disclosed, never read as a change); every outcome is the durable `acceptance_source_ack` row (§10 invariant 21). Raw owner messages stay evidence; their count is not a change in requirements.

### Own-body candidates

Body authors (queued roots, direct turns, evolution cycles) write a task-owned linked worktree of the serving repository, never the serving checkout, keeping unfinished edits out of serving imports. The candidate starts at the serving HEAD on branch `candidate/<task>` under the isolated worktree root, as a `kind=body_candidate` row of the worktree registry, which restores the binding across a retry, a Resume or a new worker. `prepare_self_change` prepares it; body writes, PR-integration verbs (`git_pr.BODY_WORKTREE_TOOLS`) and an acting `self_worktree` child reach the same preparation through `body_candidate.authoring_seam` before resolving any target; reads before preparation stay on the serving tree. Light mode, capped trees, subagents and the managed-update resolver get none; Cyber Pro may choose `in_place`; a body with no Git tree keeps in-place authoring.

Binding rewrites one fact — `repo_dir`, `system_repo_dir` and `branch_dev` of the tool context name the candidate — so every consumer, the review subject and `commit_reviewed` included, shares one identity under own-body policy; an external workspace stays the root's active folder (the receipt says so); a candidate is never an external workspace, and `serving_repo_dir` keeps the running checkout for review governance, the restart marker and rollback. A process whose cwd is inside the candidate or its admitted own-body child copy runs in an isolated environment beside it (`<candidate>.env`, `test_environment.isolated_environment`: its own HOME and data root, no credentials or global Git config, pip only inside a venv), so a push, a provider call or a pip install outside a venv runs from a cwd outside the candidate; when it cannot be prepared the process is refused (`CANDIDATE_ENVIRONMENT_UNAVAILABLE`), not started with the serving one.

Ownership is the root task: a host-validated continuation inherits its predecessor's candidate, `prepare_self_change(resume=…)` selects one exact retained candidate, and either moves ownership only from a terminal owner whose ledgered processes are settled; nothing is inherited by room, name or date. Binding appends the candidate to the lineage's mutation baseline, so `commit_reviewed` stages what the task's own baseline attributes to it exactly as on the serving checkout; the commit is never auto-pushed. A candidate commit is version-neutral (every carrier span byte-identical to HEAD, no tag) or a numbered release (VERSION and every carrier in one diff, tagged); the release gate names the form from the diff, a partial carrier move is neither. Retention counts from last use: a candidate with no unique work expires; otherwise its files are captured on `refs/ouroboros/candidates/<id>` and the checkout is removed only when the capture is complete and the verdict still holds (`body_candidate.verdict_holds`); a nested `OUROBOROS_RETAINED.txt` marker keeps the process environment and source checkout.

Adoption is deliberate and restart-bound (`body_adoption.py`): `request_restart(adopt_commit=<sha>)`, or an evolution cycle's own restart, authorizes one exact commit that builds on the serving HEAD, came through the commit gate (Cyber Pro records the exception), keeps the entry files and the package-init hook and changes no path where the serving checkout holds uncommitted work; a constitutional change needs a numbered release outside Cyber Pro. The old generation never writes the tree: the carrying restart re-verifies under the update lock, its exit tail arms only on the stop owners' own evidence that the old readers are gone, and the engine pin the next generation selects is read from the candidate's file before the owned daemon's fate is decided (§9). The owner's Restart and Panic never arm or wait: a stuck stop must not hold the owner hostage; evolution cleanup abandons only its own authorization, and crash recovery retains a reviewed candidate without authorizing adoption. The switch and its recovery are §2; `settle_on_boot` records `adopted` only for a generation that attested the switched tree before its imports, bootstrapped and is supervisor-ready.

Selecting Publish calls `POST /api/skills/{skill}/publish-preflight` (`gateway/skill_publish.py`, read-only), which captures and scans one current payload, recomputes review staleness and returns exactly one backend-authored state (`ready`, `warnings`, `needs_attention`, `repairable`, `hard_block`); the browser only renders it; only `hard_block` prevents task creation. The authoritative flow is:

`passive index (no scan) → selected preflight → explicit confirmation → ordinary managed task → immutable current capture with separate review provenance → payload scan → GitHub read-only planning → derived-output scans → first GitHub mutation → validated same-skill pull-request receipt → ordinary completion`

Publication authority is `skill_publish_eligibility.publication_author_acceptance`: fresh publishable critic authority or qualified current Advisory author authority; owner attestation alone is not that chain, and catalog hashes and PR receipts never become review PASS. Every outbound byte derives from the capture (`skill_publish_snapshot.py`), never a reread live payload. Outside Cyber Pro, Betterleaks `high` findings (`skill_publish_scanner.py`) block the outbound call; lower or unknown confidence is a redacted warning; Cyber keeps scanner and review results as independent advice. Publish never downloads Betterleaks (§8). A `skill_publish` task (`tools/skill_publish.py`) is accepted only when its pre-truncation metadata holds a validated pull-request receipt for the requested skill and its destination's repository (origin, hub entry or the owner's source: `skill_publish_destination.py`); the receipt proves the observed publication. A failed envelope (`skill_publish_result.py`) names the failed stage (`reason_code`), a `repair_hint` and the transport's sanitized `error_detail`.

Owner lifecycle actions share `skill_lifecycle_actions.run_skill_action`: grant/toggle run in the lifecycle lane, local delete uses `skill_uninstall_state`, and attestation keeps its deterministic floor. The host supplies actor identity and checks exact resource/revision plus an existing chat message, answered quiz or owner-mailbox record when owner intent is needed; the model interprets that source. A generated edit-and-review request confers no grant, attestation, deletion or enable authority: a client `allow_enable` flag authorizes nothing, Presence ceilings come first, a newer owner disable in `enabled.json` wins, and a Repair review never auto-enables; the model chooses `toggle_skill`. There is no permission ledger and no HTTP impersonation. `skill_exec` returns the revision captured before its script launch, and extension tool receipts carry the descriptor's `content_hash` only after physical dispatch; neither is review PASS or a semantic test verdict. Install rollback and the publication receipt: §13.
