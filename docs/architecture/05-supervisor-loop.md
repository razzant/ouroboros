# 5. Supervisor Loop

`server.py::_run_supervisor()` schedules pooled work through one tick thread and lifecycle lock, persisting cancellation intent before teardown. Admission, schedules, waits, stops, workers, maintenance and ingress keep intent, outcome and money as separate durable facts; unknown is never zero or no.

### Tick and locks

Only `state.init_state` creates state, on first-boot proof before bridge publication (PERSISTENCE.md); unavailable controls or bindings never block independent work, chat or diagnosis. Each tick publishes liveness, rotates logs, checks workers, drains one bounded batch of worker and direct events (bounds: `runtime_limits.py`), accepts bridge input, flushes a dirty budget projection, enforces deadlines and schedules, runs throttled maintenance, admits evolution and assigns, snapshots, publishes direct roots and ticks the threadless consciousness alarm. Bridge intake precedes the slow steps, because a blocking step must never starve new-message intake; a backlog skips the idle sleep. Three consecutive tick failures clear readiness and notify the owner. Shutdown errors are not crashes: `_SignalStopServer.handle_exit` sets the local stop on SIGTERM/SIGINT so the event Manager is not killed early (§9).

The `state.json` budget projection is display, not admission (§10 invariant 28): only totals persist, per-root money comes from `usage_projection`, and `usage_writer_snapshot` renders it once per dirty tick after bridge intake. The write is ordered by the ledger's `(compaction_epoch, seq)` provenance, so a stale render never overwrites a newer one; a quarantined ledger (`integrity_degraded`) freezes the projection until explicit repair, and a failed write stays dirty and retries after `BUDGET_PROJECTION_RETRY_SEC`. The OpenRouter comparison is one asynchronous diagnostic that never changes monetary admission.

`supervisor.queue._queue_lock` (Q) is the single authority over live `PENDING`/`RUNNING` lifecycle. Admission reserves identity before project, workspace, attachment or routing effects and refuses typed (`detail` carries the repair); assignment skips reaping, budget pauses, closed projects, conflicting writers and exhausted root capacity. Capacity is the assignable idle workers after custody, reaping and admission fences, not the configured count. Only evolution has runtime-mode fences (`supervisor/evolution_lifecycle.py`): Light refuses campaign entry and assignment drops leftovers while `evolution_block_reason()` is set; generic `enqueue_task()` has no mode predicate.

### Admission and addressing

Headless addressing is fixed at admission (`log_addressing.ingress_chat_id`). A registered Project's explicit `chat_id` must match its thread; another address, including hidden, is refused with a typed 400, so a Main card is never detached from its Project work. Without a Project, ordinary API tasks default to `HIDDEN_CHAT_ID` (0). Confirmed browser Publish carries `source="web"` and `WEB_UI_CHAT_ID` to request Main: caller-declared addressing, not authentication; other non-Project conversation addresses are refused. Work for an active registered Project is admitted into that project's thread. Main gets one host-stamped completion only for work addressed or bound there. Registration alone does not qualify: other work stays in the hidden partition, silent in every chat, readable through the terminal, `--result-json-out`, Logs and `GET /api/tasks/<id>`. Reserved inactive Projects keep their chat valid so the queue gives its typed lifecycle refusal.

The run is also named at admission and chat promotion, without a new model call. An authored `title` (`ouroboros run --title` or the top-level contract) fills `title`/`suggested_name`; `metadata.title` is refused with a 400, as is `metadata.project_id`. Otherwise the first request line fills only `suggested_name` and never outranks a real name coined later. Admission broadcasts `task_named`, never using status as a title.

`queue_snapshot.json` atomically projects pending and running rows, acceptance and root-budget fences, worker capacity, pool-disabled reason and bounded root focus (`supervisor/queue_snapshot.py`). A snapshot restores into an empty PENDING; RUNNING survivors get `server_shutdown` cancel intents (`terminalized_running`) for custody settlement, except saved work: a row or direct turn with a working checkpoint or current-attempt wait source and no Stop becomes its same-id successor carrying the frozen source (`restart_retention.recover_saved_running`), returned or held as §6 Saved working state says. Boot `kill_workers` settles children of interrupted parents as `pending_parent_interrupted`. Accepted never-started rows never expire; only rows without never-started proof keep the 900 s rule. Acknowledged planned handoffs, exact pauses, owner-Restart holds and accepted Project rows ignore snapshot age (§6 Project registry and lease). Restore persists Restart holds before `auto_resume_after_restart` consumes the marker. Scratchpad resumption needs `pending_restart_verify.json`, never log-tail inference.

Dispatch possibility is monotonic on row, result and schedule receipt: `_claim_worker_launch` stamps `dispatch=possible` before the worker put, so a snapshot never replays a possibly-started row while live retries and exact continuations still run; a working successor also needs its exact frozen source and a monotonic `admitted_dispatch_attempt` mark below its target (budget-pause restore and `sleep_wake.py` grants: §6 Exact budget pause and Resume). Terminal rows stay terminal; custody cancels an accepted or sealed root's descendants except exact pauses; malformed fences stay closed. `task_status` separates lifecycle from `execution_observation`: fresh local evidence proves activity, gaps stay unknown, and only pooled work admits worker-boot orphan inference.

### Schedules and follow-ups

`supervisor/queue_schedules.py` alone writes `state/scheduled_tasks.json`; every mutation enters `schedule_transaction` (Q, then the sidecar lock). `load_schedule_store` treats only absence as empty; an unreadable table raises `ScheduleStoreUnreadable`, refuses mutation and reads as unknown.

`schedule_occurrence.py` admits at most one root per due occurrence, enqueued with a frozen receipt. A typed `hold` is a wait, not a failed root. Enqueue alone cannot execute and restore needs the receipt, so the same token and task id re-prepare after a restart; unreadable or foreign results and receipt-less admissions stay unknown. Edits and disable govern unstarted work only; deletion returns `delete_deferred` for owed or unknown work. A waiting cron row keeps one overdue occurrence, then advances. A `kind:"notify"` row is a note, not an occurrence: the tick consumes it and `schedule_notes.py` shows the mind's words as one signed `reminder` System row; an unconfirmed show is recorded as `last_error`, never retried.

`followup_policy.py` binds explicit related/independent relationships; host provenance (`continuation_of`, origin) establishes neither relationship nor billing authority, and related work keeps its origin's group cap, source and deadline. Lifecycle controls govern future work and report `running_or_queued`; workers read the durable snapshot, and an absent, unreadable or stale one (`_QUEUE_SNAPSHOT_MAX_AGE_SEC`) means unknown, held in flight by the tick. Restart and Stop persist their restrictions before the marker is consumed; a Stop's `followup_stop` lands on the original result even when completion wins. `stop_action_id` names the ingress action apart from custody `request_id`: an exact retry rejoins the current control, altered arguments under one id refuse, an omitted id claims no replay. Restore with `expected_hold_id` releases only that observed hold; generic Restore can re-enable a schedule and cancel pending deletion. `schedule_mutation` intent and outcome rows share one `operation_id`: intent failure refuses, outcome failure reports `changed_audit_incomplete` with no unaudited rollback. `manage_schedules` and `POST /api/schedules/{id}/action` share this seam with explicit action and reason, no text inference; owner-authored edits live in `supervisor/schedule_lifecycle.py`. Final enqueue and worker put share `followup_policy.scheduled_start` (lock order: its module docstring, then the task's own lock); preparation and provider waits stay outside.

### Completion, owner waits and restarts

Pooled completion separates a finished file-save attempt from publishable terminal truth: the worker prepares its terminal files (`headless.prepare_terminal_task_files`) before `task_done`, and the host publishes only when `headless.terminal_task_files_ready` confirms them current. A completion whose files are not yet publishable stays RUNNING under `enqueue_terminal_file_recovery` and retries on the health cadence, never a false Done and never replayed model work; only confirmed absence of a terminal source reaches the lifecycle-fault owner, which marks execution `infra_failed` while the authored answer, review and cost survive.

A required owner wait keeps the task RUNNING with its worker and browser after a completed-tool checkpoint; capacity is lent, and a capped grant resumes the same attempt without replay. The wait row rides every later write, so a planned restart keeps it; any mail wakes it, only an owner answer answers, and Stop, deadline and ceiling still bind. A settled Project result is not steerable even while post-work holds RUNNING (`owner_mailbox.mailbox_drain_ended`), so cleanup cannot eat unread input. Ordinary Main and Project waits stay in-process (`owner_wait.direct_owner_wait`), lend no pooled slot and grant no cold restart.

Existing crash/timeout retries use the current-attempt checkpoint without blind replay; whole-app crashes wait for Resume, and boot returns work only under a fresh acknowledged restart, without OS browser sessions. Managed updates prepare handoffs before stopping the pool and pass parked ids as `preserve_running_task_ids`: waits requeue instead of being interrupted; preparation failure blocks the update. Manual rollback prepares no wait handoff. Same-server update aborts return retained work through §6 Saved working state. Cold continuation restores saved economics but rereads cost-ceiling authority (`task_pacing.restore_cost_ceiling`); calendar deadlines and owner-wait time stay unchanged.

### Cancellation

Cancellation is intent-then-custody (§10 invariants 14-15): intent and outcome are separate fields, because one field carrying both wedges a task forever. The skeleton:

1. **Intent.** Every cancel ingress (the `cancel_task` tool, HTTP single and cascade, evolution stop, project deletion, the cascade sweep, boot recovery of `cancel_requested` files) writes one durable row through `ouroboros/cancel_intents.request_cancel` into locked `state/cancel_intents.json`. A failed write tears nothing down (tool `CANCEL_INTENT_WRITE_FAILED`, HTTP 503), so no teardown runs without a watchdog-replayable fence. The owner's evolution stop is sticky: the campaign stays open under `evolution_owner_stopped`, which only an owner start clears.
2. **Scope.** Recorded scope is widen-only (single to cascade, so Stop-now cannot shrink a cascade). Timeout reaping is not a cancel ingress: the reaper keeps its own `reaping` custody, because cancellation is reserved for explicit intent.
3. **Claim.** `supervisor.task_lifecycle.cancel_task_custody` is the one settle owner: it claims the intent before any mutation and a refused claim exits untouched, so racing custodies never double-settle. A live direct-chat turn stops through the same custody (`supervisor/worker_chat_lane.py` writes one typed `finalize_now` control; the loop ends at its next round boundary with no further model call); a Stop during post-task synthesis discloses skipped paid stages as `post_task_stop_reason`. A still-live turn releases the claim for the sweep rather than publishing a fabricated `cancelled` row.
4. **Kill and re-check.** Custody confirms process death, then re-reads the child's settled result. Natural completion wins: a child that finished before the kill keeps its result, artifacts and cost, and the cancel settles as already-settled.
5. **Reconcile and capture.** Open delegated runs are re-audited from durable custody rows; workspace artifacts are captured from the real tree, and a failed or unrunnable capture is `failed`, never `missing`.
6. **Settle.** The result carries reconstructed-or-unknown cost, never a fabricated `$0`; `parent_decision` is stamped only here. `cancel_publication` keeps the provenance as `cancel_origin` through the terminal event, task detail, history and result reads. HTTP proves transport, never a personal owner.
7. **Owe, then publish.** The owner's terminal answer is registered as owed in the durable outbox before the intent settles and before `task_done` publishes, so a crash between settle and send replays the answer instead of losing it. A cascade delivers one root message with a children digest under the delivery id `cascade:<root_tid>:<request_id>`.
8. **Watchdog.** The tick's off-drain sweep (`server_maintenance.py`) has `sweep_cancel_intents` re-feed unclaimed or abandoned intents into custody, a cascade replayed as a cascade, so a lost control event or a custody that died mid-teardown cannot wedge a cancellation.

Readers see typed `cancel_state: "pending"` with `cancel_reason` on effective results until settlement (UI projection: §3 Stop and cancel controls). Steering writes (`steer_task`, mailbox follow-ups, `forward_to_worker`) are refused typed while a cancel is pending, which makes the single-turn owner-stop rail safe; restore and pre-assignment read the projection under Q, so a cancelled pending task never starts. `task_done` asserts a settled outcome validated against the durable result; a mismatch is a lifecycle fault, left to custody while a cancellation is pending.

`supervisor/terminal_delivery.py` owns terminal sends from one bounded outbox (`state/terminal_deliveries.json`): owed before enqueue, replayed on boot and tick, with restart-surviving `delivery_id` dedupe shared by natural completion. Exhaustion emits `terminal_delivery_exhausted` and a notice that this message's send is unconfirmed and its copy saved. Cancel and non-retry reap send lineage-routed unreviewed salvage; retryable reap sends nothing. §10 owns the custody, completion-wins and owed-before-published invariants.

### Stop policy and hurry

Stop policy is an axis on the same durable intent, independent of cascade scope. An omitted or empty-body cancellation is synchronous immediate teardown, which keeps programmatic callers' budgets bounded. `stop_policy=finalize_then_cancel` answers 202 with the intent open and runs one bounded finalization episode (`supervisor/owner_stop.py`): live descendants settle first, then the root's `finalize_now` control allows at most one tool-less model turn over a bounded child-result projection, terminalizing under the honest owner reason, not a false deadline. Grace is bounded by `OWNER_STOP_OUTER_CAP_SEC`; explicit deadline and absolute ceiling stay independent. Transitions are monotonic: immediate hardens a pending graceful intent and graceful never softens an accepted immediate one; Panic bypasses both.

The owner "hurry" is a typed task-local `kind=hurry` owner-mailbox control (`ouroboros/owner_hurry.py`, `gateway/task_hurry.py`) that skips the next otherwise-eligible acceptance panel with a typed reason, zeroes the remaining improvement passes and makes the force-plan projection advisory for that task. It is never a chat message, a settings mutation or a weakening of the P3 commit and review gates, and it is attempt-scoped: a shared `retry_reset` strips it on every same-id requeue.

### Event bus, timeouts and worker readiness

The event bus is process-lifetime, not worker-generation-lifetime: respawns reuse one manager-backed queue shared by workers and direct chat, because a force-killed producer can corrupt a raw multiprocessing feeder frame and a queue rebuilt on pool rotation strands surviving producers on the old endpoint. One persisted event yields exactly one live frame: `ouroboros/utils.py::append_jsonl` streams only runtime `logs/*.jsonl` rows into the process log sink, and each process suppresses the types whose live delivery has a dedicated owner (`WORKER_LOG_SINK_SUPPRESSED_TYPES`, server superset `SERVER_LOG_SINK_SUPPRESSED_TYPES`); an LLM call failure is one durable `llm_api_error` row.

Heartbeat and progress differ: a heartbeat proves a process alive; owner-visible progress and model-usage events prove the task advanced. Progress keeps an orchestrator alive, but deadline, Stop and budget stay hard, and the absolute ceiling ends solving and owner-stop finalization, not settled post-work (§6). Timeout handling freezes its decision under Q, marks the worker `reaping` and hands kill, join, salvage, retry and respawn to the single off-loop reaper (`supervisor/task_reaper.py`). An orchestrator with live descendants is never blindly retried, because a retry would replay its plan and spawn a competing tree. No retry or assignment may occupy a timed-out slot until the original process is provably dead: when kill and join cannot establish death, the reaper keeps the `reaping` slot, emits a visible `task_reaper_wedged` receipt with a restart hint and writes no terminal, retry or respawn; one slot is sacrificed so that no live process races a replacement. Typed timeout codes keep their `task_incident` identity (`queue_timeouts.TIMEOUT_TERMINAL_REASONS`).

Slots stay unassignable until the child's PID-bound `worker_ready` (`supervisor/worker_pool_lifecycle.py`); readiness is not liveness. `worker_sha_verify.ok` is equality against the managed baseline and warns only; it attests neither loaded code nor review. The readiness window extends once on a live child's `worker_starting` (bounds: `runtime_limits.py`); exhaustion (`readiness_exhausted`) is final per slot. Total exhaustion closes pooled ingress (owner `/review` included) but not direct chat, control or boot and update recovery; `disable_exhausted_worker_pool` then fails unstarted PENDING with a Restart hint. Linux uses forkserver; macOS and Windows use spawn.

`worker_health.recover_confirmed_dead_worker` reserves exact custody under Q, then enqueues the reaper's `confirmed_dead_worker`. Saved terminal bytes win even after signal death; an unknown or incomplete publication stays `TerminalFileRecoveryPending`, and only confirmed absence reaches crash policy: a signal is an infrastructure failure, an eligible crash retries within `QUEUE_MAX_RETRIES` preserving cost and owner-wait restrictions, and a budget continuation forbids ordinary retry (§6). Crash storms suppress respawn while terminal sources settle, then fence pooled admission; direct chat remains. Startup recovers addressed `pending_drives`, nonterminal and synthesis obligations after process custody and adopts saved answers before orphan healing.

### Maintenance and custody

Startup and throttled maintenance reconcile three residue classes: process custody, delegated runs, and producer-less task, review and project records (`ouroboros/server_maintenance.py`); the custody and reconcile passes run off the loop thread on their own latches (§10). Process custody checks strict PID, start-time, command, owner-task, session and generation evidence before reaping; delegated-run reconciliation applies the same owner-gone reasoning to harness rows (§6 Delegated subagents). None of these is a command-line-class kill sweep, and one instance never reaps another. The dedicated watchdog observes phase-stamped loop liveness and every native actor: a wedged chat turn alerts with a `/restart` hint, a loop stall only journals, and neither kills a thread.

Cooperative project checkpointing (`supervisor/events_coop_checkpoint.py`) has two equivalent quiescence triggers, a root settling with no live descendants and the last child settling beneath an already-terminal root, because a root-scope budget stop terminalizes the root before its children and a root-only trigger would see a live tree once and never return. The bounded git chain revalidates quiescence under Q immediately before mutation. Only host-minted project roots are eligible: owner-attached folders are never auto-committed, credential-shaped files stay excluded and disclosed, and every material success, skip or error receives a durable receipt.

### Bridge intake and commands

Bridge intake is a bounded batch (`LocalChatBridge.get_updates`), each update keeping its monotonic id and own reply transport. Web owner ingress passes its durable canonical row as the dequeue witness (§4 WebSocket protocol). Host Service delivery and late quiz answers share the off-loop ingress boundary. Authenticated WS and HTTP Panic use the bound `server_control.PanicIngress` before ordinary intake; that door starts the emergency owner on its own thread, apart from supervisor intake and shared executors. A failed handler requeues the unprocessed tail for the next read, memory-only and lost on exit; accepted on-disk rows survive without automatic replay.

The bridge recognizes `/panic`, `/restart`, `/review`, `/evolve [on|off]`, `/bg [start|stop|status]` and `/status`; all other text enters ordinary agent routing. External transports may invoke these commands only with positive owner identity and a transport-specific owner-chat binding known current; unknown refuses and registers nobody. Panic may use a positively observed immutable binding from this bridge generation without a fresh state read; owner Reset closes that binding before deleting state. The commands reuse runtime-mode, queue, cancellation and typed-result authority, not parallel control paths. Archive readers preserve the retained timelines of rotated runtime logs (§1).

Confirmed budget pauses and whole-tree owner pauses register pending `pause_notices` in the same task-result update that publishes the task into the `pause_notices` obligation set (`ouroboros/pause_notices.py`). The off-loop terminal-maintenance duty reads that set without scanning results or chat; the saved System chat row proves local recording before the obligation is removed, so a failed append stays owed. Resume and later pauses retain older owed episodes. Consciousness reports a parked wake as paused or pausing and an unreadable outcome as unknown.
