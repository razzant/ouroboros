# 12. Host Service, Companion Processes, and Chat IDs

The token-authenticated loopback boundary for reviewed skills, the Presence turns admitted through it, host-supervised companion processes and chat-id delivery live here. Three decisions shape the chapter: a chat id is a value and the hidden partition is a real destination; an owner-bound reviewed transport is a first-class control surface; and external speech is observed with its source preserved, never turned into a request, while a Presence author never acts twice on an outcome it cannot prove.

### Host Service boundary

The Host Service (`ouroboros/gateway/host_service.py`, port `OUROBOROS_HOST_SERVICE_PORT`) authenticates every request with an opaque `x-skill-token` bound to payload hash, executable review, enablement and grants; tokens hold no secrets, go stale on a payload edit and refuse stringification (`skill_token.py`). Routes and permissions: the §4 table's Host Service rows. `POST /notify` (`host_notify.py`, grant `notify_owner`, advertised as `notify_version` on `/identity`) writes one sentence of at most `NOTIFY_TEXT_MAX_CHARS` as a `skill_notice` System row in the owner's chat signed `Notice · <skill>`, waking no model; 503 means the row is unconfirmed. Transport review covers identity and attribution, bounded polling, panic cleanup, token confinement and exfiltration. An owner-bound reviewed transport can control Ouroboros; external slash commands bind a separate positive-identity owner slot (`supervisor/state.py`), so an unidentified transport cannot bind and web identity cannot lock out the remote owner. `wait_for_response` is A2A-only.

Shared decision and language writers: §4 Server API Endpoints. Review-operation waits reach their exact live controller after author completion through the canonical `pending_action`; a stale revision or identity, or no consumer, is 409 (§6 Quota and auth waits). Acceptance grants no continuation or additional skill authority.

Admission is one limiter with two policies (`host_service._RateLimiter`): the WS relay lane (`/ui/ws-message`) is a token bucket, so a burst does not silence a widget for the rest of a minute, and every other lane keeps the sliding window. Refused relays aggregate per burst into one durable `host_service_ws_relay_dropped` row in `logs/events.jsonl` with the dropped count; the child's `send_ws_message` stays best-effort `None`, and the in-process broadcast path has no bound.

Chat uploads have one storage owner, `chat_uploads.store_upload`, for Host-confined paths and completed multipart spools: the Host Service calls it directly, the browser's `/api/chat/upload` through the `gateway.files` facade. The request's worker both copies and closes its spool, so HTTP cancellation cannot interrupt cleanup; the skill keeps its source. Neither ingress rejects a file for its size; the Host's request count bound (`_INJECT_ATTACHMENT_MAX`) and the Files-browser upload policy keep their own contracts. Host attachment copies share one request-local cleanup stack: a partial copy, refusal or cancellation removes only new unaccepted copies, a replay never adopts duplicates, and accepted bytes survive disconnects and unknown write outcomes, which claim no acceptance.

### Operation correlation

A named injected message has `operation_ref=<chat_id>:<client_message_id>` on 202, 200, 504 and disconnect responses. `supervisor.message_bus.accept_local_message` (`message_ingress.py`) serializes check, canonical inbound-row acceptance and enqueue; work queues only behind a landed `log_chat` row. A repeated same-id, same-text, same-skill delivery rejoins even before supervisor dequeue; changed content or source is refused with 409. Content includes the ordered `[sha256, name]` of the inline photo and files (`chat_uploads.same_message`), so a regenerated stored name is the same message. The inline photo (`_INLINE_IMAGE_MAX`, judged before decode; wire rules: CREATING_SKILLS `inject_chat`) is parked once in `data/uploads` and always staged, so model pixels keep a retained original; bytes that prove no image stage as an ordinary file, never vision under the transport's label. The queue stays in memory: a crash after acceptance can lose delivery and reads `lost`, never authorizing a second enqueue; one same-id retry of a canonical write that raised in this process hands the row over (`queued`). Routing annotations and outbound task ids are discovery hints only: task reads and cancellation require the queue or task record's complete `origin_message_ref` to match the authenticated skill's canonical source (`DirectActivityRegistry` carries the same origin), and a named response wait polls that exact operation and its retry-aware effective result, because chat ordering never proves a reply. Cancel enters the durable intent and cascade-custody owner (§5) only for work with that origin and the same installation root; anything else is `cancel_unsupported` before any intent is written, and unresolved custody never becomes a false `cancelled`.

### Presence turns

`POST /presence/turn` (`presence_runner.py`) admits exact provider, account, conversation and thread facts, skill-confined files and a reviewed binding; conversation and active-turn gates hold cross-process leases, and an HTTP disconnect neither cancels work nor returns capacity early (only a continuing author's yield does). The Host joins a live retry by turn ID only when the canonical conversation, actor and text match; a mismatch is `presence_event_identity_conflict` (409, rejected), never another room's answer. Refusal codes and dispositions on the wire: CREATING_SKILLS "Presence behavior profiles and transport ingress".

A turn never acts twice on an unknown outcome. Before any model or tool call, `handle_task` writes and reads back a source-bound RUNNING row in the task-result store. A failed or ambiguous start write is `presence_start_unwritable`; a RUNNING or INTERRUPTED row with no terminal, or a terminal under the unknown-outcome fence (`metadata.presence_unknown_outcome`), is `presence_attempt_outcome_unknown` (both 409, retry), never completed or silent; that durable row is the one authority the Host reads back after `handle_task`, and provider monetary abandonment does not prove the absence of an external effect. When a quota refusal remains unresolved after routing, `resource_refusal_no_resend` becomes a retryable `presence_resources_unavailable` (409) with no terminal speech: the event stays with its transport, the gate is released and Main gets one deduplicated notice. A failed row is reusable only with terminal `presence_retry_proof` (first-round temporary refusal, every route and rotation operation engine-confirmed `not_started` and ledger-released, no response, tool or handoff, and a future reset); after the reset the conversation gate writes `presence_retry_next`, a locked link to a new physical task ID derived from the predecessor's, and the Host still joins by the original event ID. Old, unproven or undated rows stay empty 409 and owner-only; nothing claims exactly-once for arbitrary external APIs. Same-round transport-death repeat: §6 Context fitting, retry, and compaction.

Same-author continuation (`presence_continuation.py`): an author whose result waits for its acceptance panel keeps its stack, task, controls and paid review but lends its conversation. At the review park, only if its own tool, process and service custody is idle, it persists and reads back a source-bound write-once initial envelope on its RUNNING row, lists itself in the conversation's `open_turns`, publishes the envelope, then lends conversation and active slot; before any further model, tool or forced call it reacquires both in admission order and reads the `[PRESENCE CONVERSATION RESUMED]` facts since its yield. A hard stop meanwhile ends on the zero-call control rail; rounds and wallet are not reset. Blocking holds the final; Advisory `pending_review=finish` and Cyber release it to a `continuation_version: 1` consumer while the author stays for the criticism, and a PASS publishes nothing itself. A released selection (`output_ref`) is never resent; without `continuation_version` the request waits for the author's terminal. `continuation_status()` projects RUNNING as `interrupted` only when the retained controller identity (`author_controller`) is positively gone; incomplete or foreign evidence stays unknown, no author restarts automatically, and an explicit new event continues from retained facts as a new turn. Wire shape: CREATING_SKILLS "Presence continuation".

Reentry keeps the exact observed rows and read gaps in an immutable `presence_reentry` checkpoint in the existing task artifact store, read through the caller's existing task-read scope (`get_task_result(task_id, presence_reentry_sha256, …)`, paged by `presence_reentry_offset`); no reader or capability is added at reentry. Missing, replaced, truncated or malformed sources remain gaps (`history_source_changed`), never empty-complete, and full observed text is not proof of complete history. Transport inbox observations (`presence_observations.py`; `event.conversation.transport_queue` or authenticated `POST /presence/work/{continuation_ref}`) are dated observations of queued events, never inbox certainty, admission or delivery proof; no received snapshot means unknown.

Entry and receipts key on `presence_bindings.conversation_key` (empty thread `0`). The durable `first_lent_at` anchors later parks and terminal writes, so a returning author updates its own open entry without replacing a newer turn's pointer; `open_turns` retains each unfinished author independently. Outcomes are `message`, `silent`, `tool_delivered` and `deferred`; deferred requires admission, and orphaned children replay silent. `peer_roster.independent_message_target` admits `forward_to_worker` to a source-bound RUNNING turn as peer context, not an owner directive. Owner chat and consciousness at Act or above may `initiate_presence` on an enabled binding.

A binding's own work is an independent root carrying its nonempty binding id (`presence_related_work`); other bindings, owner roots, inline turns and rows without that provenance are never attributed. Host-bound readers and `steer_task` address that binding’s work (`presence_scope=own_binding`); task-result reads, cancel and selected forward also reach the caller’s own tree. A selected global reader stays global. A delegated descendant inherits the ceiling plus only `metadata.presence_binding_authority`, never the speaker's `metadata.presence`, and its follow-ups carry `presence_root_carrier`: related work that never speaks. Promotion of a turn to a task copies the ceiling, cost and return context by value and keeps Project, workspace and source (§11.1 `task_contract`). The ceiling covers knowledge, scratchpad, identity and history, never correspondent-tool or owner-command authority (profile admission: §6 Skills and extensions).

`presence_context.py` supplies route facts and frames incoming speech as observation, distinct from initiation or inherited work; the model chooses concise participation or silence, and early speech goes through selected send tools, never Working forwarding. `presence_finish` enters the common completion checks after the tool, control and budget tail. A forced final is the internal record: only a valid `presence_finish` declared inside that one call speaks; anything else says nothing new and records `presence_declaration`. Host-authored text stays owner-side, and a tool-send `finish_note` is never prior speech.

Receipt reporting is negotiated per turn (wire fields: CREATING_SKILLS "Reporting actual Presence delivery"); `presence_delivery.py` accepts authenticated `POST /presence/delivery` observations through the chat writer. Mode 1 writes outgoing history on provider receipts; mode 0 keeps an authored, delivery-unconfirmed row. Speech is typed `presence_delivery`, never a task-finalizing untyped row; failed or uncertain attempts are System facts. Receipts prove writing, not reading: identical readable reports deduplicate, conflicting ones refuse, and a malformed retained row makes the projection `history_coverage=gapped`, where `duplicate=false` means only that no matching readable receipt was indexed. Transport outboxes own provider receipts and their report backoff; a slow or failed report neither resends nor blocks delivery. A post-task reflection reads these rows for its task lineage (§6 Post-task reflection): `host_bound` by a nonempty row `task_id`, otherwise `skill_claimed` by `origin.task_id`, neither a provider audit.

### Companion processes

Companion processes are host-supervised: reviewed manifest-declared descriptors enter durable custody, reconcile after lifecycle changes and restart, and stop on disable, unload or panic. `state/extension_generation.json` carries the opposite direction, the server's published live set, which a running task worker adopts at a task's start or at a dispatch miss, so an enable after boot is not invisible until the pool respawns. Worker-side changes write durable reconcile requests (`state/extension_reconcile/`) rather than spawning server-owned children, and every reconcile state names the process that answered. Health is process-qualified: aggregate and Skills UI health take the server observation as authority and expose the worker observation only as a qualifier, so a failed handoff cannot advance `last_known_good`; restart-budget exhaustion persists a terminal reason cleared only by a later successful start. A companion's cwd is the reviewed payload directory, so a payload edit stales review before reload instead of silently mutating a live process. The live projection is `state/extension_companions.json`.

### Chat-id delivery

Each message has exactly ONE destination. Chat IDs are values; absence is `None` (§11.1 `chat_id_policy`). `HIDDEN_CHAT_ID` (0) is the real hidden destination for Skill Review and unbound headless work, with no browser reader. `message_bus.notification_chat_route` decides where a notice goes; a `chat_id=0` history query coerces to Main, which excludes chat-0 rows. Only durable lineage binding brings them to a Project; negative A2A ids never enter human streams. An exhausted terminal outbox notice skips chat 0 because it has no reader, while the durable incident and saved message remain; only positive same-id, same-destination evidence suppresses that notice (`terminal_delivery`), never a bare delivered id or a missing ACK. Memory and consolidation provenance follows the same value/`None` policy: a per-window registry snapshot names Main and the current Projects with stable chat ids, missing or ambiguous values stay explicit and never default to Main, and a presence room is named only by transport facts that re-derive its chat id. These labels are read-only source attribution and alter no routing, visibility or delivery state.
