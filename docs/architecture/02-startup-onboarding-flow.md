# 2. Startup / Onboarding Flow

Startup sequences launcher preconditions, gateway onboarding and one atomic save of settings, next-boot runtime mode and install-time presets. Two rules: launcher and server boot normalization never create `settings.json` (fresh-install latches need its absence); the supervisor starts only with structurally sufficient provider configuration. A supervisorless gateway is supported, not a second server, mode or onboarding state machine. Automatic intent (`--launch-intent automatic`; direct `server.py`: `OUROBOROS_LAUNCH_INTENT=automatic`) passes `launcher_bootstrap.automatic_launch_allowed`: after Panic it exits 0 before startup, marker intact; the launcher's intent overrides its child's inherited one; owner or default intent starts normally. Containers: [DEPLOYMENT](../DEPLOYMENT.md#containers).

### Boot order

Before the server, the launcher prepares platform UI (or Linux browser mode), takes the single-instance lock, verifies Git, prepares `--runtime-venv` and validates/bootstraps the embedded seed. Its lifecycle thread (exit 42, crash fuse: §1 Runtime topology) awaits the proven endpoint; onboarding uses that server before the shell/browser opens. The server starts the gateway, then the supervisor/worker pool only after `has_startup_ready_provider()`, event-bus setup and extension reload: an overdue note on the first scheduler tick would otherwise miss a late subscriber (Telegram).

Onboarding follows the gateway: subscription login is a live `/api/*` conversation, not a form field. `launcher_onboarding.py` owns presentation, never settings writes. Changed boot-pinned values recycle the managed server without counting a crash.

`has_startup_ready_provider()` (key list: `server_runtime.py`) is a structural gate: any non-empty recognized remote configuration or active task-capable local routing flag passes; it probes no network, credential, entitlement, model or local process. `LOCAL_MODEL_SOURCE` alone is insufficient; `USE_LOCAL_HEAVY` is migration input only. On a false gate the server marks startup complete without workers and the web UI serves the blocking onboarding overlay; a later passing settings save hot-starts the supervisor.

`store_switch.start` opens the import window before HTTP. Its thread resumes pending switches (restarting if switched), otherwise `startup_migrations.py` calls `store_import.ensure_current_store` to import/reconcile legacy facts into `state/current.sqlite` (older writers' absent/NULL flags derived) and stamp `state/migrations.json`. Legacy questions then bind a quiz address once, only from a stable capture's unique publication row (ask-time chat/routing prove nothing); others stay `question:` unknowns (unstable history: one boot retry, then explicit rebuild). Until publication, writes and task/history reads return 503 `migrating`; readers retry every 700 ms. Supervisor, recovery and providerless readiness wait; failures keep it open without re-import. After owner binding, `store_switch.startup_notice` reports each failed switch once (`reported` in `switch_progress.json`). Recovery reads store sets. `supervisor.jsonl` records lifecycle durations and process age at readiness. Explicit seal audits (`startup_historical_audit`, `startup_migrations` rebuild) and packing share `finish_maintenance_job`: publish custody, recheck Stop, record phase under their own schema/error policy.

### Onboarding wizard and completion

Desktop opens `/onboarding`, the blocking overlay frames it, and a browser opens it directly. The applied interface directory may supply `onboarding.html` (§4); otherwise, or with `?builtin=1`, the core renders `onboarding_template.html` with the `settings_setup_contract` bootstrap and the wholly builtin `/onboarding/static` module graph. `/api/onboarding` remains the readiness probe (204 when ready, otherwise builtin HTML). These reads and `/api/onboarding/bootstrap` persist nothing: creating `settings.json` would disqualify install-time latches. Custom pages use the same HTTP writer and existing host handoffs (CLIENT_CONTRACT §4). The builtin wizard boots `i18n.js bootLanguage`; its Summary stages the shared Language control (`settings_language.js`), applied only after completion saves settings. Launcher dialogs, Linux browser-fallback and Colab bootstrap stay English.

Steps: Accounts, Models, Review, Budget, Summary; context mode stays outside the wizard. Accounts mounts the shared login cards in `full` mode, because `compact` omits the paste-code entry a Claude login needs when its localhost callback cannot complete. Its account facts come from the shared Claudexor status store and become the completion payload's `subscriptionsConnected` declaration: a request to look at the daemon, not an authority. The bootstrap carries settings-file absence as display-only `freshInstall`: a new install takes the provider's Main/Light/Vision/Fallback defaults (Z.ai Vision is the image-capable Flash when Main is remote) and, if subscription-only, clears untouched API suggestions; moving Main local withdraws only the generated Vision suggestion. Owner edits and stored choices stay (Provider defaulting). Completion re-proves freshness server-side.

Completion is one HTTP conversation on every host, `POST /api/onboarding/complete` (`gateway/onboarding.py`; step order: its docstring), so providers and runtime mode cannot be left half-saved. Its single write, re-proved under the settings lock, persists settings, next-boot runtime mode, the fresh-install `OUROBOROS_SAFETY_MODE=light` default no other endpoint may author, the one-shot preset marker and the durable completion fact; the supervisor starts only then. Install time requires three proofs (`gateway/onboarding.py::preset_eligible`): onboarding never completed here, no preset generation applied, no `settings.json` yet; three, since an old install's failed key alone yields "no startup-ready provider", and a preset there would overwrite the owner's reviewer choices. A completion failing after bytes reached disk reports it saved plus the failing stage; one outliving the shared settings-writer bound answers 503 `settings_save_timeout` with `saved: null`, and the wizard offers "Check status", not a blind re-save. Only the exact success envelope is a completion (it carries the saved runtime mode and restart receipt); a boot-pinned change then shows the restart card in the framed overlay and the saved-but-restart-required screen in a plain tab.

Validation (`settings_setup_contract.validate_setup_payload`, shared by desktop and web wizard via `onboarding_wizard.py`) is structural: at least one exposed remote configuration, selected managed model source or local model source; Main is required, other slots keep inheritance/empty semantics; enforcement and runtime mode are closed enums, budgets finite. Credential length is checked only on fields the payload changes: rejecting an unchanged short stored value would discard the whole form, including its own repair.

### Install-time agent presets

`ouroboros/subscription_install_presets.py` is a pure compiler for sibling task actors, the review pool's Reviewer marks and model assignments (emission rules and Agy-neutrality contract: its docstring). API-only and local-only installs need only normalized settings. A declared subscription makes `gateway/onboarding.py` read one live account snapshot and the raw-model source catalog before the settings transaction: the authority for supported harnesses, exact model ids and enabled accounts. Durable seat facts (kind, enabled, verified) decide the once-only preset, not the hour's quota reading: a spent Claude window at save time must not yield a permanent Codex-only preset. Task-actor rows stay unpinned and grow linearly; a fresh install's reviewers are catalog rows the preset marks `review_eligible` (an unmarked generated catalog gains the factory API rows), while an owner-configured roster is validated, not regenerated. Missing required discovery is a typed refusal before any write. `POST /api/onboarding/subagents/preview` runs the same compiler on the open draft without persisting; the editable result becomes `OUROBOROS_SUBAGENTS`.

Accounts reads raw model-source metadata independent of that optional proposal: a known source permits manual model entry even if its inventory or the preset fails, and an agent-only connection does not invent Main. If automatic assignments fail, the owner can re-route every marked row onto the selected Main (`gateway/onboarding.review_rows_on_main`) without another daemon read; the pool's count, identities and effort stay, as do unmarked task actors. Finish then saves the visible draft, preset skipped, and a draft with rows but no mark saves only with the owner's explicit `allow_empty_review_pool`; recovery closes onboarding without a preset marker and later changes stay manual in Settings.

### Provider defaulting

Readiness and defaulting are separate. A Main, Light or Fallbacks slot neither the document nor an operator variable sets (not our echo: §7) is proposed from configured access per read (`server_runtime.provider_slot_proposals`): the exclusive direct provider's ids (§7 Direct-provider routes), blank Light/Fallbacks if local-only (unless that lane alone runs local), else shipped defaults. For an unset Main, multi-direct/compatible access without OpenRouter retains the shipped id; if unusable, no reviewers are minted (log: `OUROBOROS_MODEL`); the wizard proposes blank slots. A saved value (former default, blank, unreachable route) beats the environment, only respelled onto the exclusive provider; blank Main runs as `model_slots._main_model` reads it. Only a Settings edit, the wizard and Colab author an absent slot or never-configured catalog (`unedited_unauthored_slots`, `repropose_unedited_catalog`); a wait card authors only its model slot.

### Packaged seed and managed checkout

The packaged seed (§8 Build scripts) comes from a clean named checkout. A `--seed-bundle` host (Android, the managed container) keeps its seed's own `VERSION`, bundle and manifest; its exit 42 re-executes the repository's launcher on the same interpreter (`--runtime-venv` too, minus options an older launcher lacks); the seed is never rebuilt or relabelled. The launcher validates manifest fields and bundle SHA-256, not per-file membership: clone-time Git verification already proves the manifest's source object exists and equals checked-out HEAD.

`ensure_managed_repo()` owns packaged checkout bootstrap. A first install clones the bundle into a temporary checkout, verifies and configures the pinned source SHA, managed branches and remotes, then moves it into `repo/`. Once a managed git checkout exists, a changed application manifest never archives or swaps its working tree: bootstrap refreshes managed metadata and the official `managed` remote in place, preserving the local branch tip and owner edits. Ordinary packaged restart does no network fetch; moving to an approved official SHA belongs to `supervisor/git_ops.checkout_and_reset`, and `origin` stays optional personal persistence, not the update authority.

Bootstrap also creates the initial world profile when absent and seeds launcher-owned native skills without resurrecting an intentionally deleted seed. `launcher_bootstrap._per_skill_version_resync` overwrites marker-owned payloads whose manifest version differs in either direction and keeps installed bytes and lifecycle state on equal versions, so a bundled payload change must bump that skill's own manifest version, independent of the application version. After exit 42 the launcher refreshes bundle metadata and syncs dependencies before starting the edited body. A failed install gets one visible retry (`launcher.py`); a second failure is logged while startup continues under the crash fuse: silent pip failures obscure later ImportError, but refusing every offline restart would break checkouts with requirements already installed.

### Rescue and dependency sync

Bootstrap rescue (`supervisor.git_ops`; §10, invariant 9) writes a merge-aware directory before reset or clean: `rescue_meta.json`, porcelain status, `changes.diff` as raw bytes to preserve merge resolutions a stash cannot capture, a stash-created rescue ref when possible, copied untracked files with completeness metadata and unpushed-commit evidence (`git_ops_rescue.py`). An incomplete snapshot blocks `rescue_and_reset`, never licensing loss of what it missed. Normal managed bootstrap then cleans back to the local branch's own HEAD, not `managed/<branch>`.

All destructive update rollbacks use `rollback_managed_update`; it and boot re-materialization rescue afresh first: the pre-update copy lacks the resolver's work. Failed rescue is disclosed, never blocking; unreadable status counts as dirty. `rollback_rescue` prevents duplicate snapshots on retry. Rescue stays outside Evolution, lest unrelated rollback abandon its cycle. Re-materialization re-creates a dirty tree, not the rescued edits. A rollback whose whole target is verified present runs no destructive Git command; only a stash restore awaits a held lock. A replace refused taking its first index lock abandons only its transaction (rescue/keep refs stay); Restore's single, non-repairing reset so refused returns unrestarted; others stay fenced. Only the store switch moves to a store-less target. Managed bootstrap reports returned failures (`server_restart._noticed_bootstrap`), not deliberate deferrals. A landed update keeps its identity/smoke authority despite a failed redundant checkout; adoption needs a successful bootstrap.

An active Evolution transaction or managed merge uses `rescue_and_block` to preserve the tree and pause Evolution; otherwise startup uses `rescue_and_reset`. Dependency sync runs pip only when the requirements, interpreter or target fingerprint change. Source/local-dev entry skips the reset and runs dependency sync plus the import test; `OUROBOROS_PYTEST_ACTIVE=1` suppresses only dependency sync. Destructive bootstrap requires the launcher marker and a matching `OUROBOROS_MANAGED_REPO_DIR` or managed metadata; a copied marker without matching identity runs as local-dev. `runtime_environ`, `ProcessContainer.spawn` and the server re-exec scrub both variables.

### Interpreters

`server.py` sets `OUROBOROS_AGENT_PYTHON` from its actual interpreter right after binding the repo import root, before workers or review subprocesses start; hermetic commit/review preflight uses that handle (then `sys.executable`, then `python3`) so tests run in the environment with Ouroboros dependencies. User process tools have a separate surface-aware resolver, `ouroboros/process_interpreters.py` (its docstring: priority ladder; rule: DEVELOPMENT "Mutation Attribution Rule"): an unversioned `python`/`python3` resolves once before the deterministic guards, so guard and handler see one argv, and bare `node` after the dispatch gates, because its health probe executes the candidate; nothing installs, and only an unprovable system interpreter fails closed.

### Body switch at entry

Every entry (`server.py`, the module CLI, the source and Android launcher, a packaged launcher starting `repo/server.py`) first runs the stdlib hook at the top of `ouroboros/__init__.py`; with no pointer in the checkout's Git dir it costs one failed `open`. An armed body adoption (authorization and arming: §6 Own-body candidates) runs the helper captured in `state/body_adoption/`: each changed file is replaced atomically, then the index entries, the branch compare-and-swap last, then a fresh process takes over (exit 42 under a launcher, whose cycle syncs dependencies and the native host; exec otherwise, after the stored dependency command). An interrupted switch resumes by content at the next entry. Bytes that are neither side are never overwritten: the transition is abandoned onto the coherent old tree, handed to a fresh process when the current one began on a half-switched tree; a moved HEAD or unusable helper stops the boot with exit 3 instead of importing a mixed tree (`body_switch.py`: file, cache and index rules). A failed dependency sync returns the files; installed packages may stay changed. The managed boot after a switch, or a returned or still-open transition of this checkout (`holds_checkout`), skips its reset and clean; a boot whose bootstrap failed settles the adoption as unready, not adopted. After exit 42 the launcher re-executes itself only when the landed checkout changed a module it had loaded; a packaged launcher counts its bundle-imported helpers under their repository paths and carries its immutable bundle via `--seed-bundle` into that checkout launcher's next reconciliation.
