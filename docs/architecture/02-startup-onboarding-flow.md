# 2. Startup / Onboarding Flow

Startup orders launcher checks, gateway onboarding and an atomic save of settings, next-boot mode and install-time presets. Boot normalization never creates `settings.json`: fresh-install latches need its absence. Sufficient provider configuration starts the optional supervisor. Automatic intent (`--launch-intent automatic`; direct server: `OUROBOROS_LAUNCH_INTENT=automatic`) passes `launcher_bootstrap.automatic_launch_allowed`: after Panic it exits 0 before startup, marker intact. Launcher intent overrides the child's inherited intent; owner/default intent starts normally. Containers: [DEPLOYMENT](../DEPLOYMENT.md#containers).

### Boot order

`server_boot.mcp_startup` makes the server the only MCP lister, pruning then listing in background (§6).

UI preparation (Linux: browser), PID lock and automatic-intent check precede activation/Windows tray and Git/venv/seed bootstrap. `launcher_bootstrap` reaps noninteractive commands on completion or Quit/Panic: Jobs on Windows, lifelines on source POSIX, group/token custody without an abrupt-death guardian on frozen POSIX. OS installers keep terminal semantics and captured roots; shutdown during another bootstrap command also requests their stop. The lifecycle thread (exit 42, crash fuse: §1) probes `/api/health` while its child lives (`launcher_readiness.py`); exit before serving fails startup. Readiness permits onboarding, then shell/browser.

Before serving, the lifespan admits the data root, applies settings/UI/runtime-mode baseline, starts the WebSocket heartbeat and opens the store's import window (`store_switch.start`). Data-, extension- and child-dependent work runs in the lifespan-owned boot coordinator (`server_liveness.start_boot_coordinator`; steps: `server_boot.py`), ending with store and supervisor publication outcomes. `/api/health` answers 200 as soon as the socket serves and carries the `boot` document (`gateway/health_contracts.py`: `phase` starting → serving → ready | failed, `dialogue_ready`, `tasks_ready`, steps, jobs), which `/api/state` repeats for the chat header. A fail-soft step (an extension that did not load) is reported failed and the boot goes on; an unpublished store or a failed supervisor init fails the phase with its cause.

Dialogue precedes repairs. At store publication (`store_switch.when_ready`), the first coordinator step publishes bridge/bus (`server._open_dialogue`): owner messages enter canonical chat with their turn waiting for an executor while the supervisor recovers, then attaches. The supervisor/worker pool needs `has_startup_ready_provider()`, store publication and `_extensions_ready`, set after extension bus subscriptions so the first scheduler tick cannot miss Telegram or another late subscriber. `tasks_ready` (pooled admission, `supervisor_ready`) stays the supervisor's recovery outcome; chat turns do not wait for it. Before the bridge exists, `initialization_notice` refuses the frame and explains why it was not saved. Colab and CLI `--start` wait for `boot.dialogue_ready` while the server lives, ending on `phase: failed`, never a clock.

Onboarding follows the gateway: subscription login is a live `/api/*` conversation, not a form field. `launcher_onboarding.py` owns presentation, never settings writes. Changed boot-pinned values recycle the managed server without counting a crash.

`has_startup_ready_provider()` (`server_runtime.py`) accepts nonempty recognized remote configuration or active task-capable local routing; it probes no network, credentials, entitlement, model or process. `LOCAL_MODEL_SOURCE` alone fails; `USE_LOCAL_HEAVY` is migration input only. A false gate marks startup complete without workers and shows the blocking onboarding overlay; a passing settings save hot-starts the supervisor.

`store_switch.start` resumes switches (restart if switched), else calls `prepare_startup_state(initialize_journal=True)`: one read transaction for a clean root, plus existing child headers for journal compatibility ([USAGE_STORE](../USAGE_STORE.md) §1), without history reads. NULL flags, old schema or changed mounts trigger preparation; `job:current_store_import` resumes children; stamped absence is `StoreLost`. Child writes import; reads never do. `body_sha` grants no journal authority.

Before `_bootstrap_supervisor_repo` overwrites `state/state.json.current_sha`, `_run_supervisor` waits in `require_published`; boot compares that SHA with `meta.last_store_body.sha`, and a changed, missing or unreadable one queues `legacy_reconcile` once per observed stamp (a stamp that never changes, as on bootstraps that do not write it, is reconciled once), a maintenance job (`store_import.run_legacy_reconcile`; never in the lifespan or supervisor; manual: `python -m ouroboros.store_import --reconcile-legacy [--root PATH]`; baseline/conflict limits: [PERSISTENCE](../PERSISTENCE.md)). Cancel/question work is generation-gated: only unique stable publication evidence binds a question (ask-time routing proves nothing); others stay `question:` unknowns, and unstable history gets one maintenance retry, then explicit rebuild; maintenance also classifies old-body asks.

Fresh current/dialogue/usage stores commit schema, headers and seeds once before rename; `store.connect` keeps FULL/journal policy. Until publication, writes and task/history return 503 `migrating` (700 ms retries); supervisor/recovery/providerless readiness wait. Failures keep import open. After owner binding, `startup_notice` reports switches once (`switch_progress.json.reported`). Recovery reads sets; timings go to `supervisor.jsonl`. Seal audits/packing share `finish_maintenance_job`.

With both state copies absent, `state_initialization.supervisor_evidence` counts a nonempty chat stream in `state/dialog.sqlite` (before cutover, a nonempty legacy chat file by stat) as prior history; an unreadable store is unknown and mints no identity, and the probe creates no store or import job.

### Onboarding wizard and completion

Desktop opens `/onboarding`, the blocking overlay frames it, and a browser opens it directly. The applied interface directory may supply `onboarding.html` (§4); otherwise, or with `?builtin=1`, the core renders `onboarding_template.html` with the `settings_setup_contract` bootstrap and the wholly builtin `/onboarding/static` module graph. `/api/onboarding` stays the readiness probe (204 when ready, otherwise builtin HTML). These reads and `/api/onboarding/bootstrap` persist nothing (same latches). Custom pages use the same HTTP writer and existing host handoffs (CLIENT_CONTRACT §4). The builtin wizard boots `i18n.js bootLanguage`; its Summary stages the shared Language control (`settings_language.js`), applied only after completion saves settings. Launcher dialogs, Linux browser-fallback and Colab bootstrap stay English.

Steps: Accounts, Models, Review, Budget, Summary; context mode stays outside the wizard. Accounts mounts the shared login cards in `full` mode, because `compact` omits the paste-code entry a Claude login needs when its localhost callback fails. Its account facts come from the shared Claudexor status store and become the completion payload's `subscriptionsConnected` declaration: a request to look at the daemon, not an authority. The bootstrap carries settings-file absence as display-only `freshInstall`: a new install takes the provider's Main/Light/Vision/Fallback defaults (Z.ai Vision is the image-capable Flash when Main is remote) and, if subscription-only, clears untouched API suggestions; moving Main local withdraws only the generated Vision suggestion. Owner edits and stored choices stay (Provider defaulting).

Completion is one HTTP conversation on every host, `POST /api/onboarding/complete` (`gateway/onboarding.py`; step order: its docstring), so providers and runtime mode cannot be half-saved. Its single write, re-proved under the settings lock, persists settings, next-boot runtime mode, the fresh-install `OUROBOROS_SAFETY_MODE=light` default no other endpoint may author, the one-shot preset marker, the durable completion fact and client `attempt_id`; only then does the supervisor start. Install time is three proofs together (`gateway/onboarding.py::preset_eligible`): onboarding never completed here, no preset generation applied, no `settings.json` yet, because an old install whose key fails reaches "no startup-ready provider" alone and a preset there would overwrite the owner's reviewer choices. A completion failing after its write reports it saved and the failing stage; one outliving the settings-writer bound answers 503 `settings_save_timeout`. "Check status" then reads that attempt back (`GET /api/onboarding/complete`), as after a lost answer: never a re-save, nor readiness an older provider passes. Only that exact success envelope (runtime mode, restart receipt) completes; a boot-pinned change then shows the overlay's restart card or a plain tab's saved-but-restart-required screen.

Accounts shares Settings' connection editor; masked rows pass through preview/completion. `validate_setup_payload` restores keys by `(kind, name)` and requires remote/local/subscription access and Main; other roles keep blank/inheritance. Enforcement/runtime enums are closed, budgets finite. Compatible keys are optional; other changed keys are length-checked. Discovery suggests per-server models.

### Install-time agent presets

`subscription_install_presets.py` compiles actors, Reviewer marks and models (emission/Agy rules: its docstring). API/local installs need normalized settings; declared subscriptions make `gateway/onboarding.py` read live accounts and the raw-model catalog before the settings transaction, establishing harnesses, exact IDs and enabled accounts. Raw managed proposals leave Safety blank to inherit Light's binding; explicit pins stay. Durable kind/enabled/verified facts decide the once-only preset, never current quota: an exhausted window must not permanently exclude its harness. Unpinned actors grow linearly. Fresh reviewers carry `review_eligible`; an unmarked generated catalog gains factory API rows, while an owner roster is validated, not regenerated. Codex prefers 6.1 Sol, then 5.6 when discovery lacks 6.1; preview and receipt explain that choice, never a runtime substitution. Missing required discovery refuses before writing. `POST /api/onboarding/subagents/preview` compiles without persisting; its editable result becomes `OUROBOROS_SUBAGENTS`.

Accounts reads raw model-source metadata apart from that optional proposal: a known source permits manual model entry even if its inventory or the preset fails; an agent-only connection invents no Main. If automatic assignments fail, the owner can re-route every marked row onto the selected Main (`gateway/onboarding.review_rows_on_main`) without another daemon read; the pool's count, identities and effort stay, as do unmarked task actors. Finish then saves the visible draft, preset skipped, under §7's one review-pool judge; recovery closes onboarding without a preset marker and later changes stay manual in Settings.

### Provider defaulting

Readiness and defaulting are separate. A Main, Light or Fallbacks slot set by neither the document nor an operator variable (not our echo: §7) is proposed from configured access per read (`server_runtime.provider_slot_proposals`): the exclusive direct provider's ids (§7 Direct-provider routes), blank Light/Fallbacks if local-only (unless that lane alone runs local), else shipped defaults. An unset Main under multi-direct/compatible access without OpenRouter keeps the shipped id; if unusable, it mints no reviewers (log: `OUROBOROS_MODEL`); the wizard proposes blank slots. Saved values (former default, blank, unreachable route) beat the environment: Main/Light/Fallbacks may respell onto the exclusive provider; Vision/Consciousness stay exact; blank Main runs as `model_slots._main_model` reads it. Only a Settings edit, the wizard and Colab author an absent value or never-configured catalog (`unedited_unauthored_slots`, `repropose_unedited_catalog`); a wait card authors only its model slot.

### Packaged seed and managed checkout

The seed (§8), a clean named checkout, is never rebuilt/relabelled. Android/container hosts keep VERSION/bundle/manifest; validation checks fields/bundle SHA-256; Git proves source/HEAD.

`ensure_managed_repo()` clones temporarily, verifies the SHA, configures branches/remotes and moves to `repo/`. Existing tips/owner edits survive: changed manifests refresh metadata/`managed`, never replace/archive the tree. Restart fetches nothing; `supervisor/git_ops.checkout_and_reset` applies approved official SHAs.

`launcher_bootstrap.exec_source_launcher` adopts changed helpers: packaged trees at cold start, loaded helpers at exit 42, `/app` included. Windows quotes argv, hides GUI successors and keeps CLI consoles. Every handoff probes source imports before teardown; macOS checks `MACOS_SOURCE_ENTRY_PROTOCOL`, then uses the signed entry (§8), retaining app identity/profile and venv option. Body/venv/probes use plain Python; other successors drop consumed `--runtime-venv`. Stop fences teardown/spawn; the icon leaves before unlock. Refusal retakes the lock and restores the shell unless stopping; a released lock is never released again. Probe refusal keeps the shell; post-spawn crashes have no fallback. Commits select changes; working files execute. Plain-Python Windows window/taskbar and Linux WM_CLASS identity stay unqualified. Cold adoption needs one corrected archive: Update cannot patch old executables/add macOS entries. Legacy profiles stay intact.

Pre-import Windows repair respawns legacy GUI handoffs hidden: matching PyInstaller archive/GUI PE, seed, sole visible console, one-use entry marker. Classic-console visibility cannot qualify Windows Terminal/ConPTY. Old CRT quoting can fail before repair on spaced paths: use the corrected archive.

Bootstrap creates an absent world profile; `verify_system_state` refreshes its measured block (§6). Built-ins (`skill_builtin.py`): fresh installs get ticked, platform-eligible skills (computer use, `ui_design`). Upgrades offer each default-on built-in once, respecting Off and removal. Startup re-seeds unmodified marker-owned copies on a manifest-version change, keeping enablement and unchanged-request grants; bundled changes bump that version. Edited copies await the owner's choice. Dropped built-ins: unchanged ones go after a clean re-seed (grants kept), edited ones become the owner's. An enabled Unix copy installed without an `os` limit keeps Windows remote eligibility (`legacy_remote_platform=win32`; not recorded launcher auto-ON; §13). Off the boot path, receipt or not, the server (never the frozen launcher) readies admitted skills on or requested on, packageless ones too; only extensions reload; failures retry next boot. `state/native_seed.json` records the committed `skills` tree: unchanged clean trees cost one receipt read and two Git queries. A changed or unknown tree invalidates it before reconciliation; successful source phases restore it. Package work and unfulfilled turn-ons never hold that source receipt. After exit 42 the launcher refreshes bundle metadata/dependencies before starting the edited body. A failed install gets one visible retry (`launcher.py`); a second stays logged under the crash fuse, so a lost pip failure cannot hide behind a later ImportError; offline checkouts holding their requirements still restart.

### Rescue and dependency sync

Bootstrap rescue (`supervisor.git_ops`; §10, invariant 9) writes a merge-aware directory before reset or clean: `rescue_meta.json`, porcelain status, `changes.diff` as raw bytes to keep merge resolutions a stash cannot capture, a stash-created rescue ref when possible, copied untracked files with completeness metadata and unpushed-commit evidence (`git_ops_rescue.py`). An incomplete snapshot blocks `rescue_and_reset`, never licensing loss of what it missed. Normal managed bootstrap then cleans back to the local branch's own HEAD, not `managed/<branch>`.

All destructive update rollbacks use `rollback_managed_update`; it and boot re-materialization rescue afresh first, since the pre-update copy lacks the resolver's work. Failed rescue is disclosed, never blocking; unreadable status counts as dirty; `rollback_rescue` prevents duplicate snapshots on retry. Rescue stays outside Evolution, lest unrelated rollback abandon its cycle. Re-materialization re-creates a dirty tree, not the rescued edits. A rollback whose whole target is verified present runs no destructive Git command; only a stash restore awaits a held lock. A replace refused taking its first index lock abandons only its transaction (rescue/keep refs stay); Restore's single, non-repairing reset so refused returns unrestarted; others stay fenced. Only the store switch moves to a store-less target. Managed bootstrap reports returned failures and fallbacks (`server_restart._noticed_bootstrap`), not deliberate deferrals; a fallback passes the store-switch owner, never booting a recovery point that cannot read the stores. A landed update keeps its identity/smoke authority despite a failed redundant checkout; adoption needs a successful bootstrap.

An active Evolution transaction or managed merge uses `rescue_and_block` to keep the tree and pause Evolution; otherwise startup uses `rescue_and_reset`. Dependency sync runs pip only when the requirements, interpreter or target fingerprint (packaged: bundle content, relative paths) changes. A successful import smoke over an unchanged clean checkout writes `state/git_bootstrap.json` (repository, branch, HEAD, that dependency fingerprint); an exact match next bootstrap skips checkout/reset and the import subprocess, while dirty or unknown state, transaction markers, body adoption or active Evolution prevent reuse, and every checkout or rollback writer invalidates the receipt even at the same HEAD (`git_ops_reset._bootstrap_snapshot`). Source/local-dev entry skips the reset and shares dependency sync and the receipt; `OUROBOROS_PYTEST_ACTIVE=1` suppresses only dependency sync. Destructive bootstrap needs the launcher marker and a matching `OUROBOROS_MANAGED_REPO_DIR` or managed metadata; a copied marker without matching identity runs as local-dev. `runtime_environ`, `ProcessContainer.spawn` and the server re-exec scrub both variables.

### Interpreters

`server.py` sets `OUROBOROS_AGENT_PYTHON` to its actual interpreter on entry, before workers or review subprocesses start; hermetic commit/review preflight uses that handle (then `sys.executable`, then `python3`), so tests run where Ouroboros dependencies live. User process tools have a separate surface-aware resolver, `ouroboros/process_interpreters.py` (its docstring: priority ladder; rule: DEVELOPMENT "Mutation Attribution Rule"): an unversioned `python`/`python3` resolves once before the deterministic guards, so guard and handler see one argv, and bare `node` after the dispatch gates, because its health probe executes the candidate; nothing installs, and only an unprovable interpreter fails closed.

### Body switch at entry

Every entry (`server.py`, the module CLI, the source and Android launcher, a packaged launcher starting `repo/server.py`) first runs the stdlib hook atop `ouroboros/__init__.py`, costing one failed `open` without a pointer in the checkout's Git dir. An armed body adoption (authorization, arming: §6 Own-body candidates) runs the helper captured in `state/body_adoption/` (`body_switch.py`: files replaced atomically, then index entries, the branch compare-and-swap last; an interrupted switch resumes by content at the next entry), then a fresh process takes over (exit 42 under a launcher, whose cycle syncs dependencies and the native host; else exec after the stored dependency command). Bytes matching neither side are never overwritten: the transition is abandoned onto the coherent old tree, handed to a fresh process if the current one began half-switched, and a moved HEAD or unusable helper stops the boot with exit 3, never importing a mixed tree. A failed dependency sync returns the files; installed packages may stay changed. The managed boot after a switch, or a returned or still-open transition of this checkout (`holds_checkout`), skips reset and clean. Handoff follows the seed contract above. Helpers count by named or resolved repository path: macOS Frameworks symlinks lead outside that root. `--seed-bundle` carries the immutable bundle into reconciliation.
