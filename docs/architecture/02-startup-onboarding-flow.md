# 2. Startup / Onboarding Flow

Startup orders launcher preconditions, live-gateway onboarding and one atomic completion that persists settings, next-boot runtime mode and install-time presets together. Two decisions shape it: launcher and server boot normalization leave an absent `settings.json` untouched, because fresh-install latches depend on its absence; and the supervisor starts only when provider configuration is structurally sufficient, so a gateway without a supervisor is a supported state rather than a second server, mode or onboarding state machine. Direct `server.py` entry opts into `launcher_bootstrap.automatic_launch_allowed` with `OUROBOROS_LAUNCH_INTENT=automatic`: after Panic it exits 0 before startup with the marker intact, so a restart policy cannot undo Stop; owner or default intent starts normally. Container policy: [DEPLOYMENT](../DEPLOYMENT.md#container-restart-policy-and-panic).

### Boot order

The launcher prepares the platform UI runtime (or runs the Linux browser-mode probe), acquires the single-instance lock, verifies Git, and validates and bootstraps the embedded managed-repo seed; these are server preconditions, so they run first. It then removes only identity-proven stale server state and ports, starts the lifecycle thread and waits on `/api/health` at the port published in `data/state/server_port`; first-run onboarding is presented against that live server before the pywebview shell or browser presentation opens. The server starts the gateway first and the supervisor/worker pool only when `has_startup_ready_provider()` passes, and then only after the event bus and the extension reload: the first scheduler tick may show an overdue note, and the bus keeps no history for a subscriber (Telegram) that attaches later. Lifecycle thread, exit 42 and the crash fuse: §1 Runtime topology.

Onboarding runs after the gateway because connecting an agent subscription is a live `/api/*` conversation, not a form field. `ouroboros/launcher_onboarding.py` owns the presentation and holds no settings-write authority. When completion reports a boot-pinned value changed, the launcher recycles the managed server instead of counting the exit as a crash.

`has_startup_ready_provider()` (`server_runtime.py` carries the key list) is a structural gate: any non-empty recognized remote configuration or an active task-capable local routing flag passes, and nothing probes network, credential, entitlement, model or local process. `LOCAL_MODEL_SOURCE` alone is insufficient; `USE_LOCAL_HEAVY` is migration input only. When the gate is false the server marks startup complete without workers and the web UI serves the blocking onboarding overlay; a later successful settings save hot-starts the supervisor.

Lifecycle import (`startup_migrations.py`) runs before producers on every startup door: it retries stamped process stops, imports inherited result obligations and open delegated custody once, and stamps `state/migrations.json`; a failed import is logged and boot continues without the dependent recovery. Ordinary recovery reads `state/obligations/`; `supervisor.jsonl` keeps each lifecycle job's duration and a `supervisor_ready` row with the process age. Historical seals are audited only on request (`python -m ouroboros.startup_historical_audit --data-root <root>`, or the explicit `startup_migrations` rebuild), never at boot.

### Onboarding wizard and completion

Every host renders one served page: `GET /onboarding` returns `onboarding_template.html` with the `settings_setup_contract` bootstrap injected and loads `web/modules/onboarding_wizard.js` and the wizard CSS as static assets, so the steps import the same modules as the rest of the UI. The desktop setup window opens that URL, the blocking overlay frames it, a browser owner opens it directly; `GET /api/onboarding` is the readiness probe (204 once the gate passes, otherwise the page). Both reads normalize what they display and persist nothing, because a read that created `settings.json` would disqualify the install-time latches. The page boots the SPA's translation overlay (`i18n.js bootLanguage`), so an install whose language is already chosen reads translated from the first screen; the Summary step carries the same Language control as Settings → Appearance (`settings_language.js`) in staging mode, applied through the one language writer only after the completion transaction wrote `settings.json`. Pre-UI surfaces (launcher dialogs, the Linux browser-fallback page, the Colab bootstrap) stay English.

Steps: Accounts, Models, Review, Budget, Summary; context mode stays outside the wizard. Accounts mounts the shared login cards in `full` mode, because `compact` omits the paste-code entry a Claude login needs when its localhost callback cannot complete. Its account facts come from the shared Claudexor status store and become the completion payload's `subscriptionsConnected` declaration: a request to look at the daemon, not an authority. The bootstrap carries settings-file absence as display-only `freshInstall`: a new install takes the provider's Main/Light/Vision/Fallback defaults (Z.ai Vision is the image-capable Flash when Main is remote) and, if subscription-only, clears untouched API suggestions; moving Main local withdraws only the generated Vision suggestion. Owner edits and stored choices stay, even default-equal or blank. Completion re-proves freshness server-side.

Completion is one HTTP conversation on every host, `POST /api/onboarding/complete` (`gateway/onboarding.py`; its docstring carries the step order), so providers and runtime mode cannot be left half-saved. Its single write, re-proved under the settings lock, persists settings, next-boot runtime mode, the fresh-install `OUROBOROS_SAFETY_MODE=light` default that no other endpoint may author, the one-shot preset marker and the durable completion fact; the supervisor starts only then. Install time is three proofs together (`gateway/onboarding.py::preset_eligible`): onboarding never completed here, no preset generation applied, no `settings.json` yet. Three, because an old install reaches "no startup-ready provider" alone whenever its key stops working, and a preset there would overwrite the owner's own reviewer choices. A completion that fails after bytes reached disk reports that it saved plus the failing stage; one that outlives the shared settings-writer bound answers 503 `settings_save_timeout` with `saved: null`, and the wizard offers "Check status" instead of a blind re-save. Only the exact success envelope is a completion, because the saved runtime mode and the restart receipt live in that body; a boot-pinned change then shows the restart card in the framed overlay and the saved-but-restart-required screen in a plain tab.

Validation (`settings_setup_contract.validate_setup_payload`, shared by the desktop and web wizard through `onboarding_wizard.py`) is structural: at least one exposed remote configuration, selected managed model source or local model source; Main is required while the other slots keep inheritance/empty semantics; enforcement and runtime mode are closed enums and budgets finite. Credential length is checked only on fields changed in the payload: rejecting an unchanged short stored value would discard the whole form, including its own repair.

### Install-time agent presets

`ouroboros/subscription_install_presets.py` is a pure compiler for sibling task actors, the Reviewer marks of the review pool and model assignments (its docstring carries the emission rules and the Agy-neutrality contract). API-only and local-only installs need only normalized settings. A declared subscription makes `gateway/onboarding.py` read one live account snapshot and the raw-model source catalog before the settings transaction; they are the authority for supported harnesses, exact model ids and enabled accounts. Durable seat facts (kind, enabled, verified) decide the once-only preset, not the hour's quota reading: a spent Claude window at save time must not yield a Codex-only preset permanently. Task-actor rows stay unpinned and grow linearly; a fresh install's reviewers are catalog rows the preset marks `review_eligible` (an unmarked generated catalog gains the factory API rows), while an owner-configured roster is validated, not regenerated. Missing required discovery is a typed refusal before any write; no partial preset persists. `POST /api/onboarding/subagents/preview` runs the same compiler against the open draft without persisting, and the editable result becomes `OUROBOROS_SUBAGENTS`.

Accounts reads raw model-source metadata independently of that optional proposal: a known source permits manual model entry even when its inventory or the preset fails, and an agent-only connection does not invent Main. If automatic assignments fail, the owner can re-route every marked row onto the selected Main (`gateway/onboarding.review_rows_on_main`) without another daemon read; the pool's count, identities and effort are kept and unmarked task actors are untouched. Finish then saves the visible draft with the preset skipped, and a draft with no marked row saves only with the owner's explicit `allow_empty_review_pool`; recovery closes onboarding without a preset marker and later changes stay manual in Settings.

### Provider defaulting

Provider readiness and provider defaulting are separate. The exclusive direct-provider rule (§7 Direct-provider routes) selects provider-prefixed defaults and migrates untouched shipped slot values; mixed-provider choices stay owner-editable and OpenRouter keeps router-style routing. An arbitrary OpenAI-compatible endpoint gets no guessed model ids, because compatible servers have no universal safe name; the owner selects explicit `openai-compatible::...` routes. A local-source install with no remote provider clears only untouched shipped remote Light/Fallback values that would be unreachable. This is migration of defaults, not a model allowlist, and not proof that the local server is running.

### Packaged seed and managed checkout

The packaged seed (§8 Build scripts) comes from a clean named checkout. The launcher validates the manifest fields and the bundle SHA-256 but no per-file member set, because clone-time Git verification already proves the manifest's source object exists and the checked-out HEAD equals it.

`ensure_managed_repo()` owns packaged checkout bootstrap. A first install clones the bundle into a temporary checkout, verifies and configures the pinned source SHA and the managed branches and remotes, then moves it into `repo/`. Once a managed git checkout exists, a changed application manifest never archives or swaps out its working tree: bootstrap refreshes managed metadata and the official `managed` remote in place, preserving the local branch tip and owner edits. Ordinary packaged restart performs no network fetch; movement to an approved official SHA belongs to `supervisor/git_ops.checkout_and_reset`, and `origin` stays optional personal persistence, not the update authority.

Bootstrap also creates the initial world profile when absent and seeds launcher-owned native skills without resurrecting an intentionally deleted seed. `launcher_bootstrap._per_skill_version_resync` overwrites marker-owned payloads whose manifest version differs in either direction and keeps installed bytes and lifecycle state when versions are equal, so a bundled payload change must bump that skill's own manifest version, independently of the application version. Dependency installation runs only when checkout or bootstrap metadata changed; after exit 42 the launcher refreshes bundle metadata and synchronizes dependencies before starting the edited body. A failed install gets one visible retry (`launcher.py`); a second failure stays in the logs while startup continues under the crash fuse, because silently losing a pip failure makes a later ImportError inexplicable, while refusing every offline restart would break a checkout whose requirements are already present.

### Rescue and dependency sync

Bootstrap rescue (`supervisor.git_ops`; §10, invariant 9) writes a merge-aware directory before reset or clean: `rescue_meta.json`, porcelain status, `changes.diff` as raw bytes to preserve merge resolutions a stash cannot capture, a stash-created rescue ref when possible, copied untracked files with completeness metadata and unpushed-commit evidence (`git_ops_rescue.py`). An incomplete snapshot blocks `rescue_and_reset`; it is not permission to discard what could not be captured. Normal managed bootstrap then cleans back to the local branch's own HEAD, not to `managed/<branch>`.

Managed update is the second user of that machinery. Every destructive rollback passes one choke point, `rollback_managed_update`, and both it and boot re-materialization take a fresh rescue before the first destructive command, because the pre-update snapshot predates the merge and holds none of the resolver's work. The hook is fail-open: a rescue that cannot be taken never blocks the rollback (it is logged and disclosed), and a `git status` that cannot answer counts as dirty. The rescue is deliberately not linked to an active Evolution transaction, which would flip the campaign's cycle to abandoned for an unrelated reason; the update transaction's own `rollback_rescue` pointer is the replay guard, so a retried rollback takes no duplicate snapshot. Re-materialization re-creates a dirty tree without replaying the rescued edits and must not be read as their return.

An active Evolution transaction or managed merge uses `rescue_and_block` to preserve the tree and pause Evolution; otherwise startup uses `rescue_and_reset`. Dependency sync runs pip only when the requirements, interpreter or target fingerprint changes. Source/local-dev entry skips the reset and runs dependency sync plus the import test; `OUROBOROS_PYTEST_ACTIVE=1` suppresses only dependency sync. Worker-boot checks (`agent_startup_checks.py`) are warnings, never a gate. Destructive bootstrap requires the launcher marker and a matching `OUROBOROS_MANAGED_REPO_DIR` or managed metadata; a copied marker without matching identity runs as local-dev. `runtime_environ`, `ProcessContainer.spawn` and the server re-exec scrub both variables.

### Interpreters

`server.py` establishes `OUROBOROS_AGENT_PYTHON` from its actual interpreter right after binding the repo import root, before workers or review subprocesses start; hermetic commit/review preflight uses that handle (then `sys.executable`, then `python3`) so tests run in the environment that contains Ouroboros dependencies. User process tools have a separate surface-aware resolver, `ouroboros/process_interpreters.py` (its docstring carries the priority ladder): an exact unversioned `python`/`python3` on the public process launch surfaces is resolved once before the deterministic guards, so guard and handler see identical argv; absolute or versioned interpreters, shell bodies and non-Python commands stay literal, and bare `node` resolves after the dispatch gates because its health probe executes the candidate. Resolution never installs dependencies and fails closed only when a system-owned interpreter cannot be proven.

### Body switch at entry

Every entry (`server.py`, the module CLI, the source and Android launcher, a packaged launcher starting `repo/server.py`) first runs the stdlib hook at the top of `ouroboros/__init__.py`; with no pointer in the checkout's Git dir it costs one failed `open`. An armed body adoption (authorization and arming: §6 Own-body candidates) runs the helper captured in `state/body_adoption/`: each changed file is replaced atomically, then the index entries, the branch compare-and-swap last, and the process hands over to a fresh one (exit 42 under a launcher, whose own cycle syncs dependencies and the native host; exec otherwise, after the stored dependency command). An interrupted switch resumes by content at the next entry. Bytes that are neither side are never overwritten: the transition is abandoned onto the coherent old tree, handed to a fresh process when the current one began on a half-switched tree; a moved HEAD or an unusable helper stops the boot with exit 3 rather than importing a mixed tree (`body_switch.py` carries the file, cache and index rules). A failed dependency sync returns the files; installed packages may remain changed. The managed boot after a switch, or a returned or still-open transition of this checkout (`holds_checkout`), skips its reset and clean, and a boot whose bootstrap failed settles the adoption as unready, not adopted. After exit 42 the launcher re-executes itself only when the landed checkout changed a module it had loaded; a packaged launcher counts its bundle-imported helpers under their repository paths and carries its immutable bundle through `--seed-bundle` into that checkout launcher's next reconciliation.
