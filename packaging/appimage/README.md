# Bundled Linux native window candidate (#688)

The selected contract is GTK3 + WebKit2GTK 4.1 inside the x86_64 AppImage, including GI in the frozen launcher and the standalone Python used after source handoff. Playwright WebKit remains a separate browser-tool dependency. The native qualification target is Ubuntu 22.04 x86_64 with Xvfb/Openbox; other desktop and driver combinations remain unqualified.

Build the closure on Ubuntu 22.04 (Jammy) x86_64, targeting glibc 2.35 and the Jammy graphics stack; this is not a promise for older glibc distributions or newer host drivers. `OUROBOROS_BUNDLE_LINUX_GTK=auto` selects it on that builder only; `=1` requires it (release CI), and `=0` retains the previous host-backend build. Non-target builders, including aarch64, keep their existing archive/AppImage path without GI extras or a native-window claim. Missing Jammy build inputs never cause an automatic downgrade. `build_linux.sh` installs the locked `linux-desktop` extra into both interpreters; `Ouroboros.spec` collects GI's typelib graph. After freezing, `scripts/bundle_linux_gtk.py` copies the declared Debian package resources and recursive ELF dependencies, package notices, common license texts, WebKit helpers, GIO TLS modules and GStreamer plugins into `_internal/linux-gtk`. libgirepository reads `GI_TYPELIB_PATH` first and then, silently, its compiled `/usr/lib/x86_64-linux-gnu/girepository-1.0` and Debian's `/usr/lib/girepository-1.0` (gobject-introspection 1.72.0-1), and it loads each typelib's header dependencies eagerly. The builder therefore refuses a shipped typelib whose dependency typelibs are not shipped too, and ships every library a typelib names, so the builder's own `/usr` cannot hide a gap that would break a host without `gir1.2-*` packages; Jammy's `Pango-1.0.typelib` requires `HarfBuzz-0.0`, which `gir1.2-harfbuzz-0.0` supplies. A GI extension may name libpython only if its own interpreter ships that file; the builder's libpython is never copied. The closure manifest records package versions, binary/source-package versions, file hashes, host-library exceptions and relocation edits. Source collection observes every owning binary's source version and refuses multiple versions for one source name before writing the manifest; it never silently keeps only the last version. `_internal` library aliases point to that same closure, preventing PyInstaller from loading a second GLib/WebKit stack. The AppImage packer requires that manifest for native builds; an explicit legacy `=0` build keeps the host-backend path.

`Ouroboros` is a shell entry that saves caller loader/resource values before executing the adjacent frozen `Ouroboros.bin`. AppRun, the tarball and the deb/rpm desktop entry/user unit all reach this same entry; `Ouroboros.bin` is an internal implementation file. `desktop-env.sh` preserves absent versus empty values, including `LD_LIBRARY_PATH_ORIG`, then sets the GUI loader path. PyInstaller 6.22 [treats empty environment values as absent and overwrites the loader backup](https://github.com/pyinstaller/pyinstaller/blob/v6.22.0/bootloader/src/pyi_utils_posix.c), so a Python runtime hook would be too late for this capture. `desktop_media.prepare_linux_bundle` restores resource paths after the frozen GI hooks and selects GTK even in a KDE session. Its `host_environment` returns a copy with the caller values restored and the private capture fields consumed. The named server, bootstrap, external-browser and external-file seams receive that copy; this is not a claim that every launcher-side POSIX diagnostic helper (such as process/port probes or native-attention helpers) uses it. pywebview 5.4 GTK `_blank` navigation uses a backend-local adapter to the same detached opener. The browser resolver runs in a separate plain Python process because `webbrowser.open` has no environment argument; no temporary global environment swap occurs. In the Jammy `webkit2gtk` 2.50.4 source, release builds ignore the developer-only `WEBKIT_EXEC_PATH` (`ProcessExecutablePathGLib.cpp`) and start every helper from the compiled `PKGLIBEXECDIR` through `g_subprocess_launcher_spawnv` without setting a working directory (`ProcessLauncherGLib.cpp`); the web process opens its injected bundle under `PKGLIBDIR`, which Debian builds as the same directory. The builder replaces bounded, NUL-delimited `/usr` prefixes of those paths and of the dormant bubblewrap/xdg-dbus-proxy helpers with equal-length `././` prefixes; offsets and lengths stay fixed. Read offline, the 2.50.4 package library carries three of the listed prefixes at four sites, while the `libexec` and `share` alternatives are absent and left alone; the native manifest records the actual edits. A relative path resolves against the spawning process's cwd, so the desktop shell keeps `_internal/linux-gtk` as its cwd, including after the existing source-launcher exec, and neither the launcher nor pywebview 5.4 changes it afterwards. Server processes use their repo cwd and caller loader/resource environment; AppRun CLI dispatch bypasses GUI setup and retains the caller's cwd. The source-launcher probe and exec explicitly keep the full GUI environment, including saved caller state, and WebKit helpers inherit the native resources/cwd. These are source and byte expectations, not execution proof. Missing display/backend still uses the existing browser fallback, bridge and close paths. To avoid native startup, use the existing `--no-ui` external-UI mode or unset both `DISPLAY` and `WAYLAND_DISPLAY` for the existing browser/headless path. A graphics-library abort after native initialization begins cannot use that fallback.

## Frozen desktop environment contract (v1)

The prebootloader `desktop-env.sh` and managed `desktop_media.LINUX_DESKTOP_KEYS` share a frozen cross-update vocabulary, documented here as contract v1 (the existing `OUROBOROS_DESKTOP_ENV_SAVED=1` marker, not a new negotiation mechanism). For each key, `OUROBOROS_DESKTOP_HOST_<key>` is empty when absent and `1` followed by its exact value when present, including empty. The 22 keys are:

```
LD_LIBRARY_PATH LD_LIBRARY_PATH_ORIG XDG_DATA_DIRS PYWEBVIEW_GUI
GI_TYPELIB_PATH GIO_MODULE_DIR GIO_EXTRA_MODULES GSETTINGS_SCHEMA_DIR
GTK_DATA_PREFIX GTK_EXE_PREFIX GTK_PATH GTK_IM_MODULE_FILE
GDK_PIXBUF_MODULE_FILE GDK_PIXBUF_MODULEDIR
GST_PLUGIN_SYSTEM_PATH_1_0 GST_PLUGIN_SCANNER PANGO_LIBDIR PANGO_SYSCONFDIR
GST_PLUGIN_PATH GST_PLUGIN_SYSTEM_PATH GST_REGISTRY GST_REGISTRY_FORK
```

Older installed wrappers must work with updated managed source, and newer wrappers with rolled-back source. Do not add, remove, rename or change the encoding of v1 keys in an ordinary source update: the current strict reader requires every snapshot and consumes exactly this vocabulary. A future change needs an explicitly compatible versioned handoff design and old-wrapper/new-source plus new-wrapper/old-source qualification. Today's two lists match; this delta changes neither.

## Host ABI boundary

The OS supplies the kernel, glibc/loader, X11 or Wayland session, graphics drivers, fonts and trust store. The graphics ABI is libglvnd's `libGL.so.1`, `libEGL.so.1`, `libGLdispatch.so.0` and `libGLESv2.so.2` (Ubuntu `libgl1`, `libegl1`, `libglvnd0`, `libgles2`) with Mesa, gbm and drm. The shipped libepoxy (Ubuntu 1.5.10-1, no Debian patches) resolves GLES2 functions for a non-GLX context by dlopening `libGLESv2.so.2` and calls `abort()` when that fails (`src/dispatch_common.c`), so `ldd` never shows it. On a fixture without `libgles2`, native run 39636484833 printed that dlopen failure, and its server logged the launcher gone about 4 s after serving, before any window; the exit status was not recorded. libglvnd describes `libGLESv2` as a wrapper over the dispatch table in `libGLdispatch`, and Ubuntu's `libgles2` 1.4.0-1 depends on exactly `libglvnd0 (= 1.4.0-1)`, which ships `libGLdispatch`, so it is taken from the host with the rest of libglvnd rather than shipped. GTK, WebKitGTK, GI, Soup, ICU and TLS libraries are shipped. The first proposed qualification is Ubuntu 22.04 x86_64 with a mapped X11 window on Xvfb/Openbox. It cannot establish physical-GPU, Wayland, Fedora/Astra/RED OS, microphone or broad codec compatibility. No sandbox-disable environment variable is added. The target is the Jammy graphics stack, not a minimum distro version implying that newer drivers work. The retained closure includes Jammy `libstdc++`, `libgcc_s`, Wayland/X11/xcb, expat, zlib/zstd and libelf; host Mesa/LLVM/vendor modules can resolve those older copies in the same process. GCC [adds GLIBCXX_3.4.31 in GCC 13](https://gcc.gnu.org/onlinedocs/libstdc++/manual/abi.html), beyond the retained GCC 12 library. The [AppImage community excludelist](https://github.com/AppImageCommunity/pkg2appimage/blob/master/excludelist) excludes libstdc++, libxcb, libX11 and libwayland-client for these driver interactions. Broadening the graphics boundary or implementing host-versus-bundle library selection needs a separate design decision and newer-driver tests. This repair changes neither. Native Jammy/Xvfb results cannot discharge that gap.

WebKit's web-process sandbox is off in this design because WebKitGTK's 4.1 API defaults it off, not because of any switch. In 2.50.4, `WebProcessPool` starts with `m_sandboxEnabled { false }`; only the 6.0 API (`ENABLE(2022_GLIB_API)`) enables it for every context, and the 4.1 API leaves it to `webkit_web_context_set_sandbox_enabled`, which pywebview 5.4's GTK backend never calls (it uses `WebContext.get_default()`). WebKit therefore starts `WebKitWebProcess` directly, as for any pywebview 5.4 GTK window on WebKitGTK 4.1. The qualifier records the observed mount namespaces and any bubblewrap/xdg-dbus-proxy process and requires neither outcome. The shipped `bwrap` and `xdg-dbus-proxy` and their relocated paths stay dormant. Enabling the sandbox is a separate security and packaging decision: `BubblewrapLauncher.cpp` passes `PKGLIBEXECDIR` as both bind source and destination, and a relative relocated prefix has not been qualified there.

## Parent-run bounded experiment

`.github/workflows/linux-appimage-native.yml` is dispatch-only, read-only, secretless and separate from the release graph. The parent must register the delegated repair evidence archive before integration, then capture this patch in a research branch/commit. Earlier complete archives remain with the parent; new tests are newly authored, not recovered historical QA. Dispatch that exact branch with `candidate_sha` equal to its 40-character HEAD; the workflow checks both checkout and event SHA. The delegate does not push or dispatch.

```bash
gh workflow run linux-appimage-native.yml --ref <research-branch> -f candidate_sha=<exact-sha>
```

The workflow is bounded to 120 minutes (90 build, 18 native). `native-qualification.Dockerfile` uses the digest-pinned Ubuntu image with the ordinary Ubuntu archive, accepted only with the image's archive keyring (`signed-by`). The dated `snapshot.ubuntu.com` endpoint returned 503 for every suite in run 39601252706, so apt inputs are whatever the archive serves during the build and are not reproducible. The image's own packages are upgraded first because `apt-get source` can fetch only versions the archive still lists; the build keeps the signed `InRelease` files present at its start (`apt-release/`), the installed package list and the manifest's exact binary and source-package versions. uv 0.12.1 has its own digest, Python/Node/Betterleaks/Claudexor retain repository pins, and `uv.lock` pins Python inputs. Build-system dependencies resolved while compiling sdists are not a bit-reproducible lock either: preserve build logs, exported requirements, final package inventory and artifact digest on every run. The normal release-tag guard is untouched. The experiment creates a tagless diagnostic bootstrap seed and uses the production spec, closure builder and AppImage packer; it never publishes, attests, signs, tags or installs the product on the runner.

Build and qualification run under `safe_test` with disposable roots outside Git and no project installation into the dependency environment. The clean desktop container receives only the candidate source and output artifacts, has no installed GTK3/WebKitGTK/GI, no build-library mounts, no host display socket, no external network and runs as a non-root user. Docker's default seccomp filter is lifted only so that a bubblewrap attempt, if WebKit made one, would be observed rather than refused by Docker; the container is not privileged and no WebKit sandbox variable is set either way. This condition is part of the evidence, not a claim about the default Docker sandbox.

`x11_window_identity.py` reads `_NET_CLIENT_LIST` as WINDOW/32 and each client's map state, geometry, `WM_CLASS`, `_NET_WM_PID` and `_NET_WM_NAME` directly through libX11. [EWMH](https://specifications.freedesktop.org/wm/latest/ar01s05.html) specifies the title as UTF8_STRING; [XGetWindowProperty](https://xorg.freedesktop.org/archive/current/doc/libX11/libX11/libX11.html#Obtaining_and_Changing_Window_Properties) returns format-32 data in native C longs (also on LP64). Titles decode strictly as UTF-8, with raw property bytes retained as hex. The qualifier requires the expected launcher PID, class, visible geometry and exact title from the launcher source. Missing properties remain absent, empty titles remain empty, and display/protocol/type/decoding errors fail explicitly. It preserves every poll; it performs no locale conversion or regex title search.

`qualify_linux_appimage.py` starts the actual AppImage and observes fresh Setup, then completes real onboarding with an inert keyless loopback provider. It refuses and counts generation requests, requires zero, and checks a visible Main without the onboarding overlay, screenshot, genuine JavaScript → `MainApi.shell_info()` roundtrip, bundled GTK/WebKit library maps and live bundled WebKit web/network helpers. It records the web process's mount namespace beside the launcher's, plus any bubblewrap/xdg-dbus-proxy process, in `webkit-sandbox.json` without requiring either outcome. A saved HTML suffix instruments only the disposable managed page. That uncommitted suffix can race supervisor bootstrap's reset: a missed witness is a failed qualification, not evidence of a broken native window. The initial Setup image records mapping without paint synchronization; judge rendered Setup separately. It then records a comment-only local fixture commit and repeats through production source handoff, checking the standalone Python executable and bridge source identity. This is cold source handoff, not a live update-feed or restart test. It also runs the unchanged extracted payload's public `Ouroboros` entry directly, as deb/rpm/tarball consumers do, with the same bridge/library/helper assertions. This does not prove package installation. Every case checks the actual server process environment against the caller, including absent versus empty state. No-display and deliberately removed-typelib cases must report browser fallback and stop cleanly. The artifact is not modified for the damaged-backend negative; that case runs a separately extracted copy. All cases use private ports/state and check ordinary close/TERM cleanup; none calls Panic or a model.

Download `issue688-native-<sha>-<attempt>` immediately and register the complete artifact before discarding the run or integrating this candidate. It includes the AppImage and SHA-256, seed/source identities, GTK manifest, matching Debian source archives with hashes, container identities, package lists, raw logs, JUnit, process maps, bridge replies and screenshots. The existing release Linux matrix retains its `ubuntu-latest` artifact label but explicitly runs on `ubuntu-22.04`, upgrades installed packages before source-version collection and installs the same GTK build dependencies. Other platform jobs, tags and release topology are unchanged. Neither release nor this experiment pins apt inputs to a snapshot. Binary relocation modifies WebKit; copying copyright files alone is insufficient. [WebKit licensing](https://webkit.org/licensing-webkit/) includes LGPL/BSD components, and the applicable package notices govern each file. Before any distribution, retain and provide matching source archives (including Debian patches/build scripts), the exact relocation script and dated change notice, licenses and the materials needed to rebuild/replace the libraries; satisfy the applicable source-delivery and modification/debugging terms. Both production and diagnostic builders run `scripts/capture_linux_sources.py`: it downloads the manifest's exact source-package versions from authenticated `deb-src` indices, checks descriptor identity and source-file hashes, and archives them with the GTK manifest, notices, relocation script, dated change notice, lock/build inputs, signed InRelease files and installed-package inventory. A missing/superseded version fails the build. Enable matching `deb-src` entries before running a native build; on Jammy the package list is in `.github/workflows/ci.yml` and `native-qualification.Dockerfile`. The `native-sources-linux-<VERSION>.tar.gz` companion stays outside the release binary naming pattern, so it does not add an unqualified asset to the release set. Production CI retains even partial captures on failure and attaches the completed archive/hash to the build artifact for 30 days. That retention is neither permanent source hosting nor release-recipient access; the distributor must preserve and provide the source beyond CI expiry. The payload carries notices, common licenses, original/modified hashes and the transformation. The distributor must arrange recipient access and independently assess the selected licenses and replacement path. No compliance approval is claimed.
