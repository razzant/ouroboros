# macOS launcher window renewal

The manual desktop workflow runs the same fixture on two frozen commits of Ouroboros, sequentially on one GitHub-hosted Mac. It asks whether Restart or Update leaves a working window on the new server, with unsent room input and running work accounted for. The second Update changes `launcher.py` and exercises the source handoff used by the signed app. The fixture runs the source launcher. The signed binary, original black screen, GPU failure and fullscreen-Space defect are outside this experiment. The fixture never invokes Panic. Unit tests exercise immediate delivery to an inert stop handler; the hosted window test does not measure native shutdown.

## Run and evidence

After independent review of the exact candidate, select its ref in **Desktop window**, enable **macos_window_renewal**, and supply the full baseline and candidate commit IDs; neither has a default. The job checks that the candidate is the dispatched revision and that the baseline is its ancestor. The same job runs the focused Python and Node tests, size ratchet and domain checks. A branch push or pull request never starts this macOS job.

Use the configured hosted Mac with code intended for publication and fictional data. The launcher opens real windows and its persistent WebKit store belongs to the runner account. Each arm has its own HOME, data, settings, work folders and Git repos underneath the safe_test root. The provider is the maintained loopback scripted model. The seed contains the frozen arm's exact tree. Its local managed mirror (`arm_source.py`, also tested with plain Git) first offers a child changing a comment in `server.py`, then a descendant changing a comment in `launcher.py`. The fixture sends the Settings Restart command and preflights and applies each clean Update with its exact base and target. It observes a lost reply without repeating the request.

The artifact contains `report.json` (schema `ouroboros.macos-window-renewal/9`) and synthetic room PNGs. The report binds each arm to its commit, observer hashes, server processes, native window and view IDs, message and reply identities, task IDs, and the loopback model's aggregate request-attribution counts. It checkpoints before each transition and after the new server answers. Each missing observation has a check or a stage in the report. Public error reasons omit page text, command output and private paths. A caught setup or cleanup error stays in the final report with its arm, stage and redacted reason. If the process itself is lost, the last checkpoint is incomplete evidence; it cannot certify either arm. Raw driver output and the safe_test evidence stay in job-owned private storage under the runner's temporary directory and are never uploaded; each settled arm's root — its HOME, data including `launcher.log`, both installations and the work folders — is removed with it, and an unconfirmed exit keeps the root under its safe_test retention marker instead. The summary also gives independent Python, Node, size and domain results. The candidate arm waits for confirmed exit of the baseline's processes.

## What the observations mean

| Observation | Evidence |
| --- | --- |
| Backend replacement | The old child PID and birth end. A different child of the same launcher binds its port and answers ready. A separate HTTP client checks state and the running update revision. Before that client creates a project, the window subscribes to `projects_changed` on its own WebSocket client. `live_connected` requires an incoming event whose `project_id` and `chat_id` match the creation response. `peer_visible` checks the new project's visible sidebar label independently, including when the three-second HTTP refresh paints it. |
| Native replacement | An inherited private socket observes the launcher's pywebview 5.4 Cocoa host on AppKit's main thread. Both views must be WKWebView instances installed as the content view of the observed NSWindow. Ordinary Restart and the first Update keep the shell, PID, NSWindow object and positive WindowServer ID. Only the candidate should change its WKWebView. The separate source handoff requires a fresh launcher image and the expected loaded revision. A changed view or document during observation leaves a gap. If the old view is still the one observed when the 25 s settle ends, that is provisional: only the final view read after the phase's steps, still the same, makes `view_new` a measured false (the baseline's control, or a candidate failure). A different or unreadable final view leaves `view_new` and every page-bound check of that phase unestablished, never green. A Project Send that the arm's own complete history reads contradicted is not page-bound: a duplicate, a leak to Main, a row outside its own room or a row lost from its accepted address stays false after that, while a negative resting only on the page's wire counter or on the captured frame does not. |
| Window use | The scenario measures native size and menu zoom, closes to the status item before Restart, and enters fullscreen for Update. After Update it waits for the same window's AppKit exit notification before Close. Open Ouroboros must return the same visible key window and installed successor view before native typing. A confirmation must reach the native Cancel button. Before Help, the fixture establishes a visible, key target on a different page and records its focus. The menu must open the visible built-in setup at `/onboarding?builtin=1` in that same installed view, from both the built-in and custom interfaces. |
| Room on return | After reopening the hidden Restart window, before selecting any room, the fixture reads whether the new server's own document visibly mounted Main. Both Updates must instead visibly mount the same named Project with its composer, and that field must accept editing and receive a hit at its centre. A different mounted room is a contradiction; an unready document or unfinished composer mount is missing evidence. Later explicit Main/Project navigation is only for independent draft and typing checks. |
| Ordinary draft | Main holds text, a reply to its saved assistant row and a tiny file. Each Update stages different text and a file in the Project, with a reply to a saved user row there. The fixture compares the exact draft text, all persisted quote fields in memory (including author, timestamp and any attachment-view reference), and separately the composer strip's visible author, local clock (ignoring the day prefix in the time and label), excerpt, thumbnail presence and label. The visible strip must jump to the original row. Neither quote shapes nor displayed parts reach the report: only the resulting check. The fixture checks the reattachment notice, empty picker and file counts without storing the fixture bytes or making an upload; in Main it also reattaches the file. |
| Project Send | Each intended Send uses exactly one native AppKit Return on the observed visible key window, with no substitute or retry on uncertainty. The captured frame must retain the Project and chat IDs, draft text and quote address. Complete Project history must have one accepted row with the original ID, sender, text and resolved reply, while complete Main history has no row matching ID or text. The observed Project feed must contain one bubble bound to that accepted row and client ID that is actually shown (display, visibility, effective opacity, the feed's clip and an exposed hit point): this is measured after acceptance, not a pre-ACK local echo. A row present but not shown at the deadline, such as one still fading in, leaves the check missing. The wire counter must be one, including when server deduplication conceals duplicates. After later transitions and cold relaunch, each previously accepted row must still be at its original room address. A complete read showing its loss or reassignment fails; an unavailable or incomplete history read leaves the result unknown. An uncaptured frame leaves native-drive proof missing; the ledger can still prove duplicate writes. Each row also records what the history reads alone contradicted (`server_kept`): the server's own complete read, never the captured frame or the page's counter. |
| Visible typing | After the Project Send and before selecting Main, AppKit types `Window` in the Project field and appends a space and a second `Window`. The field must read `Window Window` and both the WindowServer image and the WebKit snapshot must show the added letters there. Main has the same typing check on all three transitions. The final window image supplies the client-area readability check for each room. |
| Already pressed Send in Main | A normal Send must produce one accepted history row with its original message ID, sender and saved address. The old page then holds a different Send immediately before its WebSocket write. It captures the product's original reply frame, observes its local bubble and retained frame, and verifies its absence in complete server history. Each successor must offer one retry for that same ID, sender, room, content and quote. The fixture leaves retry untouched. A document-start script counts writes for each tagged fixture message and forwards them unchanged. The first Main Send calibrates the counter. Test-owned local storage retains the counts. |
| Work and Quit | Two tasks read different probes; each is named by its own submitted description (never by a marker in a roster or other request), the loopback model holds their next requests and the owner pauses one. A held request is bound to a server PID and birth only by its measured parent chain. Untied arrivals are counted from immediately before the transition; neither these arrivals nor a quiet 180 s with no tied request prove a stop. The same live task must present its saved read in a tied request without asking to read again. A wrong identity, a known terminal state or a repeated probe read contradicts continuation. The paused task must retain its typed owner-pause state with both held-request and read-probe counters unchanged; advancement in either is a contradiction, even if the activity still reports owner pause. A gateway phase or pause cause of `unknown` with both counters unchanged is missing evidence. On cold relaunch only an unknown reading is retried; the first conclusive one, with its sample, stands. Quit settles only on observed server generations that have ended. The sampled facts stay in the report. After release the live task's original ID and probe must appear in its durable result. Cold relaunch rechecks drafts, pending Send state, wire counts, the Project ledger and the pause. |
| Custom interface | A final Restart selects the synthetic interface. `sample_document_opened` checks that its button opens a local page in the successor before Help opens built-in setup, not that a diagnostic was logged. |
| Diagnostics | For each transition, a bounded read of that arm's own `launcher.log` pairs the replacement-request marker with its current-process OSLog lookup by timestamp. The report carries only the observed boolean and a fixed result, never log lines. Ordinary Restart and Update need both records; source exec can cut the asynchronous writer, so handoff reports them without gating. No matching entry or an unavailable OSLog store is not a GPU assertion or a fault injection. |
| First opening | Each launcher launch adds one entry to the arm's `opening` list, even when no server ever became ready. The entry is frozen and checkpointed at the boundary of that launch's first normal open of the Main room, whether the window was observed or not, or at an earlier failure while waiting for its ready server or checking its PID lock; later Restarts, Updates, log lines, server generations and the cold relaunch, which adds its own entry, never change it. An entry has the process state at that boundary (`exit`: a signal number or exit code, or none while the launcher was still running, which does not say it never ended) and `stages`, the labels of what that launch observably reached, in a fixed order: it was spawned; the fixture's observer loaded, imported pywebview, created the main window and reached its before-show hook (empty marker files the observer leaves in the launch's own private directory); its `launcher.log` was written to and carries the known server-spawn, server-exit, lock-refusal and uncaught-exception lines (read only past the size the log had before this launch); its PID lock names this process; a child of this launcher bound a server; the driver saw one ready. Then the window's own stages, witnessed through pywebview's `shown` and `before_load` events and around four `MainRenderer` methods whose arguments, results and exceptions pass unchanged: the observer's hook returned, the product's window setup began and returned (with `product_session_registered` when its room session and navigation delegate were installed, and `session_registration_failed_logged` for its own logged refusal), the window was shown, the product entered its own request for the window's first chat document while none was bound (`first_navigation_entered`), WebKit's `loadRequest` returned a navigation for it (`first_navigation_requested`), and that document committed, failed or finished. `inferred` names only the furthest of those window stages observed and the next one, which may still have happened unobserved. `error_classes` lists a known process-fatal signature found in the tail of this launch's own stderr file: `python_fatal_error`, `assertion_failed`, `abort_called` or `objc_exception`, with the exception name only from a short Foundation list plus PyObjC's `OC_PythonException`, and `python_exception:<class>` when that bridged reason opens with a listed Python class. `raised` names a listed Python class (else `other`) that crossed one of those product operations (`window_setup`, `document_request`, `document_commit`, `navigation_failure`) or the product's logged session registration; `navigation_errors` keeps the stage, NSError domain and code of the product's own logged WebKit navigation errors. `evidence` says whether the log, the stderr file and the markers were `present`, `absent`, `unreadable` or `unattributed` (shorter than before the launch). The stderr file is a fresh private regular file under the arm, never a pipe; it stays in the arm's private root and is removed with it or kept under the retention marker, never uploaded. Only labels and numbers from these closed tables reach the report: no line, path, message, address or stack. A stage or class that is absent is an unobserved one, not proof that it did not happen, and no entry says why a launcher exited. The entries gate no check and change no verdict, but a first launch whose window was not observed ends its arm there with a gap, and no Restart, Update or other control is sent to a window never seen. |

### Early failures, verdicts and what remains

UNSUPPORTED (4) has exactly two early exits, both recorded before any arm starts: the host is not macOS, or the safe_test disposable root (`OUROBOROS_TEST_TEMP_ROOT`) is missing. Every other missing prerequisite — no Screen Recording grant for the window capture, a launcher that never opens its window, an observer that never answers, a first probe round whose requester cannot be resolved — is a named gap and yields INCONCLUSIVE (3), never UNSUPPORTED.

INCONCLUSIVE (3) is the verdict for missing evidence: an arm that stopped in any phase (the harness import, a launcher PID-lock mismatch, a first window never observed, no new ready generation within 480 s, an old server that did not exit within 300 s, a canonical exchange, first-Send identity or pending-frame absence that was never observed, a custom interface not observed at its bound server, an unidentified Cancel); a required candidate check left unestablished — including a native Send whose input proof stayed missing, an unreadable stored quote, an unattributed held request, or a ledger row whose history or counter read failed; a calibrated candidate false whose baseline probe did not hold either; a baseline control that did not stay false or a baseline same-operation check that was not true; an arm whose exit was not confirmed, which stops the later arms; and a cleanup failure. Each appears as a gap with a sanitized reason.

FAIL (1) needs a demonstrated candidate failure: a required check observed False — a duplicated or leaked ledger Send, a restored quote whose stored shape differs, a task that verifiably stopped or diverged with no untied arrival, a view that changed where it must not — even when a different measurement was unavailable.

Before teardown, every failure already observed is checkpointed into `report.json` with its arm, stage and redacted reason; `public_reason` keeps only words the fixture or observer wrote, so no page text, log line, private path or attachment byte enters the report. What remains after the run: `report.json` and the PNGs in the job's report directory (the uploaded artifact), and, when an arm's exit could not be confirmed, its root under the safe_test retention marker. What is removed: each settled arm's root with its installations and logs. Raw stdout/stderr and the safe_test evidence stay in job-owned private storage and are never uploaded.

### Reading the typing evidence

For each room, compare `*-window-quiet-0.png` through `*-window-quiet-2.png` with the matching `*-window-typed.png`. The `update-project-` and `handoff-project-` files show the Project composer. These captures show the single WindowServer window selected by its positive window number. ScreenCaptureKit also checks its owner PID and excludes the cursor and shadow. The observer checks the installed view, visible key window, origin and geometry around every image and native input. The report records the capture source, window and view identities, image dimensions and measured field rectangle. That rectangle includes the WK client offset within the native frame, page zoom and capture scale.

In each field crop, the first `Window` and the blank space where the second will appear supply a reference for the strokes. The field's measured font gives the horizontal distance between the copies. The fixture shifts the reference by that distance and compares it with the pixels that changed from **all three** quiet images. At least 70% of each mask must be within one CSS pixel of the other. The changed area must be between 60% and 160% of the reference area and exceed three times the largest quiet-pair change plus 40 times the squared pixel scale. A background repaint or a blinking caret alone fails this check.

The same measurement applies to the `*-renderer-*.png` WebKit snapshots. On a common CSS-pixel grid, at least 60% of each capture's changed pixels must also fall within two pixels of a change in the other. The report includes both measurements alongside the PNGs.

PASS requires all candidate checks and the baseline controls, including the baseline's own Main compositor echo. The baseline must keep its view on ordinary Restart, first Update and custom-interface Restart. An older build may visibly return to Main after either Update. Its Project restoration is recorded as false and its Project-only input and Send are left unmeasured. Its Main controls still calibrate the comparison. An unfinished room mount, missing candidate image or incomplete delivery history leaves the affected check unknown. With a required check missing, the verdict is INCONCLUSIVE (exit 3). A demonstrated candidate failure yields FAIL (1), including when a different measurement was unavailable. A missing platform prerequisite yields UNSUPPORTED (4). The job never requests a privacy grant or captures a display.

## First opening only

To look at one launch rather than the comparison, enable **macos_first_open** in **Desktop window** on the reviewed ref and supply its full `candidate_sha`; `baseline_sha` is unused, and this input takes precedence over **macos_window_renewal**. One job of at most 30 minutes, with no focused suites, runs `first_open.py` (schema `ouroboros.macos-window-first-open/1`): it prepares one arm as above and starts the candidate's source launcher once. It only reads whether that first window is usable on its own first chat document: this launch's installed loopback view, visible, key and on screen, on its own server's root, with Main the mounted, editable room and the page's WebSocket connected. Nothing is navigated, closed, reopened or clicked to make it so; the journey's own opening, which may do that, is not used here. Only then does it record one WindowServer image of that window alone and type `Window Window` into Main. Only when that native evidence is positive (the letters reached the field and show in both the WindowServer image and WebKit's snapshot, and the image is readable) does it send one ordinary Settings Restart in the same session and read the successor's view identity, document, landed Main and the same image and typing. Then it stops. No Update, Panic, relaunch, second arm, task, Send or retry; an absent or contradictory native observation, or less than four minutes of `--budget` left, leaves the Restart unattempted. The budget ends the scenario's waits; the ordinary Quit and cleanup follow.

PASS means a usable first window and one Restart that renewed the WKWebView inside the same NSWindow, with Main shown and the typed letters visible: one observed Restart, not a finished repair. FAIL needs a demonstrated failure: the launcher ended before its window was usable, the old view stayed to the final read, or a probe that held in the first window failed after Restart. Anything missing is INCONCLUSIVE with a gap. Read `candidate.opening[0]` for the launch at its first-open boundary and `candidate.facts.launch_at_end` for the same launch where the scenario ended, before the fixture's own Quit. The artifact holds only `report.json` and the candidate's PNGs.
